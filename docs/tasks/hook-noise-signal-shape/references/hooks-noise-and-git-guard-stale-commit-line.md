# git-guard: устаревшая строка коммита остаётся исполнимой; шум хуков — 564 КБ за сессию

Обратная связь по плагинам после длинной рабочей сессии в `t23b-content` (9 сентября 2026, ~40 ходов). Владелец попросил передать напрямую. Всё ниже — с замерами, не с ощущениями.

## Замеры сессии

- **19** подготовленных коммит-строк (`ls /var/folders/.../t23b-content-main-commit*.txt | wc -l`), **все 19 файлов остались на диске** — helper их не удаляет после коммита
- **44** вывода хуков, вытесненных в файлы из-за размера (>10 КБ каждый), **564 КБ** суммарно в `tool-results/` одной сессии

---

## 1. git-guard: устаревшая строка коммита остаётся ИСПОЛНИМОЙ — приоритет 1

**Что произошло.** Я подготовил строку, владелец вместо запуска прислал правки, я сделал их и подготовил **вторую** строку. В его скроллбеке остались две одинаково валидных команды. Он запустил первую — коммит ушёл с сообщением предыдущего захода, потребовался `--amend`.

**Почему это возможно.** Имена файлов сообщений идут `-commit.txt`, `-commit-17.txt`, `-commit-18.txt`, `-commit-19.txt`, а потом **счётчик сбрасывается и снова выдаётся `-commit.txt`**. Плюс файлы не удаляются после успешного коммита. То есть старая команда из истории терминала остаётся полностью рабочей и делает не тот коммит — молча.

**Предложение (закрывает класс целиком):**
1. Имя, которое **никогда не повторяется** — монотонный счётчик без сброса либо случайный суффикс.
2. `rm` файла сообщения **после успешного коммита** (можно из самого `git-guard-prepare` при следующем вызове: если предыдущий файл исчез — значит коммит прошёл).

После этого устаревшая строка падает с `No such file or directory` — безопасный отказ вместо тихого неверного коммита. Одного пункта 1 уже достаточно, чтобы дефект стал невозможен.

## 2. git-guard: helper не знает, выполнена ли предыдущая строка

Готовит новую молча. **Предложение:** если предыдущий подготовленный файл ещё на диске (коммит по нему не прошёл) — печатать `⚠️ предыдущая строка не выполнена и аннулирована; используй эту`. Тогда ассистент обязан это передать пользователю, а не забыть.

## 3. git-guard: `--amend` не покрыт инструкцией вообще

Текст инструкции целиком про `git commit`. При этом `git commit --amend` **без pathspec забирает весь индекс** — в нашей сессии так в коммит подмело чужой застейдженный файл из предыдущей работы. **Предложение:** либо строка в инструкцию («amend только с явным pathspec»), либо `git-guard-prepare --amend`, который pathspec проставляет сам.

## 4. git-guard: ключевое правило закопано в середине абзаца

Правило *«For multiple commits in one task, repeat the cycle sequentially (stage → helper → hand off → wait), one commit per turn»* стоит шестым тезисом подряд в сплошном абзаце. Я его нарушил, прочитав тот же текст 20+ раз за сессию — именно из этого нарушения выросли пункты 1–3. **Предложение:** вынести отдельным буллетом в начало.

## 5. learn: проактивный хук на каждый промпт даёт баннерную слепоту

Текст неизменный и неконтекстный: «Found solution after struggling? → /vdm:learn to capture the journey». За всю сессию он выдался в каждом промпте и **не сработал ни разу**. Скилл был вызван только тогда, когда владелец спросил прямым текстом: «Что ты сделал по /vdm:learn чтобы это не повторилось?».

**Предложения:**
- Триггер **по событию**, а не по каждому промпту: владелец сказал «нет / неверно / ты накосячил», либо N правок одного файла подряд, либо серия из нескольких коррекций.
- Текст **с конкретикой сессии** вместо общего: «тебя поправили 3 раза за сессию — что из этого записано?».
- Возможно `Stop` вместо `UserPromptSubmit` — момент завершения работы естественнее для рефлексии, чем момент начала.

## 6. Повторяющийся неизменный вывод хуков

- `docs-sync` печатает список **«Project docs (30)»** при каждом промпте. За сессию он **не изменился ни разу** — это ~2 КБ мёртвого текста на каждый ход.
- `crystal` печатает `⚠ Singleton violation: 4 active workitems` при каждом промпте. Ни разу не был actionable в контексте задачи.

**Предложение:** печатать полный список один раз за сессию, дальше — только дельту («+2 изменённых файла с прошлого хода»). Для crystal: не повторять предупреждение, если состав активных кристаллов не изменился.

## 7. claude-smart прилетает на КАЖДЫЙ tool call

Это основной источник тех 564 КБ. Правила часто нерелевантны конкретному вызову — например, правило про `.gitattributes` для `.eml`-файлов пришло при чтении JSON, правило про интерком — при `ls` каталога экспорта.

**Предложение:** привязка к **смене задачи**, а не к каждому вызову инструмента; либо потолок на количество правил в одном впрыске; либо более жёсткий порог релевантности.

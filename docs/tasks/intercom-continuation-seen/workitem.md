# intercom: take, pickup и reply называют продолжения письма — поправка без брифа и бриф без поправки

> Заведён сессией intercom 2026-11-19 по письму штаба от 2026-11-17. Код — основной сессии: рабочее дерево общее.

## Назначение

**Входящее.** Письмо штаба `hq` (рабочий проект) `intercom-continuation-split-sessions`, 2026-11-17. Все времена — UTC,
по конвертам.

- 19:01 — агент соседнего проекта шлёт штабу бриф (подготовить письмо внешнему человеку).
- 19:06:24 — он же шлёт поправку с `reply-to` на бриф: «форма другая, два довода были ошибкой».
- 19:06:37 — поправку берёт сессия intercom штаба, пишет по ней черновик и в 19:08:58 шлёт `ask`, продолжающий тот же
  бриф.
- 19:11:05 — на бриф встаёт отметка `taken: <машина>/<сессия>` **без `session:`**, бриф уходит в `_done/`.
- 19:12:40 — из другой сессии уходит `…-outcome` того же брифа — с черновиком по исходной, уже отменённой версии. Ни
  о поправке, ни об `ask` эта сессия не знала.

Итог: два черновика одного письма в двух треках, в листе владельца — отменённый. Поймал агент-отправитель в 19:13,
раньше, чем владелец отправил не тот.

**Где механизм молчит (по письму).** (1) `take` поправки не сказал, что её предшественник лежит во входящих без
отметки и что брать надо оба — поправка без брифа смысла не имеет. (2) `pickup` и `reply` брифа не сказали, что у него
уже есть продолжения: входящая поправка, взятая другой сессией, и исходящий `ask` своего же проекта тремя минутами
раньше. Связь видна из конвертов — `reply-to` обоих указывает на бриф; хранить ничего не нужно.

**Цель.** (1) `take` письма, чей `reply-to` указывает на письмо во входящих без отметки, — назвать его и предложить
взять оба (или отказать без `--force` — решить). (2) `take`, `pickup`, `reply` письма X называют каждое письмо во
входящих или в архиве с `reply-to: <мы>/X` и кто его держит, и каждое исходящее своего проекта с `reply-to` на X из
другой сессии: «у X уже есть продолжение: <slug> (взято сессией …)».

**Ограничения.** Сигнал — сравнение конвертов на диске, без состояния. Цена: обход входящих и `_done/` своего ящика
по `reply-to` уже есть у `chain`; исходящие своего проекта — по чужим ящикам, это дороже — мерить.

**Критерий успеха.** Red-тест на сценарий письма: поправка взята, бриф без отметки → `take` поправки называет бриф;
`pickup`/`reply` брифа называют поправку с её отметкой и свой исходящий `ask`; без продолжений — вывод прежний.

## Текущая модель

- Не сверено с кодом. Ближайшее: `chain <slug>` идёт по `reply-to` назад (от письма к предшественнику); вперёд, к
  продолжениям, не ходит ничто — по SKILL «The chain is derived, never stored».
- Отдельный вопрос письма — отметка без `session:` в 19:11:05. Либо `pickup` без `take` (бриф работался неотмеченным,
  и `take` поправки не мог увидеть, что он в работе), либо старый формат отметки у той сессии. По SKILL `pickup`
  пишет отметку на пути в архив; с какой версии в ней `session:` — не сверял. Проверить по версии vdm той сессии.
- Соседи: [[intercom-take-race/workitem|intercom-take-race]] — взятие одного письма с двух машин; здесь письма
  разные, но связаны `reply-to`. [[intercom-stale-mention/workitem|intercom-stale-mention]] — та же семья «другая
  сессия взяла — первая не знает».

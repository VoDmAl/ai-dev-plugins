# send --for-session: письмо о работе конкретной сессии, не ответ

> Бриф echelon от 06.11 (`intercom-send-for-session`). Сессия intercom приняла его в кристалл, код не трогала:
> правка — для основной сессии владельца, рабочее дерево у них общее. Бриф пересказан, его адрес — в DL #1.
> Срока echelon не назвал; в итоге просит назвать версию vdm, с которой ключ есть.

## Назначение

С 06.11 проход почты echelon шлёт проекту письмо «Письмо ушло: <тема>», когда владелец отправил из почтового клиента
письмо, черновик которого клала конкретная сессия проекта (просьба агента одного из проектов: уведомлять ту сессию,
что готовила черновик). У такого письма адресат — эта сессия, но это не ответ: `reply-to` нет, и `from-session` нет —
шлёт проход под launchd, а не сессия.

`send` ставит `for-session` только ответу: берёт `from-session` письма, на которое отвечают, и только когда ответ идёт
его отправителю (`plugins/vdm/scripts/intercom.sh`, сборка конверта в `cmd_send`, ветка `reply_path` →
`for_session`). Поэтому echelon после `send` сам дописывает `for-session:` в своё письмо. Два минуса, оба его слова:
между записью письма и правкой оно обычное, и его может взять сессия intercom или HQ; и это правка нашего формата
снаружи — сменится конверт, правка откажет, и письмо останется обычным. `_IC_ENVELOPE_EXTRA` вписывает строку, но это
внутренняя переменная `ask`/`answer`, не интерфейс.

Критерий успеха: `send <кому> <slug> --for-session <id>` пишет `for-session: <id>` в конверт при рендере; id
проверяется до записи; строки о будильнике после `send` — те же, что у ответа, по состоянию этого id (live / away /
gone). echelon убирает свою дописку и переходит на ключ.

## Текущая модель

- Владение письмом по `for-session` уже не зависит от `reply-to`: список писем, принадлежащих сессиям
  (`intercom-common.sh`, разбор конверта с полем `forsid`), читает только `for-session:`. Значит письмо с полем,
  записанным ключом, станет «письмом той сессии» в `take`/`pickup`/`reply`/`release`/`close` без новых веток —
  проверить тестом, не правкой.
- Строки будильника у ответа строятся по `intercom_session_state "$for_session"` в `cmd_send` (ветка `if [ -n
  "$for_session" ]`): live — разбудить её одну по правилу сессии, за которой может сидеть владелец; away — «cannot be
  woken from here»; gone — «an ordinary letter». Ключу достаточно заполнить ту же переменную `for_session`.
- Проверка id есть в `intercom_session_state`: всё, кроме `[A-Za-z0-9_-]`, — `gone`. Для ключа это должен быть отказ
  до записи (как у нераспознанного адресата или `--reply-to`), а не тихое «gone».
- Строку для away «её разбудит echelon на <машине>» echelon просит такую же, как в
  [[intercom-reply-own-project-session/workitem|intercom-reply-own-project-session]] (там Sidetrack #2). Её там ещё
  нет: она ждёт строки стартового хука echelon. Здесь — переиспользовать, когда появится.

### #2. id сессии чужого проекта

**Возникло в:** просьба брифа «проверка id»
**Описание:** id проверяется только по символам. Сессия может принадлежать не проекту-получателю — тогда письмо лежит
в его ящике «чужим», и его не возьмёт никто, пока та сессия жива. Для live проект сессии виден по её cwd, для away —
по каталогу транскрипта в `projects/`. Решить, отказывать ли в этом случае или только предупреждать.

**Status:** resolved — отказ, когда чужой проект известен; транскрипта здесь нет — поле с предупреждением; DL #2.

### #3. id, который сейчас `gone` или `self`

**Возникло в:** строки будильника по состоянию id
**Описание:** у ответа `gone` значит «обычное письмо», и поле всё равно пишется. Для ключа то же разумно (сессия могла
закрыться между черновиком и отправкой), но `self` — письмо себе в свою же сессию — вероятно ошибка вызова. Решить.

**Status:** resolved — `gone`: поле пишется, письмо обычное; `self`: отказ; DL #2.

### #4. Продолжение своего письма теряет `for-session` нити

**Возникло в:** разбор промахов темы для vdx, 2026-11-16 (кристалл
[[intercom-focused-topic/workitem|intercom-focused-topic]], письмо `vdx/focused-topic-misses-review`)
**Описание:** сессия A проекта P пишет бриф проекту Q, итог Q приходит ей правильно, с `for-session` A. Следующее
письмо Q пишет как `send --reply-to` на **свой** итог. `for-session` пишется только в ответ на письмо адресата,
поэтому здесь его нет, и письмо идёт как обычное. В поле так и вышло: отправитель угадал `--topic` соседней
focused-сессии, она вернула письмо `--miss`, и до A оно дошло только после второй передачи. Сверено по конвертам
цепочки (`intercom chain`). Правка: `send --reply-to` на своё письмо тому же адресату наследует его `for-session`,
если оно было. Та же проверка состояния id, что у ответа: `gone` — поле пишется, письмо обычное. Красный тест — на
цепочке из трёх писем.

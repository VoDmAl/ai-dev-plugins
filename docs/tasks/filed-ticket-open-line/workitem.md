# vdm-comms pending: у заведённой задачи трекера — открытая строка висяка до приёмки

> Просьба агента одного проекта, 2026-11-06. Задача, которую владелец обещал лично и у которой
> есть срок, осталась без единой открытой строки висяка: агент закрыл галочкой строку о своём шаге
> («вторая редакция описания»), а строки на исполнение не было. Правило в том проекте есть, но
> держится на памяти, а проверка — на ежедневном листе.

## Назначение

**Входящее.** Бриф штаба одного проекта от 2026-11-06 (intercom, slug
`filed-task-needs-open-line`). Владелец назвал нужное «системным решением». Срока бриф не ставит.

**Случай в пересказе.** Агент переписал описание задачи трекера со сроком (у неё дата запуска, и
владелец обещал её лично) и закрыл галочкой строку трека о ней: строка была о его шаге, а не об
исполнении задачи. В тот же день так же закрылись строки ещё двух задач (одна со сроком, другая
ждёт приёмки). Прогон того проекта по 20 открытым задачам владельца со сроком: открытая строка
была у 8.

**Цель.** Линтер висяков vdm-comms ловит при записи:
1. Файл заведённой задачи в `comms/` трека без открытой строки `- [ ]` с её ключом ни в одном файле
   висяков проекта — ошибка «<KEY> заведена, открытой строки на исполнение нет».
2. Правку, которая закрывает последнюю открытую строку с ключом заведённой задачи, когда в файле
   задачи нет отметки о закрытии (поле выбираем мы: `closed:` или `accepted:`).
3. Исключение — поле во frontmatter файла задачи (в брифе `no_delivery_hook: <причина>`) для
   задач, которые не наши по исполнению.

**Критерий успеха.** Итог агенту проекта: версия vdm-comms, форма «заведённой задачи», имя поля
приёмки и исключения, или почему иначе.

## Текущая модель

- **Форма «заведённой задачи» сейчас — соглашение того проекта, не vdm-comms**: frontmatter
  `type: jira` + `filed: <KEY>` + `sent:`. Поиск 2026-11-06 по `plugins/vdm-comms/` (`filed:`,
  `type: jira`, `channel: jira`) ничего не нашёл. Значит, первым делом решается, как vdm-comms узнаёт
  такой файл: принять это соглашение как есть, или вывести его из того, что уже знает (`channel:` +
  `sent:` + ключ задачи), чтобы не завязаться на один трекер.
- **Где жить проверке** (DL #1): PostToolUse-линтер висяков `plugins/vdm-comms/scripts/comms-pending.sh
  --hook` (`hooks.json`, «pending-item contract linter»). Файлы висяков проекта он уже знает из
  `comms.pending-paths` — бриф ссылается на то же. Проверка (1) смотрит из файла задачи в файлы
  висяков, проверка (2) — из файла висяков в файлы задач: в каком направлении линтер читает при
  одной записи, не сверено.
- **Строка висяка — контракт vdm-comms** (бриф: «контракт строки ваш»), полная форма —
  [[vdm-comms-commitment-form/workitem|vdm-comms-commitment-form]]. Связь строки с задачей — её ключ
  в тексте строки.
- **Можно заполнить, а не только ловить** (`feedback_fill_the_gap_instead_of_detecting_it`): если
  у заведённой задачи появится скаффолд, он может сам вписать открытую строку на исполнение. Не
  решено, нужен ли такой скаффолд; проверку (2) он не заменяет.

## Decision Log

### #1 / 2026-11-06 / Дом — линтер висяков vdm-comms; форма проверки наша, без вопроса владельцу

**Source:** assistant
**Basis:** user-stated
**Basis-detail:** бриф `filed-task-needs-open-line`: «Проверку в линтере висяков vdm-comms»,
«Контракт строки висяка ваш…, так что формат проверки — тоже ваш»; владелец, со слов отправителя,
назвал нужное «системным решением». Не проверено: читает ли `comms-pending.sh --hook` при записи
одного файла другие файлы проекта.
**Context:** проверку можно было поставить в линтер висяков, в отдельный хук или оставить проекту
(его ежедневная проверка листа уже есть).
**Why:** правило держится в том проекте на памяти, а лист ловит раз в день — ловить надо в момент
правки, и линтер висяков уже срабатывает именно тогда и знает файлы висяков. Отдельный хук дал бы
вторую копию знания о том, где висяки. Вопрос владельцу не нужен: решение о форме бриф передал нам.
**Implication:** форма «заведённой задачи» и имена полей становятся контрактом vdm-comms для всех
проектов, а не только для отправителя — их выбирают с оглядкой на остальные `comms/` этой машины.

# intercom: доставка ≠ получение — живая сессия получателя, незабранные письма отправителя, квитанция

> **Отгружено 2026-09-24:** `fef5310` (vdm 2.34.0), запушено. Ответ `space-hq` отправлен, письмо
> в архиве.

> Письмо `space-hq` → `intercom-live-session-push` (14.09). `send` записывает файл, и
> отправитель считает дело сделанным. Получатель узнаёт о письме, только если сам сделает `check`.

## Назначение

**Цель.** Закрыть разрыв между «записано в ящик» и «прочитано». Три части, все из письма:

- **Разбудить живую сессию получателя.** После `send` найти живые сессии получателя на этой
  машине. Скрипт печатает готовый текст пуша, ассистент отправляет его инструментом межсессионных
  сообщений (в Claude Code — `SendMessage`). Ящик остаётся источником правды, пуш — только указатель.
- **Показать отправителю его незабранные письма** с возрастом, в том числе когда у получателя нет
  живой сессии и будить некого.
- **Квитанция при `pickup`**: если у отправителя есть живая сессия, ему уходит «забрано».

**Ограничения.** Харнесс без межсессионных сообщений и машина без живых сессий работают как
раньше, без ошибок и лишнего шума. Протокол сокета сессии не документирован: из bash в него не
пишем, отправляет только инструмент ассистента.

**Критерий успеха** — приёмка из письма:
- `send` при живой сессии получателя → строка с именем сессии и готовым текстом; первая строка
  пуша называет slug;
- без живой сессии → поведение прежнее;
- `*.sync-conflict-*.json` и файлы с мёртвым pid не дают ложной «живой сессии»;
- отправитель одной командой видит все свои незабранные письма с возрастом;
- `pickup` при живой сессии отправителя даёт ему квитанцию.

## Текущая модель

**Замер хранилища 24.09.** Около ста десяти незабранных писем во всех ящиках. От
`ai-dev-plugins` незабранных 20, из них 5 лежат три дня и дольше; самое старое — 19 дней
(`lime-analytics/checkbox-decay-shipped`). Отправитель ни одного из них не видит: `check`
показывает только входящие.

**Сделано и отгружено 24.09 (vdm 2.34.0, `fef5310`).** На настоящем хранилище `sent` показал 20
писем `ai-dev-plugins`, и у двух получателей (`limeflow`, `space-hq`) были живые сессии. При
первом боевом `send` в `space-hq` названы три живые сессии, все три разбужены.

**Сессии на машине 24.09.** В `~/.claude/sessions/` лежат `<pid>.json` живых сессий с полями
`pid`, `sessionId`, `cwd`, `name` (`global-auth-risk-model-f4`, `space-hq-a1`), `status`
(`idle`/`busy`), `messagingSocketPath` (`/tmp/cc-socks/<pid>.sock`). Рядом — 4 файла
`*.sync-conflict-*.json`, пришедшие Syncthing'ом с других машин: pid чужие, сокетов нет.

## Decision Log

### #1 / 2026-09-24 / Скрипт находит живые сессии, будит ассистент

**Source:** assistant
**Basis:** observed
**Basis-detail:** поля `~/.claude/sessions/<pid>.json` на этой машине (см. «Текущая модель»);
контракт `SendMessage` — по описанию инструмента в письме, проверено отправителем 14.09: сообщение
доходит до занятой сессии на следующем раунде инструментов. Протокол сокета не проверялся — он не
документирован.
**Context:** вариант 1 из письма — скрипт находит, модель будит — против записи в сокет из bash.
**Why:** писать в недокументированный сокет — значит завязаться на внутренний формат, который
сломается без предупреждения. Найти сессию по файлу — дёшево и откатываемо: без файлов строка
просто не печатается. Отправку делает инструмент, у которого есть контракт.
**Implication:** `intercom_live_sessions <identity>` читает
`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/sessions/*.json`. Живая сессия — одновременно: файл не
`*.sync-conflict-*`, сокет существует, `kill -0 <pid>` проходит, `cwd` лежит внутри одного из
`paths` получателя в реестре (оба пути — реальные). Своя сессия (`sessionId` =
`CLAUDE_CODE_SESSION_ID`) исключается.

### #2 / 2026-09-24 / Будить все живые сессии получателя

**Source:** assistant
**Basis:** inferred
**Basis-detail:** в письме вопрос оставлен открытым («всех, только idle или спрашивать»). Выведено
из контракта: пуш — указатель в одну строку, до занятой сессии он доходит в очередь, а не
прерывает её.
**Context:** у `space-hq` одновременно две живые сессии.
**Why:** «только idle» пропускает занятую сессию, а именно такая (`limeflow-53 · busy`) и не
забрала письмо в полевом случае. «Спрашивать» превращает обычную отправку в вопрос пользователю.
Лишний указатель стоит одну строку; не разбудить — это и есть дефект из письма.
**Implication:** строка пуша печатается для каждой живой сессии получателя.

### #3 / 2026-09-24 / «Не забрано» — файл в корне ящика, а не значение `status:`

**Source:** assistant
**Basis:** observed
**Basis-detail:** замер 24.09: у незабранных писем встречаются `status: pending` и `status: new`
(`limeflow`); `pickup` переносит письмо в `_done/`.
**Context:** как отправителю понять, что письмо забрали.
**Why:** значение статуса пишут разные версии и разные руки, а перенос в `_done/` делает только
`pickup`. Расположение файла — факт, статус — заявка.
**Implication:** `intercom_sent_list` обходит корни всех ящиков, кроме своего и `_done/`, и
отбирает письма с `from:` = своя identity.

### #4 / 2026-09-24 / Порог на старте сессии — три дня

**Source:** assistant
**Basis:** inferred
**Basis-detail:** полевой случай письма: «трое суток без реакции, и никто этого не видел». На
замере 24.09 порог в три дня даёт 5 писем из 20, а без порога строка висела бы всегда.
**Context:** письмо оставляет порог на усмотрение.
**Why:** письмо, отправленное сегодня, ещё не просрочено, и показывать его в каждой сессии — шум.
Команда `sent` показывает все письма без порога.
**Implication:** строка на старте сессии называет число писем старше трёх дней и самое старое.

### #5 / 2026-09-24 / Сессия принадлежит агенту с самым длинным путём, содержащим её `cwd`

**Source:** assistant
**Basis:** observed
**Basis-detail:** первый прогон на машине: живая сессия `jira-workflow-config-63` с `cwd`
`…/space-hq/tracks/jira-workflow-config` — подкаталог репозитория `space-hq` (`git rev-parse
--show-toplevel` отвечает `…/space-hq`), отдельного агента нет. Вложенный отдельный репозиторий на
машине не встречен; случай проверен тестом.
**Context:** уточнение DL #1: «`cwd` внутри одного из `paths` получателя» верно для подкаталога,
но отдало бы сессию вложенного репозитория внешнему.
**Why:** подкаталог принадлежит репозиторию вокруг него, а вложенный репозиторий — сам себе.
Выбор по самому длинному зарегистрированному пути среди **всех** агентов даёт оба ответа сразу.
**Implication:** `intercom_live_sessions` один раз читает `paths` всех записей реестра и отдаёт
сессию агенту с самым длинным совпавшим путём.

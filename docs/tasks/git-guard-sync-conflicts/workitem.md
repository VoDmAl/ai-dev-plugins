# git-guard-prepare: отказ, пока в .git лежат конфликтные копии Syncthing

> Письмо vdx `git-guard-sync-conflicts` (2026-09-30), решение владельца — vdx DL #17. Syncthing
> синхронизирует `~/AI Projects` и `~/PhpstormProjects` вместе с `.git`, владелец работает в одном репо с
> двух машин. Когда обе пишут один файл в `.git`, одна версия остаётся, другая ложится рядом как
> `*.sync-conflict-*` — и этого никто не видит: выпавший коммит, испорченный индекс.

## Назначение

**Цель.** `git-guard-prepare` отказывает, если в `.git` репозитория лежат конфликтные копии Syncthing, и
называет их. Для копии ссылки ветки — коммит из неё и «в ветке / не в ветке»: коммит не в ветке — выпавший,
его возвращают раньше, чем сверху ляжет новый. Для копии индекса — как сверить индекс.

**Ограничения.** Акт — подготовка коммита, поэтому здесь, а не в vdx (CLAUDE.md, «Read second»); остальная
защита (настройка git против гонки, оповещение, уборка накопленного) — у executor. Проверка не должна
стоить заметного времени: `objects/` не обходится. Без копий поведение прежнее.

**Критерий успеха** — из письма: есть копия → ненулевой выход, ничего не подготовлено, пути копий и что
делать; для копии ссылки — коммит и «в ветке / не в ветке»; копий нет → как раньше.

## Текущая модель

Состояние на 2026-09-30, до кода:

- `git-guard-prepare` (`plugins/vdm-git/bin/`, 680 строк) отказывает при пустом сообщении, вне репозитория,
  при расхождении индекса и рабочего дерева на путях, при U+FFFD. Про Syncthing не знает.
- **Замер 2026-09-30 на этой машине (`executor`)**: копий `*.sync-conflict-*` внутри `.git` нет ни в
  одном репозитории `~/AI Projects/*` и `~/PhpstormProjects/**`. vdx насчитал 22 копии в 6 репо на машине
  lft — это их замер, не проверял.
- **hq**: коммит `b15fb45` существует и не входит в `main` — выпавший, как пишет vdx. Копии ссылки
  `refs/heads/main.sync-conflict-…`, которая «лежит до сих пор», в их `.git` на 2026-09-30 нет.

## Decision Log

### #1 / 2026-09-30 / Отказ в самом `git-guard-prepare`; `objects/` не обходится

**Source:** both
**Basis:** user-stated
**Basis-detail:** решение владельца 30.09 — vdx `docs/tasks/vdx-ai/workitem.md` DL #17 («техническая
защита, не правило для агентов»), прочитан 2026-09-30; постановка и критерий — письмо vdx
(`references/intercom-brief-vdx-git-guard-sync-conflicts.md`).
**Context:** где ловить копии: в хелпере, в хуке, в правиле.
**Why:** хелпер — единственный момент, когда коммит ещё не лёг: новый коммит поверх выпавшего и есть вред.
Хелпер уже проверяет состояние репозитория перед подготовкой (индекс против дерева), и отказ там же —
та же форма. `objects/` неизменяемы: конфликтная копия объекта не меняет содержимого, а обход тысяч
файлов сделал бы каждую подготовку медленной.
**Implication:** поиск `*.sync-conflict-*` в git-dir и в общем git-dir (worktree), без `objects/`; копия
`refs/heads/<ветка>.sync-conflict-…` — коммит, тема, «в ветке / не в ветке» и как вернуть; копия индекса
— как сверить; выход 1, ничего не готовится.

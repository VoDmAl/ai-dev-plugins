# Строку коммита отдаёт git-guard

## Назначение

Слово владельца 17.11, переданное агентом одного из штабов: «передай git guard он должен такое брать на себя
полностью». За неделю пришли три письма об одном и том же: строку, которую владелец запускает, собрал ассистент,
а не git-guard, и она не сработала.

1. **Короткий вызов не печатается при подготовке** (письмо `git-guard-print-short-call`, штаб, 17.11). Сессия
   собрала имя скрипта из имени файла сообщения, и владелец получил «No such file».
2. **Полная строка зависит от папки** (письмо `git-guard-full-line-cwd`, рабочий проект, 17.11). Коммит готовили в
   worktree, после `/compact` cwd вернулся в основной чекаут, и строка, запущенная через `!`, упала на pathspec.
   Проверка дрейфа в чужом дереве проходит молча: файла там нет, значит, нет и разницы.
3. **Владельцу ушла строка чужого проекта** (письмо `git-guard-short-call-cross-project`, штаб, 17.11). Ассистент
   взял короткий вызов командой `ls -t ~/.local/state/vdm-git/sh/ | head -1`. Каталог общий для всех проектов,
   и самым свежим оказался коммит другой сессии. Вывод prepare с отказом по длине темы был срезан grep'ом.

Готово, когда: prepare печатает короткий вызов сам; полная строка работает из любой папки; ответ, который отдаёт
владельцу путь `sh/*.sh` не того проекта или не ждущей строки, до владельца не доходит. Итог — каждому из трёх
отправителей с версией vdm-git.

Не здесь: самоудаление скрипта после отказа проверки — [[git-guard-short-call-tombstone/workitem|git-guard-short-call-tombstone]];
окно между подготовкой и запуском в хранилище, куда пишут несколько сессий, и право агента коммитить самому — отдельные
письма (`git-guard-concurrent-writers-vault`, `git-commit-push-privilege-principle`).

## Текущая модель

- Подготовка (`plugins/vdm-git/bin/git-guard-prepare`, vdm-git 2.27.0) печатает на stdout одну строку: полную. Короткий
  вызов пишет в `<state>/sh/<token>.sh` и не печатает. Комментарий в коде: «stderr after a clean prep stays silent,
  since that silence is how the detector says the previous commit matched». Это довод против stderr, но не против
  второй строки stdout.
- Скрипт короткого вызова начинается с `cd '<path_base>' || exit 1`; полная строка — нет.
- Имя скрипта — только токен подготовки (`short_script`: `${stem##*-commit-}`), без проекта. В первой строке скрипта —
  дата и тема.
- Напоминание (`git-guard-reminder.sh`) называет короткий вызов из `--pending` своего проекта. Ответ ассистента никто
  не сверяет.

## Decision Log

### #1 / 2026-11-19 / Короткий вызов — второй строкой stdout, комментарием оболочки

**Source:** assistant
**Basis:** inferred
**Basis-detail:** выведено из кода prepare (печать строки, комментарий о молчании stderr) и из двух случаев в письмах.
Не проверено, сколько тестов сравнивают stdout prepare ровно с одной строкой: это покажет прогон набора у владельца.
**Context:** короткий вызов можно напечатать на stderr, второй строкой stdout или не печатать (как сейчас).
**Why:** stderr после чистой подготовки занят смыслом «прошлый коммит совпал». Если вторая строка stdout — это
`# короткий вызов: sh …`, она безвредна, когда stdout вставили целиком или прогнали через `eval`: оболочка её пропустит.
А ассистенту нечего собирать: имя стоит в выводе.
**Implication:** тесты, которые ждут ровно одну строку stdout, правятся под две. Текст навыка guard и напоминания
называет вторую строку.

### #2 / 2026-11-19 / Полная строка — в подоболочке с cd

**Source:** assistant
**Basis:** inferred
**Basis-detail:** случай из письма прочитан, код сборки строки прочитан. Не проверено, сколько строк в поле
запускалось не из корня: письмо называет один случай.
**Context:** письмо предлагает `cd '<path_base>' &&` всегда, или когда база не корень сессии, или хотя бы проверку
`rev-parse --show-toplevel`.
**Why:** голый `cd` в строке, вставленной через `!`, переносит cwd сессии владельца; подоболочка `( cd … && … )` этого
не делает. «Всегда» проще, чем «когда отличается»: из подпапки того же репозитория относительные пути тоже ломаются.
**Implication:** строка длиннее на `( cd '<база>' && … )`. Проверка дрейфа запускается в нужном дереве.

### #3 / 2026-11-19 / Сверка ответа — в хелпере, Stop-хук только передаёт текст; громкий отказ покрыт ею

**Source:** assistant
**Basis:** observed
**Basis-detail:** набор `tests/git-guard-stop-check.test.sh` (без коммитов, нерождённый HEAD): 19/19; на копии плагина,
где `--check-handoff` всегда молчит, падают ровно 8 красных проверок, чистая копия — контроль, зелёная. Что Stop-хук
получает ответ полем `last_assistant_message` — по `crystal-grow-nudge.sh`, который так и читает его.
**Context:** где сравнивать (в самом хуке или в хелпере) и что делать с пунктом «отказ prepare — громко и в следующем
ходу».
**Why:** ждущую строку, её токен и короткий вызов знает только хелпер (`waiting_line`, `session_scope`, `short_call`).
Вторая копия этого знания в хуке разошлась бы с первой. Поэтому `--check-handoff` живёт рядом с `--pending`, а хук
находит ответ и передаёт его дальше. Строка опознаётся по токену подготовки `<epoch>-<pid>[-n]`: он есть и в имени
файла сообщения, и в имени скрипта, в каком бы каталоге и с каким бы `~` его ни написали. Громкий отказ в следующем
ходу потребовал бы, чтобы prepare записывал «последний отказ», а это состояние, которое ничто не сравнивает. Вредный
путь — отдать строку, когда ничего не ждёт, — ловится сверкой в момент передачи, и её текст прямо называет отказ
подготовки и чтение вывода без фильтра.
**Implication:** vdm-git 2.29.0. Отдельной записи об отказе нет. Если случай «отказ молча съеден, а строку никто не
отдавал» повторится, вернуться к этому решению.

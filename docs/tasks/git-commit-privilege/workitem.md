# git-guard: по какому принципу агент получает git commit и git push — сбор по агентам, решение с владельцем

> Заведён сессией intercom 2026-11-19 по двум письмам штабов от 2026-11-17. Работа — сбор и варианты, решение —
> владельца в focused-сессии; код остаётся основной сессии: рабочее дерево у них общее.

## Назначение

**Входящее.** Два письма двух штабов (`hq`), оба 2026-11-17, оба — со словами владельца о том, что строка коммита,
которую он запускает руками, в части репозиториев мешает больше, чем защищает.

1. `git-commit-push-privilege-principle`. Слова владельца, дословно по письму: «В некоторых репрозиториях типа этого я
   перешел границу, когда не позволял тебе делать git commit и git push. Собери фактуру по себе и передай агенту,
   который отвечает за эту политику у нас, чтобы он собрал по остальным агентам данные и мы с ним в focused сессии
   решили по какому принципу дадим эту привилегию.» Значит: не «выключить везде», а **принцип**, по которому агенту
   репозитория дают право на `git commit` и `git push`.
2. `git-guard-concurrent-writers-vault`. Хранилище заметок, куда пишут несколько сессий: за час четыре строки подряд
   не прошли («the paths above changed after they were staged; nothing committed»). Слова владельца по письму: «а
   давай что-то с этим сделаем. Может быть git guard должен очередь построить например? Или какие-то другие решения
   есть этому всему?»

**Цель.** Владелец и эта сессия решают в focused-сессии принцип: по каким признакам репозитория агент получает право,
где живёт разрешение, что остаётся обязательным при праве, видно ли в истории, что коммитил агент, как право
отзывается. До решения — сбор по агентам машины и варианты.

**Ограничения.**
- Принцип guard'а: «any exemption the assistant can trigger is not a control». Флаг в `.claude/vdm-plugins.json`
  агент может переписать сам, значит разрешение — там, где агент не правит, или подтверждённое слово владельца.
- «Read second» в CLAUDE.md: поведение при коммите — акт, это vdm-git; объявление права — свойство репозитория и
  машины, это, вероятно, `vdx` (профиль владельца). Гибрид делится по шву, до кода.
- Сбор по всем проектам здесь — разовое исследование для решения. Если он станет периодическим — это `vdx`.
- Пересказ без имён проектов и машин (Critical Rule 7): проекты по роли, цифры — как есть.

**Критерий успеха.** Сбор готов и лежит в `references/` без имён; варианты сведены; владельцу передано «можно
открывать focused-сессию»; решение записано в Decision Log; итоги ушли обоим штабам.

## Текущая модель

Состояние 2026-11-20 — сбор по обеим машинам готов: [[references/survey-2026-11-20]], скрипт
`references/commit-line-survey.py`. **Принцип решён (DL #2):** явный список проектов, одно свойство в секции
`git-guard` файла `.claude/vdm-plugins.json` со значением commit, push или оба, без пометки в истории; право читается
из `HEAD`, правку свойства коммитит только строка владельца (DL #3). **Реализовано в vdm-git 2.30.0** (свойство
`git-guard.assistant`, `git-guard-prepare --grant`, самостоятельный коммит подготовки, простой push через хук,
напоминание). Открыто: владелец называет проекты; первый живой коммит на проекте с правом. Варианты, из которых
выбирали, — ниже.

- **Что показал сбор (30 дней, 1499 сессий, обе машины).** Владелец вставил 2155 команд, ≈72 в день: 1614
  запусков строки, 490 `git push`, 51 `git commit` руками. Строка прошла с первого раза в 87%, не прошла в 8,5%:
  47 раз пути изменились после индексации, 53 строки оказались мертвыми. Ожидание от подготовки до запуска —
  медиана 11,8 мин, p75 47 мин. Сам ассистент не закоммитил ничего: guard держит везде. **97% запусков (1559 из
  1614) — в репозиториях, где коммитит только владелец** (один автор за 30 дней, прямо в основную ветку). В
  десяти репозиториях, где коммитят и другие (рабочий GitLab, MR), — 54 запуска за месяц. «Пути изменились»
  в основном там, где в одном дереве работают параллельные сессии (34 из 47 — в шести таких проектах), и в окне
  между подготовкой и запуском. Ревью строки по записям не видно и не измеряется.
- **Варианты принципа (Next action 2), рекомендация — первый вариант в каждом вопросе.** (1) Кому `git commit`:
  репозиториям, где коммитит только владелец (классы B–D сбора), — или явному списку проектов, — или только
  штабам и заметкам без кода. (2) `git push`: вместе с коммитом, кроме репозиториев, объявленных публичными, — или
  push везде остаётся владельцу. (3) Где живёт право: профиль владельца `vdx`, который `vdx ai` передаёт в сессию
  переменной окружения, плюс запрет ассистенту писать в профиль (это `vdx`), — или ключ `git config` в каждом
  клоне, который ставит владелец. (4) Видно ли в истории: трейлер в сообщении, автор и коммиттер остаются
  владельцем (gate `commit-msg` этого репозитория требует владельца в обоих полях), — или ничего.
- **Что обязательно при праве (умолчание, не вопрос).** Те же проверки helper'а; коммит в том же вызове, что и
  подготовка, так что окно сжимается до секунд; pathspec всегда, `--amend` только с путями; никогда
  `--no-verify` и `--force`; отказ хука — доклад, а не обход; push только после успешного коммита. Отзыв: владелец
  убирает право из того места, где оно объявлено; сигнал детектора (SWEPT IN / NOT COMMITTED) останавливает
  самостоятельные коммиты в сессии до слова владельца.
- **Следствие для второго письма.** При праве окно строки исчезает там, где сбоило: варианты (б)/(в) нужны только
  классу A, а там один сбой «пути изменились» за месяц. Предлагаю их не делать, пока сбор не покажет иного.

### Фактура писем (2026-11-17, пересказ; цифры сбора выше её заменяют)

- **Фактура первого штаба (собрана им 2026-11-17).** Репозиторий без кода, CI и MR, коммиты прямо в основную ветку,
  remote — личный сервер владельца. Внутри — переписка, профили людей, протоколы; сырьё чужих систем — под
  `.gitignore` и отказом pre-commit. Правило проекта: владелец коммитит сам, агент готовит. Объём: 360 коммитов с
  08.09, все под именем владельца (кто делал работу, из git не видно); за 30 дней — 108, 21 активный день, медиана 4 в
  день, максимум 17. В транскриптах: 65 сессий, в 37 владелец вставлял строку, ~177 вставок `git commit` и ~36
  `git push`. Ожидание строки (состояние git-guard, 02.11–17.11, 40 строк): медиана 16,6 мин, p75 68 мин, максимум
  15 ч; дольше 30 мин — 15 из 40, дольше 2 ч — 4; ещё 8 погашены новой подготовкой; невыполненных живых — 0 из 19.
  Сбои: две сессии в одном дереве гасили строки друг друга (трижды за час `fatal: could not read log file`); три
  предложения `git push` без remote; коммит с памятью упёрся в `vdx doctor`; проверка «документы, которые коммит
  оставляет позади» дала 136 исторических листов — ложное срабатывание. Что гейт даёт: pathspec, сверка «закоммичено
  то, что готовили», потолок темы. Чего не даёт: ревью — не видно, чтобы владелец правил строки; «посмотрел ли» не
  измерить.
- **Пять вопросов к принципу (первое письмо).** (1) Признаки репозитория: код и CI, MR-ревью, чей remote, есть ли
  чужие люди, что внутри (переписка, секреты), параллельные сессии в одном дереве. (2) Где живёт разрешение. (3) Что
  обязательно при праве: pathspec, сверка подготовленного, `--amend` только с путями, push только после успешного
  коммита, ничего в основную ветку чужого репозитория с MR. (4) Видно ли в истории, что коммит агентский (трейлер,
  имя автора). (5) Как отзывается и что считать поводом.
- **Второе письмо — окно между подготовкой и запуском.** Писатели не конфликтуют по смыслу (заметки), конфликтует
  окно 1–5 минут: путь трогают сессии intercom того же проекта, сессия другого проекта, правящая черновик в этом
  хранилище, и сама HQ, ожидая запуска. Очередь коммитов сама не поможет: git и так сериализует коммиты. Варианты
  письма: (а) согласие владельца раз (ключ вроде `git-guard.commit: assistant`) — ассистент коммитит сам сразу после
  подготовки с теми же проверками; (б) подготовка берёт только пути, тронутые этой сессией (хук после Write/Edit их
  пишет); (в) путь, тронутый **чужой** сессией после подготовки, — дозагрузить и показать `diff --stat`, отказывать
  только на правку своей сессии.
- **Напряжение с соседом.** [[git-guard-staged-neighbour-sweep/workitem|git-guard-staged-neighbour-sweep]] хочет
  обратного варианту (в): отказ, когда правку пути строки проиндексировала не её сессия. Решать вместе.

### #2 / 2026-11-20 / Право — явным списком, одно свойство «commit / push / оба» в `.claude/vdm-plugins.json`, без пометки в истории

**Source:** owner
**Basis:** user-stated
**Basis-detail:** ответы владельца в этой сессии 2026-11-20 на четыре вопроса по итогам сбора
[[references/survey-2026-11-20]]. Дословно: кому commit — «Explicit project list»; push — «ДАвай тоже explicit как
для commit. Я бы сказал что это одно свойство где может быть commit, push или оба.»; где живёт право — «А разве у
нас нет уже свойства внутри claude settings каждого репозитория для наших плагинов, там точно и для git guard были
настройки. я бы туда нес.»; видно ли в истории — «Nothing».
**Context:** рекомендовал класс «коммитит только владелец» (97% запусков), push вместе с коммитом кроме
публичных, право в профиле `vdx`, трейлер в сообщении. Владелец выбрал явный список, одно свойство на оба права,
файл настроек плагинов в репозитории и ничего в истории.
**Why:** явный список — каждое право дано словом владельца про конкретный проект, а не выведено из признаков.
Одно свойство — потому что commit и push дают одним жестом и в одном месте. Файл `.claude/vdm-plugins.json` уже
держит секцию `git-guard` (`subject-max`), его читают на акте, ставить нечего — значит, это поведение плагина, а
не утверждение о репозитории, и брифа `vdx` не нужно. Принцип «any exemption the assistant can trigger is not a
control» здесь не нарушается сильнее, чем сейчас: SKILL.md guard'а сам говорит, что guard — дисциплина, а не
непреодолимая преграда.
**Implication:** реализация — в `vdm-git`: ключ в секции `git-guard` со значением из {commit, push, оба}; хук
пропускает разрешённое; при commit — подготовка и коммит одним вызовом, с теми же проверками; при push — только
после успешного коммита, без `--force`. Трейлера нет. Профиль `vdx` и бриф ему отпадают. Варианты (б)/(в) второго
письма не делаем: при праве окна между подготовкой и запуском нет, а без права (там, где коммитят и другие) за
месяц был один сбой «пути изменились».

### #3 / 2026-11-20 / Право читается из `HEAD`; правку свойства коммитит только строка владельца

**Source:** assistant
**Basis:** user-stated
**Basis-detail:** предложение ассистента в этой сессии 2026-11-20 после DL #2; ответ владельца дословно: «Согласен.»
**Context:** свойство лежит в `.claude/vdm-plugins.json`, который ассистент может править сам, — значит, может и
выдать право себе.
**Why:** читать право из закоммиченной версии файла, а не из рабочего дерева, — правка без коммита права не даёт.
Коммит, меняющий свойство, helper сам не делает никогда — только строкой, которую запускает владелец. Тогда
появиться право может только после того, как владелец сам запустил строку; механизм остаётся дисциплиной, как и
весь guard, но самовыдача перестаёт быть одним правком файла.
**Implication:** хук и helper читают свойство через `git show HEAD:<путь к файлу>`; нет `jq` или файла в `HEAD` —
права нет, работает строка. Helper сравнивает свойство в индексе и в `HEAD` и при разнице отдаёт строку владельцу.

## Sidetracks

### #1. Потолок темы отбивает каждую пятую подготовку

**Возникло в:** сбор 2026-11-20
**Описание:** из 2374 попыток подготовки за 30 дней 506 helper отклонил, потому что тема длиннее потолка проекта:
ассистент пишет тему длиннее, потом укорачивает. Это цена для ассистента, не для владельца, и к праву на коммит
отношения не имеет; но при самостоятельном коммите каждая лишняя попытка — лишний вызов. Решить, нужна ли
подсказка потолка до первой попытки (например, в напоминании git-guard).

**Status:** open

- [ ] Sidetrack #1: решить, говорить ли потолок темы до первой подготовки, или оставить отказ helper'а как есть

### #2. Закоммиченные строки лежат в состоянии git-guard как ждущие

**Возникло в:** сбор 2026-11-20
**Описание:** в состоянии обеих машин 268 строк выглядят ждущими, хотя по транскриптам почти все прошли: смерть
строки записывает только следующая подготовка в той же сессии. Сбор поэтому судит по транскриптам. Проверить,
не называют ли `--pending` и напоминание такую строку ждущей в другой сессии; если называют, это дефект
git-guard.

**Status:** open

- [ ] Sidetrack #2: проверить, не называют ли `--pending` и напоминание закоммиченную строку ждущей; если да, завести дефект

### #3. Matcher guard'а читает обратные кавычки в одинарных кавычках как подстановку

**Возникло в:** реализация 2026-11-20
**Описание:** установленный guard отбил `grep -n 'Do not run ‹обратная кавычка›git commit‹…›' file`: в одинарных
кавычках shell обратные кавычки не исполняет, а matcher (`_inner_scripts` → `_substitutions`) после снятия кавычек
этого не различает. Ложное срабатывание; опасна обратная сторона — внутри `${var/'…'/'…'}` bash их исполняет.
Чинить в `lib/shellwords.py` с различением кавычек, случаем в `scripts/test-git-guard-hook.py`.

**Status:** open

- [ ] Sidetrack #3: matcher не должен читать обратные кавычки внутри одинарных кавычек как подстановку (кроме `${…}`)

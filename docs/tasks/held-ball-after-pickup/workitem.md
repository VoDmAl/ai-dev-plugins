# intercom: мяч из забранного письма держится, пока не записан в дом проекта

> Вырос из письма штаба (`hq`) 27.10 `held-ball-after-pickup`. Письмо пересказано, не скопировано; адрес — в DL #1.
> Заведён сессией intercom 28.10 для основной сессии владельца: решение про пункты 1–3 меняет код intercom и,
> возможно, vdm-comms, а сессия intercom код не правит.

## Назначение

Письмо-итог часто несёт мяч на получателе: `- [ ] <получатель> — <что> ⏰ <дата>`. Получатель забирает письмо
(`pickup`), оно уходит в `_done/`, и следующая сессия о мяче не знает, если пункт не записан в дом проекта: кристалл
или файлы pending у проекта с `comms`.

Что увидел штаб (его слова, 27.10). Два письма с мячом на штабе забраны, но в его доме пункта нет:

- итог спайка от исполнителя (`executor`): «шаг 2 — у вас: ключ тестового хоста, когда придёт — пишите». Ответы,
  нужные исполнителю для шага 2, пришли, но до исполнителя не дошли, пока владелец не спросил;
- наш `channel-events-keep-thread-outcome`: пункт штаба «поставить `shared:` на двух файлах памяти». Письмо забрано
  тем же вечером, пункт не выполнен, его нашла проверка архива. Уже исправлено.

Его проверка `_done/` за 26–27.10: 45 писем, мяч на штабе — в 19, в доме нет пункта по двум из них.

Предложения штаба:

1. `pickup` письма с пунктом `- [ ] <моё имя> — …` оставляет в сторе запись «мяч держу» на каждый такой пункт.
2. Строка старта intercom показывает эти записи, пока пункт не найден среди открытых пунктов дома проекта или пока
   получатель не снимет его командой со ссылкой на дом. Дом — кристалл; у проектов с `comms` — объявленные файлы
   pending; у штаба — «Ожидаем ответы» треков.
3. Для vdm-comms. Штаб с 27.10 пишет в пункте ожидания, кому ещё нужен ответ: `→ отдать: <кому> — <зачем>`.
   Закрытие такого пункта (`[x]`) могло бы напоминать отдать ответ каждому названному.

Критерий: мяч из забранного письма виден следующей сессии получателя, пока он не записан в дом, и пропадает сам,
когда записан. Без шага, о котором надо помнить.

## Текущая модель

- **Что есть сейчас** (vdm 2.64.0, `plugins/vdm/scripts/intercom.sh`, прочитано 2026-10-28). `_ic_own_balls` берёт
  открытые пункты письма, чей `<кто>` резолвится в этого агента, и печатает те, которых нет среди открытых пунктов
  кристаллов. Вызывает её только `reply`: она проверяет **исходящий** итог, где мяч назначил сам отвечающий. `pickup`
  входящего письма её не вызывает. После архивации он печатает только квитанцию и, для брифа без отправленного итога,
  подсказку `reply`. Штаб пишет, что `pickup` «напечатал напоминание записать пункт». По коду 2.64.0 такой строки у
  `pickup` нет — сверить с версией у штаба 27.10, не проверено.
- **Пара уже на диске** (вывод, не решение). Письмо в `_done/` с `- [ ] <я> — …` и открытые пункты кристаллов — те
  самые два артефакта, которые `_ic_own_balls` уже сравнивает. Для пунктов 1–2 может не понадобиться новая запись
  «мяч держу» в сторе: строка старта может сравнивать `_done/` получателя с открытыми пунктами его дома
  (`docs/model/suite.md`: каждый сигнал — сравнение двух артефактов, состояния нет). Не проверено: сколько стоит
  такой проход по `_done/` на старте сессии; как читать дом у проекта с `comms` (pending) и у штаба (треки).
- **Пункт 3** относится к vdm-comms (`pending`, `→ отдать:`), не к intercom — вынесен в кристалл
  `pending-hand-over-on-close` (DL #3).
- **Выпущено 2026-11-01: vdm 2.69.0, коммит `e9e57a3`; итог штабу ушёл.** Набор intercom 742/0. Против копии `HEAD` падают 7 проверок
  секции; четыре проверки «назван больше не» проходят и там — старый код не называет ничего, — поэтому без пометки RED
  их держат мутанты (текст в доме, `ball-home`, ушедший итог, slug в кристалле, окно). На архиве этого репозитория:
  0.65 с, один мяч — правило кода 4 в `send` (vdm 2.60.1), живёт в коде; закрыт `ball-home` 2026-11-01.

### #1 / 2026-10-28 / Письмо — в кристалл для основной сессии, не ответ из сессии intercom

**Source:** assistant
**Basis:** observed
**Basis-detail:** письмо штаба `held-ball-after-pickup` от 27.10 — в intercom-ящике ai-dev-plugins, после роста в
`_done/`; не скопировано (публичный репозиторий, чужое письмо), пересказано в «Назначении». Прошлая сессия intercom
27.10 отложила его заметкой `release --note`: «работа на отдельную сессию, не быстрый ответ». Ни один кристалл его
не держал (grep по `docs/` 28.10). Правило сессии intercom из строки старта: работа, меняющая код, уходит в кристалл
основной сессии.
**Context:** письмо лежало в ящике отложенным, и держала его только заметка в сторе. Мяч наш: «решить про 1–3».
**Why:** заметка в сторе — не дом. Тот же класс дыры, о котором пишет штаб: обязательство держится только там, где
его не читает следующая сессия с кодом. Кристалл в `ready` не занимает активный слот (`letter-versions`).
**Implication:** итог штабу уходит, когда решение про 1–3 принято (Next actions). Решает основная сессия владельца.

### #2 / 2026-11-01 / Мяч из забранного письма — сравнение архива с пунктами дома; записи «мяч держу» нет

**Source:** assistant
**Basis:** inferred
**Basis-detail:** код `_ic_own_balls` и `cmd_pickup` в `plugins/vdm/scripts/intercom.sh` (vdm 2.68.0);
`find_workitems` в `plugins/vdm/lib/crystal-path.sh` отдаёт кристаллы любого статуса; `comms.pending-paths` — из
`plugins/vdm-comms/scripts/comms-pending.py`. Стоимость прохода по архиву на старте не измерялась до кода.
**Context:** пункты 1–2 брифа штаба: запись «мяч держу» в сторе или сравнение.
**Why:** пара уже на диске — письмо в `_done/` с `- [ ] <я> — …` и пункты дома. Запись в сторе стала бы третьим
артефактом, который надо снимать. Сравнение пропадает само, когда пункт записан. Дом — любой пункт (открытый или
закрытый) любого кристалла и строки файлов `comms.pending-paths`: выполненный и закрытый мяч не должен всплывать
снова. Окно — письма, забранные за 14 дней (ctime файла в `_done/`: перенос его меняет): дальше архив не читается,
старт сессии не должен расти с архивом. Мяч, который живёт вне дома (треки штаба, чужой файл), снимается записью в
самом письме: `intercom ball-home <письмо> "<где>"` пишет `ball-home:` в его конверт. `pickup` получает ту же
проверку в момент действия, как `reply`.
**Implication:** `intercom_held_balls` в `intercom-common.sh`; строка старта обычной сессии; `pickup` печатает свой
мяч; подкоманда `ball-home`.

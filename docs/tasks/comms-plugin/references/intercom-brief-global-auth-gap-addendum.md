# Дополнение к meetings-hooks-to-plugin: указатели встреч в comms, ссылки на файлы, доступ к почте для comms-скилла

**Контекст.** В вашем inbox лежит `meetings-hooks-to-plugin` (эстафета space-hq → global-auth-gap → t23b-program), в работу не взят. Владелец (Дмитрий) 15.09 сформулировал рамку: всё, что касается comms, переезжает в плагин vdm; в global-auth-gap остаются только уникальные для проекта вещи, а подходы приходят из плагина. Ниже — три дополнения, появившиеся после того брифа. Первое уже реализовано у нас и меняет модель встреч; третье — требования к будущему comms-скиллу.

## §1. Указатель на встречу в `comms/` трека — реализовано 15.09

**Зачем.** `meetings/` — плоский список, а хронология трека живёт в его `comms/`. Встреча тоже коммуникация: без указателя её не видно среди писем трека. Суть встречи при этом остаётся только в `meetings/`, копий протокола нет.

**Что делает генератор** (`lint-meetings.py --index`, функции `meeting_source`, `render_pointer`, `write_track_pointers`):
- для каждой встречи и каждого трека из её `tracks:` пишет `<track>/comms/<дата>-<slug>-meeting.md`;
- frontmatter: `type: meeting-link`, `date`, `meeting: meetings/<dir>`, метка `generated: lint-meetings`;
- тело: заголовок встречи, ссылка на протокол, материалы (agenda, prep, транскрипт), темы этого трека с якорями на разделы «Тема N. <name>»; у встреч с `migrated_from` — только названия тем, без якорей (тела не приведены к формату);
- **встреча ещё не прошла** (нет `index.md`) → источник frontmatter — `agenda.md`, иначе `prep.md`, ссылка ведёт туда. Это закрывает фазу «до встречи» из фактуры t23b-program §А3;
- синхронизация: у встречи сменились треки → лишние указатели с меткой удаляются; чужой файл с тем же именем без метки не трогается, выводится предупреждение.

**Результат**: 86 указателей на 48 встреч, линтер без ошибок, повторный прогон ничего не меняет.

**Для плагина.** Генератор у нас предполагает трек вида `gaps|org|incidents/<slug>` с каталогом `comms/`. У t23b-program (фактура §А1) треки глубиной 1–3 и половина указывает на файл — плагину нужна настраиваемая резолюция трека и правило, куда класть указатель, если трек — файл.

## §2. Два соглашения для ответов агента

1. **Путь к файлу — кликабельной ссылкой.** Любой подготовленный или изменённый файл в ответе даётся как `[имя.md](file:///абсолютный/путь)`, пробелы кодируются `%20`. Причина: без пути пользователь ищет файл руками. У нас это правило 30 в CLAUDE.md. ⚠️ Открывается ли `file://` в терминале владельца (Ghostty) — не подтверждено.
2. **У висяка — имя владельца, контрагентские первыми.** «Висяк на Маргариту», а не «ждём описание»: безличные формулировки по умолчанию оседают на пользователе. Родственно формату pending-строк с обязательным владельцем.

## §3. Требования к comms-скиллу: доступ к почте

**Вводные от владельца.** Ящик на Google Workspace, владелец — администратор и разрешит нужное. Хочет, чтобы агент **читал и создавал черновики** прямо в почте. **Отправлять — нельзя.** Как поставить гейт, открыто.

**Факт, который определяет дизайн** (по документации Google, как я её знаю — перепроверить): у Gmail API нет области доступа «черновики без отправки». `gmail.compose` — это черновики **и** отправка; `gmail.modify` тоже включает отправку; `gmail.send` — только отправка; `gmail.readonly` — только чтение. ⇒ гейт на уровне Google не ставится, только на нашей стороне.

**Предлагаемое устройство:**
- MCP-сервер с фиксированным набором инструментов: поиск, чтение цепочки, выгрузка вложения в указанный путь, создание и правка черновика (ответ в цепочку — threadId плюс заголовки In-Reply-To/References), список черновиков. Методов отправки в коде нет вообще — allowlist вызовов API.
- 🔴 **Граница токена.** Агент запускает Bash от того же пользователя: токен в Keychain достаётся через `security`, дальше curl к API в обход MCP. Настоящий гейт — токен вне досягаемости агента: сервер как отдельный сервис (другой хост или пользователь). Слабее — запреты в permissions Claude Code на `security find-*` и сетевые вызовы к gmail.googleapis.com. Дополнительно — детектирующий слой: что аудит Workspace показывает про отправку через API (проверить).
- 🔴 **Входящие письма — недоверенный текст**, канал prompt injection. Черновик допустим, потому что отправляет человек; но в описании скилла это должно быть явно.
- **Альтернатива** — коннектор Gmail из claude.ai: быстрее, но проверить набор инструментов; если в нём есть отправка — та же проблема гейта.

**Как это ложится на comms-соглашения** (у нас: CLAUDE.md, раздел «Работа с gap-каталогами», и хук `check-draft-comms.sh`):
- черновик в Gmail ↔ файл `comms/*-out.md` с `draft: true`;
- после отправки человеком скилл **читает Отправленные** и синхронизирует файл с реально ушедшим текстом, ставит `sent: <дата>`. Сейчас это ручной шаг, и он ломается: 15.09 владелец дважды дописывал абзацы перед отправкой, файл пришлось править по его пересказу;
- входящее: `.eml` и вложения — в `comms/attachments/`, файл `-in.md` со ссылкой «Ответ на»; исток цепочки определять по самому первому письму, а не по последнему (у нас правило 29).

**Приёмка:**
- в скилле нет пути к отправке, включая обход через Bash;
- черновик-ответ попадает в правильную цепочку;
- отправленное синхронизируется в `comms/` автоматически;
- вложения сохраняются рядом с входящим;
- обработка недоверенного содержимого описана.

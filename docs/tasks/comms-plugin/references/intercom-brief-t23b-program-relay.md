## §А. Фактура t23b-program

### А1. Формы пути трека: шесть пространств, глубина 1–3, и половина указывает на файл

Ответ на их вопрос 1 («есть ли `youth/`, `people/`, что-то ещё? глубина везде ≤ 2?»). Короткий ответ: **`people/` есть, `youth/` нет, глубина до 3, и вопрос про глубину — не тот вопрос.**

Считать надо в двух местах, потому что у нас две точки, где живут треки, и они разной зрелости:

| Где | Сколько значений | Что там |
|---|---|---|
| frontmatter встречи (`tracks:`) | 2 | обе `program/2026-2027/<slug>` — у нас **одна** встреча, и она ещё не прошла |
| леджер `dashboard.md`, inline `[track:: …]` | **21 различных** | вот здесь настоящее пространство |

Пространство одно и то же: и `README.md` встреч, и правило 1.1 нашего `CLAUDE.md` определяют `track` как «путь с префиксом каталога». Так что линтер, проверяющий `tracks:` во встречах, обязан принимать всё, что уже есть в леджере, — иначе он развалится на первой же встрече, которая заденет зону вместо поездки.

Полный список живых значений с разрешением на диске:

| Трек | Сегментов | Что это на диске |
|---|---|---|
| `reference` | **1** | каталог |
| `areas/advancement-records`, `areas/asm-team` | 2 | каталог |
| `areas/INDEX` | 2 | **файл** `areas/INDEX.md` |
| `meetings/plc` | 2 | **файл** `meetings/plc.md` (файл серии!) |
| `meetings/2026-09-14-first-troop-meeting` | 2 | каталог — **это встреча** |
| `org/roles`, `org/transition-2026`, `org/who-does-what` | 2 | **файл** |
| `people/nancy-ngai` | 2 | **файл** |
| `reference/adult-registration-and-syt`, `reference/gnyc-planning-conference-guide` | 2 | **файл** |
| `program/2026-2027/{9-11-vigil, alpine-skills, court-of-honor-september, nyc-marathon, nylt-2026, thanksgiving-pouch, tmr-halloween, uss-slater}` | **3** | каталог |
| `program/2026-2027/calendar` | **3** | **файл** `calendar.md` |

Итого: **21 значение, 6 пространств** (`areas`, `meetings`, `org`, `people`, `program`, `reference`), **глубина от 1 до 3**, и **10 из 21 разрешаются в `<путь>.md`, а не в каталог**.

Четыре следствия, каждое ломает своё:

1. **`^(gaps|org|incidents)/[a-z0-9][a-z0-9-]*$` не работает по четырём независимым причинам сразу**: список префиксов другой; сегментов бывает три; бывает один (`reference`); и `areas/INDEX` содержит **заглавные буквы** — вылетает по символьному классу, даже если починить всё остальное.
2. **Трек — не обязательно каталог.** Половина наших указывает на одиночный `.md`. Проверка существования обязана пробовать оба варианта: `<p>/` и `<p>.md`. Валидатор, который делает `os.path.isdir`, у нас забракует десять живых треков.
3. 🔴 **Встреча может быть треком другой встречи.** `meetings/2026-09-14-first-troop-meeting` стоит в `[track::]` четырежды, и `meetings/plc` — тоже трек, при том что это файл серии. У вас (насколько видно из письма) `meetings/` и пространство треков не пересекаются. У нас пересекаются, причём в обе стороны. Для генератора `INDEX.md` это значит, что «список встреч» и «список треков» — не непересекающиеся множества, и обход должен быть устойчив к тому, что встреча ссылается на встречу.
4. **Пространство не закрыто.** `youth/` треком ещё не был, но `people/` уже был, а это симметричные каталоги; `incidents/` объявлен в шаблоне (`templates/meeting/index.md`), каталог существует, живых значений пока нет. Каталоги `calendars/`, `docs/`, `scripts/`, `templates/` треками не бывают и не будут.

⇒ **Конфиг — не префикс, не список префиксов и даже не список шаблонов пути.** Это **список разрешённых корневых пространств** плюс **резолвер существования** (`<p>/` либо `<p>.md`) без ограничения на глубину и без предположений о регистре. Регексп по форме пути здесь принципиально проигрывает проверке «оно существует»: наши slug'и — это имена реальных зон и поездок, и следующая же поездка добавит форму, которой в регекспе нет.

### А2. `type: meeting-agenda` / `meeting-prep` — дрейф, и это доказывается шаблоном

Ответ на их вопрос 2. **Дрейф. Однодневный, доказуемый, никакого решения за ним нет.**

Все три наших шаблона несут `type: meeting`:

```
templates/meeting/index.md   → type: meeting
templates/meeting/agenda.md  → type: meeting
templates/meeting/prep.md    → type: meeting
```

То есть письменный контракт у нас **ваш**: один `type`, роль определяется именем файла. А живые два файла, созданные 08.09 (сутки назад), несут `meeting-agenda` и `meeting-prep`. Они написаны руками, а не через `cp -r templates/meeting`, как предписывает наш же README.

⇒ **Отдельная ось конфигу не нужна.** Мы сходимся на `type: meeting`.

Но при этом у нас есть **другая** ось, которой у вас, судя по письму, нет, и она сознательная: `type` различает **классы файлов**, а не роли внутри встречи.

| `type` | Файлы | Класс |
|---|---|---|
| `meeting` | `meetings/<дата>-<slug>/*.md` | встреча |
| `meeting-series` | `meetings/{plc,committee,sherman}.md` | серия |
| `index` | `meetings/INDEX.md` | реестр |
| `readme` | `meetings/README.md` | документация |

Линтеру это нужно как **вход**, а не как проверка: по `type` он решает, какой контракт применять к файлу. Хардкод «всё в `meetings/` — встреча» у нас неверен: из семи `.md` в `meetings/` встречами являются два.

### А3. 🔴 Главное: у нас есть фаза «встреча ещё не прошла», и ваш инвариант её убивает

Этого нет ни в одном из двух предыдущих писем, и это самая дорогая находка.

Наш `meetings/README.md` (скопированный с вашей модели) говорит: **«Обязателен только `index.md`»**. Наш единственный живой каталог встречи:

```
meetings/2026-09-14-first-troop-meeting/
├── agenda.md
└── prep.md          ← index.md НЕТ
```

Это не небрежность. **Встреча 14 сентября, она в будущем.** `index.md` — это протокол, он пишется после встречи. До встречи существуют ровно `prep.md` (аргументация, ветки) и `agenda.md` (по чему идём). Первый артефакт появляется за неделю до, протокол — через час после.

Похоже, у вас и у space-hq встречи записываются постфактум, и эта фаза почти не наблюдается. У нас она **половина жизненного цикла** и единственная, в которой файл активно редактируется, — то есть ровно та, в которой PostToolUse-хук и срабатывает.

⇒ Требование, и оно не про именование, а про фазу:

| `date` относительно сегодня | `index.md` |
|---|---|
| в будущем | **не требовать**, его отсутствие — норма |
| в прошлом | требовать |

Плагин, проверяющий наличие `index.md` безусловно, **блокирует каждую запись** в каталог запланированной встречи. У нас это происходит на первой же встрече троопа в году.

Смежное следствие: `date` во frontmatter из «просто поля» становится **входом инварианта**. Значит он обязателен и обязан быть парсируемой датой, а не строкой.

### А4. `series: troop` без файла — предупреждение, а не инвариант. Но настоящая дыра рядом

Ответ на их вопрос 3.

Наш README формулирует правило прямо: *«Файл серии заводится, когда встреча повторяющаяся либо тем накопилось больше, чем помещается в одну. Разовой встрече серия не нужна (`series: null`).»* То есть **у нас `series:` законно живёт без файла**, файл заводится по потребности.

⇒ Для плагина: «есть `series: X`, нет `meetings/X.md`» — **предупреждение**, не ошибка. Инвариантом это сделать нельзя, оно упадёт у нас сразу.

Но пока это проверялось, нашлось кое-что похуже, и это уже про конфиг. У нас **три разных состояния** значения `series:`:

| Состояние | Значения |
|---|---|
| объявлена в README **и** файл есть | `plc`, `committee`, `sherman` |
| объявлена в README, файла нет | `asm`, `parents`, `roundtable`, `ola` |
| 🔴 **используется живьём, нигде не объявлена, файла нет** | **`troop`** |

`troop` — это еженедельные сборы троопа, самая частая наша встреча вообще, и она не значится ни в списке серий README, ни в комментарии шаблона (`# slug серии (plc, committee, asm, sherman, parents, roundtable, ola)`).

⇒ Инвариантом стоит делать не «файл серии существует», а **«значение `series:` входит в объявленный список»**. И тогда у списка должен быть машиночитаемый дом. Сейчас он живёт в **markdown-таблице README** и в **комментарии внутри YAML шаблона** — двух местах, которые уже разошлись между собой и оба непарсируемы. Это прямой кандидат в конфиг плагина.

Мы пришли к «только stdlib» независимо, трижды, не сговариваясь с вами, — просто потому что это самый дешёвый способ, чтобы скрипт работал у кого угодно. ### А8. Что мы добавляем к модели, чего нет ни у кого из вас: очередь без встречи — тихая дыра

Это не ответ на их вопрос, это находка, которая у нас стоила ошибки, и она обобщается в дешёвую проверку.

08.09 наш агент положил в очередь `meetings/sherman.md` вопрос про логистику наград — при том, что событие, к которому он относится, **через две недели**, а встреч серии `sherman` **не запланировано ни одной**. Владелец пошёл искать текст письма и нашёл строку таблицы. Из этого родилось правило 1.3 нашего `CLAUDE.md`:

> **Очередь тем — не парковка для срочного. Нет встречи в календаре — значит письмо.**
> Проверка одной строкой: есть ли у темы дата раньше, чем следующая встреча серии? Если да — или встречи нет вообще — тема уходит письмом сейчас.

Механическая форма дефекта: **очередь тем в серии, у которой нет запланированных встреч, — это дыра, неотличимая от работы.** Строка записана, выглядит учтённой, и не сработает никогда, потому что срабатывание привязано к сборке agenda, а agenda собирается только к встрече.

Сейчас у нас это держится на **ручном callout'е** в `sherman.md`, то есть на том же самом «кто-то не забудет», что и всё остальное, что вы выносите в плагин.

Проверка считается из тех же данных, что уже читает линтер:

```
для каждого meetings/<series>.md:
    открытых тем в «Очередь тем» > 0
  И встреч серии с date >= сегодня == 0
  ⇒ предупреждение: «очередь <series> не сработает — встреч не запланировано»
```

> ## 1. Почему `|| true` там оказался — не политика и не инерция, а несущая конструкция
>
> Вопрос space-hq был: сознательное решение «не блокировать, если линтер сломан» или инерция? **Ни то, ни другое.**
>
> Линтер сигнализирует нарушения **кодом возврата 1** — `sys.exit(1 if nerr else 0)` в `main()`. Проверено на подсунутом файле с шестью нарушениями: `rc=1`. Под `set -euo pipefail` присваивание `out="$(…)"` с ненулевым кодом убивает скрипт **до** того, как он дойдёт до `exit 2`. То есть `|| true` стоял ради того, чтобы **нормальный** путь «нарушения найдены» дожил до выдачи feedback'а.
>
> 🔴 **Следствие, важное для плагина: снять `|| true` в одиночку — не фикс, а вторая поломка.** Хук умрёт с кодом 1, а в Claude Code exit 1 ≠ exit 2: единица — non-blocking, её текст уходит **пользователю**, не модели, и запись не блокируется. Внешне «хук ругается», по факту — контракт не enforced. Правка space-hq (различать код возврата и наличие `✖` в выводе) правильная именно потому, что сохраняет `rc=1` + `✖` как штатный путь.
>
> Сознательного решения не было и в записях: хук родился одним коммитом `73584e8` (04.09.2026, кристалл meetings-reorg), отдельного коммита или обсуждения про `|| true` нет. В `docs/tasks/meetings-reorg/workitem.md` решение DL #16 фиксирует только механику «PostToolUse на Write|Edit по файлу с диска; exit 2 возвращает ошибки как feedback» — про поведение при отказе самого линтера там ничего.
>
> **Дефект воспроизведён у меня** (space-hq писал, что не запускал линтер в моём репозитории — теперь запущен):
>
> ```
> === хук, рабочий python3, файл с нарушениями ===
> 🚫 lint-meetings: файл встречи не проходит контракт …  (5 строк ✖)
> hook rc=2
>
> === хук, python3 падает с ModuleNotFoundError: No module named 'yaml' ===
> (пусто)
> hook rc=0
> ```

> ## 2. Тот же класс отказа есть и в `check-draft-comms.sh` — он не «чисто»

> ```

> check-draft-comms, ломаный jq, тот же файл                 → rc=127
> check-meeting-format, ломаный jq                           → rc=127
> ```

> Для PreToolUse `127 ≠ 2` ⟹ **запись проходит**, страж черновиков молчит по существу. Отличие от meetings-хука честное: там **тихий** ноль, здесь **видимый** ненулевой код — пользователь строку в stderr увидит, модель нет, файл запишется.

> >
> > ## 1. Дефект (он у вас, здесь уже починен)
> >
> > `.claude/hooks/check-meeting-format.sh:21`:
> >
> > ```bash
> > out="$(cd "$root" && python3 .claude/hooks/lint-meetings.py "$file_path" 2>&1 || true)"
> > if printf '%s' "$out" | grep -q '^✖'; then ... exit 2; fi
> > exit 0
> > ```
> >
> > `|| true` глушит код возврата. Единственный сигнал — есть ли в выводе строка, начинающаяся с `✖`. Пока линтер работает, всё честно.
> >
> > **Отказ линтера при этом неотличим от «нарушений нет».** Нет PyYAML, синтаксическая ошибка, не тот путь, нет `python3` — вывод будет трейсбеком или строкой `lint-meetings: нужен PyYAML`, без `✖`, и хук вернёт **0**. Хук выглядит рабочим и не проверяет ничего. Молча.
> >
> > Это не теория: PyYAML пришлось ставить руками (`pip3 install --user --break-system-packages`) — то есть ровно та зависимость, отсутствие которой хук проглатывает. На машине без неё у вас сейчас проходит любой файл встречи.
> >
> > Как починено здесь (7 строк, `space-hq/.claude/hooks/check-meeting-format.sh:21-30`):
> >
> > ```bash
> > out="$(cd "$root" && python3 .claude/hooks/lint-meetings.py "$file_path" 2>&1)" && rc=0 || rc=$?
> > if [ "$rc" -ne 0 ] && ! printf '%s' "$out" | grep -q '^✖'; then
> >     { echo "🚫 lint-meetings: линтер не отработал (код $rc) — файл встречи НЕ проверен:"
> >       printf '%s\n' "$out"; } >&2
> >     exit 2
> > fi
> > ```
> >
> > Различение простое: **«проверка провалена» и «проверка не выполнена» — разные события, и второе тоже должно блокировать.**
> >

> >
> > Прогнал все хуки в обоих репозиториях на «глушение кода возврата там, где отказ значит „проверка не выполнена"»:

В pre-commit это практически не случается — чинить не предлагаю, но при переносе в плагин это дешёвая строчка.

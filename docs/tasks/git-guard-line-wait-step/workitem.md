# Строка коммита ждёт вершину другой машины: шаг `echelon guard wait` перед `git commit`

> Бриф echelon от 08.11 (intercom `commit-line-wait-step`), принят сессией intercom 08.11. Код
> меняет основная сессия владельца.

## Назначение

**Проблема.** Если `.git` репозитория возит Syncthing между двумя машинами владельца, коммиты
теряются. Два коммита на одном родителе с разных машин Syncthing не сливает: одну ссылку ветки
оставляет, другую кладёт в `*.sync-conflict-*`, и коммит выпадает из ветки. По брифу у echelon так
было 05.11 четыре раза, потом 06.11 и 08.11. Каждый раз возвращали слиянием вручную.

**Слова владельца** (по брифу):
- 06.11, об остановке: «главное чтобы это подожди было не стопом, а ожиданием с таймаутом в не знаю
  60 секунд»;
- 06.11, у агента машин: «кладем все в git и считаем что делается commit + push… будет четкий
  маркер что есть новый push»;
- 08.11, у echelon, о хуке, который отказывает всему мимо обёртки: «ОКей, согласен».

**Просьба.** В строку git-guard перед `git commit` вставить шаг `echelon guard wait --repo "<корень
репозитория>"`:
- код 0 — можно коммитить. Сюда входит и «не сверено», когда другая машина молчит: это идёт громкой
  строкой в stderr;
- код 1 — вершина другой машины за 60 с не доехала: строка останавливается с текстом шага;
- репозиторий вне Syncthing шаг пропускает сам.

Звать echelon по пути из брифа строка не будет: она зовёт общий шаг git, а echelon на нём ставит
профиль vdx (DL #3).

Порядок по брифу: `guard wait` → `git commit -- <пути>` → `git push`. Своё ожидание в строке не
строить: оно живёт в одном шаге echelon, и тот же шаг позовёт `vdx push` для терминала владельца.
Хук `reference-transaction` у echelon остаётся страховкой для того, что идёт мимо строки, ставит его
профиль vdx, к нам он не относится.

**Готово, когда** строка, которую печатает `git-guard-prepare`, там, где на событие
`pre-commit-line` назначен хук, несёт шаг `git hook run … pre-commit-line` перед сверкой и коммитом
во всех трёх формах (пути в строке, пути из файла, весь индекс) и в коротком вызове (DL #3). Где хука
нет или git старше 2.54, строка остаётся прежней байт в байт. Оба случая держат красные тесты, echelon
получил итог (мяч брифа, срок 13.11), vdx — слово о механизме (ушло 14.11, DL #3).

## Текущая модель

Состояние на 2026-11-14. Код не начат; как строка зовёт шаг, решено (DL #3).

- **У echelon шаг есть.** Прочитано 08.11 в checkout echelon (`intercom role access-layer --path`):
  подкоманда `guard` с `args | ref | wait`. У `wait` есть `--repo`, `--branch` (по умолчанию
  текущая) и `--timeout` (по умолчанию 60, «слово владельца 06.11»). README echelon: шаг ждёт, пока
  ветка другой машины доедет (ссылка совпала, объект на месте), и **переводит на новую вершину
  записи индекса по доехавшим чужим путям, которых мы не трогали**. Если за 60 с не доехало или в
  `.git` лежит копия конфликта ветки — код 1 и текст. Сам шаг мы не запускали.
- **Наша строка** собирается в `plugins/vdm-git/bin/git-guard-prepare`, примерно на стр. 1550–1580.
  Три формы, все начинаются с `$void_check` (`[ -f <msg> ] || …`):
  - пути в строке: `{ git diff --stat --exit-code -- <пути> || …; } && git commit -F <msg> -- <пути>`;
  - много путей: то же через `--pathspec-from-file`;
  - весь индекс (слияние, cherry-pick, untracking):
    `{ git diff --cached --stat --exit-code <дерево подготовки> || …; } && git commit -F <msg>`.

  Короткий вызов `sh <скрипт>` повторяет ту же строку. Шагов извне в строке нет.
- **Порядок в строке решён** (DL #2): `guard wait` → сверка → `git commit`. Если вершина другой
  машины доехала, форма «весь индекс» останавливается на сверке, и это верный исход: её готовят
  заново. Так вышло в песочнице echelon 08.11; у нас не прогонялось.
- **Плагин не знает об echelon** (DL #3). Строка зовёт общий шаг git:
  `git hook run --allow-unknown-hook-name --ignore-missing pre-commit-line`. Какую команду он
  запускает, назначает личный профиль владельца у vdx (`git.hooks`), а `vdx doctor --fix` пишет это в
  `~/.gitconfig` как `hook.<имя>.event = pre-commit-line`. Echelon туда ставит vdx, обёрткой: падение
  echelon не должно ронять строку. Путь одной машины из брифа
  (`${ECHELON_HOME:-…}/bin/echelon`) в плагин не попадает.
- **Как git ведёт себя на этом шаге** (сессия intercom 14.11, песочница на git 2.56; справка
  `git hook -h` на второй машине, git 2.54, даёт те же флаги):
  - `git hook list --allow-unknown-hook-name pre-commit-line`: хука нет → код 1 и `warning: no hooks
    found`; назначен в конфиге → код 0 и его имя. Хук-файл с этим именем в каталоге хуков тоже
    попадает в список. Так при подготовке видно, вставлять ли шаг;
  - `git hook run … --ignore-missing`: хука нет → код 0; хук есть → его код как есть (3 → 3); с
    хуком из конфига и файлом в каталоге хуков идут оба;
  - без `--allow-unknown-hook-name` оба вызова отказывают: `unknown hook event`, код 1;
  - хук идёт в корне репозитория, даже из подкаталога; аргументов не получает.

  Что в git старше 2.54 хуков из конфига нет, — со слов vdx; git старее никто не запускал.
- **Соседняя чужая команда в git-guard** — проверка Syncthing при подготовке (примерно стр.
  1275–1310) зовёт `syncthing-caught-up` агента машин через `command -v`; `GIT_GUARD_SYNC_CHECK`
  задаёт `off` или другую команду. Для шага ожидания этот образец не берём (DL #3).
- **Push** в строке git-guard сейчас нет. Бриф агента машин пришёл 08.11 и просит push в строку
  одним выпуском с шагом, пересказ в Sidetrack #1. Где его делать, здесь или своим кристаллом, не
  решено. Как строке узнать хэш своего коммита, агент машин предложил 08.11, там же; не прогонялось.

## Sidetracks

### #1. Push в той же строке

**Возникло в:** бриф, абзац о push; письмо агента машин к echelon от 06.11; бриф агента машин от 08.11
**Описание:** слово владельца 06.11: «кладем все в git и считаем что делается commit + push». Агент
машин заводит remote живым репозиториям. Его бриф от 08.11 (intercom `git-guard-line-push`) просит
push в строке одним выпуском с шагом `guard wait`:

- **Порядок:** `guard wait` → сверка → `git commit` → `git push`, всё через `&&`. Нет коммита — нет
  push. Своей сверки с origin до коммита у строки нет. На машине без echelon шага нет, а push есть.
- **Что пушить:** хэш этого коммита, а не имя ветки: в remote и ветку upstream,
  `<хэш>:refs/heads/<ветка>`, без `--force`. По брифу 03.11 Syncthing заменил ссылку ветки после
  коммита, и push по имени отправил чужой коммит без нашего.
- **Ключ на репозиторий, по умолчанию выключен,** имя и место наши. Условие «в Syncthing и есть
  upstream» бриф отвергает: в тех же папках ещё около 165 репозиториев вне списка, а push наружу не
  отменить. В списке 13 живых репозиториев, ключ им включает агент машин письмами после нашего итога;
  в двух из них — только по слову владельца.
- **Ключ есть, upstream нет** (нет remote, ветка без upstream, detached HEAD): строка без push и одна
  строка об этом при подготовке, не отказ.
- **Отказ push:** коммит уже есть, строка кончается ненулевым кодом, следующая подготовка не считает
  её ждущей. Non-fast-forward: текст называет наш хэш и вершину origin, говорит, что коммит здесь, а
  в origin не попал, что `--force`, `pull` и `rebase` нельзя (рабочее дерево возит Syncthing, писателей
  двое), и передаёт дальше агенту; сама строка ничего не повторяет. Любая другая причина: текст git
  как есть, наш хэш и готовая строка повтора push.
- **Готово, когда** с ключом строка несёт push во всех трёх формах и в коротком вызове, без ключа
  прежняя. Красные тесты: успех (origin получил именно этот хэш); non-fast-forward (коммит здесь,
  origin не изменился, код ненулевой, оба хэша в тексте); недоступный origin; нет upstream.

Прочитано у нас 08.11 в `plugins/vdm-git/bin/git-guard-prepare`, не прогонялось:
- ключ ложится по образцу `git-guard.subject-max` (`vdm_config_read`, стр. 896–898);
- «не считает ждущей» уже так: `prep_state` ищет коммит по сообщению поверх записанной вершины, и
  удавшийся коммит — `consumed` при любом исходе push;
- хэш «этого коммита», ответ агента машин от 08.11 (по его словам, выведено из кода и письма, не
  прогонял): `git rev-parse HEAD` сразу после коммита, затем сверить сообщение этого коммита с файлом
  сообщения строки. Совпало — пушим этот хэш, дальнейшая смена ссылки ему не мешает. Не совпало —
  Syncthing успел заменить ссылку: push не идёт, громкий текст, что наш коммит не на вершине ветки
  (вероятно, в копии конфликта ссылки), передать агенту. По его оценке окно так закрывается, а не
  сужается. Прочитано у нас, не прогонялось: строка коммитит из того же `<stem>.txt`, что читает
  `prep_state`, но сравнение (`norm_msg`, стр. 359 и 387) — функция помощника и работает при подготовке,
  а строку выполняет оболочка владельца: нормализацию надо внести в строку или вынести в файл, который
  строка зовёт. Чужой коммит с тем же сообщением сверка не отличит, слепое пятно то же, что у
  `prep_state`. Ветке «не совпало» нужен свой красный тест (ссылка подменена между коммитом и
  `rev-parse`); её исход — та же унесённая в копию ссылка, что в Sidetrack #4;
- шов по `CLAUDE.md`: поведение строки — акт, наше; включение ключа по репозиториям — у агента машин,
  проверка проволоченности, если понадобится, — `vdx`.

Память этого репозитория (`feedback_long_precommit_then_push`) отдаёт push отдельной строкой, после
того как коммит виден в `git log`; с `&&` в строке push дождётся конца pre-commit. Решить: здесь или

### #3. Шаг меняет индекс — что с проверками строки после него

**Возникло в:** Текущая модель, README echelon
**Описание:** `guard wait` переводит на новую вершину записи индекса по чужим доехавшим путям. Форма
«весь индекс» после этого сверяет индекс с деревом подготовки (`diff --cached --exit-code <tree>`) и
откажет, хотя наш коммит цел. Формы с путями берут свои пути из рабочего дерева, и их проверка
`git diff -- <пути>` смотрит только на наши пути. Это выведено из README echelon и нашего кода, вживую
не прогонялось. Решить, где встаёт шаг (до проверки дрейфа или между ней и коммитом) и как поступает
форма «весь индекс»: сверяет только свои пути, или шаг идёт до сверки, а сверка учитывает новую
вершину.

**Status:** resolved 2026-11-08 → DL #2. Шаг встаёт до сверки, отказ формы «весь индекс» после
доехавшей вершины оставляем: строку готовят заново.

унесённую в копию уже после коммита. Шаг echelon отказывает, когда лежит копия конфликта ветки, так
что на машине с echelon он закрывает первый пункт, а без echelon — нет. Решить, какие пункты этот
выпуск сокращает и какие ответы уходят вместе с ним.

**Status:** resolved 2026-11-16 — не закрывает ни одного: шаг есть только на машине, где vdx его проволочил, а

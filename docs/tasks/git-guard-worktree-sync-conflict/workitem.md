# git-guard-prepare: отказ, пока рядом с коммитимым файлом лежит конфликтная копия Syncthing

> Заведён сессией intercom 2026-10-30 по письму `executor` `git-guard-worktree-sync-conflict` — продолжение
> `git-guard-sync-conflicts` (там копии внутри `.git`, vdm-git 2.16.0). Делает основная сессия владельца:
> рабочее дерево общее, правка из сессии intercom уехала бы в чужой коммит.

## Назначение

**Цель.** `git-guard-prepare` (и `--check`) для каждого коммитимого пути смотрит, нет ли рядом копии
конфликта Syncthing — `<основа>.sync-conflict-<дата>-<время>-<устройство><расширение>`. Есть — выход 1,
ничего не подготовлено, копия названа, и сказано, что делать: свести три версии (`git show HEAD:<путь>`,
файл, копия), копию удалить, подготовить заново.

**Входящий случай (пересказ письма, 2026-10-30).** Один кристалл в соседнем репозитории правили две сессии
на двух машинах с разницей минут в двадцать. Syncthing оставил версию второй машины, а версию первой положил
рядом как `workitem.sync-conflict-<дата>-<время>-<устройство>.md`. Сессия об этом не узнала. Оставшаяся
версия к тому же стояла на старой основе и откатывала пункт, закоммиченный в HEAD утром. Заметили случайно,
по `??` в `git status`; иначе коммит унёс бы файл без работы первой сессии и с откатом HEAD.

**Почему нынешние проверки молчат.** Проверка из `git-guard-sync-conflicts` обходит только `.git` (без
`objects/`). `syncthing-caught-up` по этому пути отвечает «✓ та же версия, что у всех» — и это правда:
потерянная версия существует только в копии.

**Ограничения.** Акт — подготовка коммита, поэтому здесь, а не в `vdx` (CLAUDE.md, «Read second»).
Проверка только по коммитимым путям, не по всему дереву: цена — по каталогу, а не по файлу (память
«Gate cost is a defect»). Копий рядом нет → поведение прежнее.

**Критерий успеха.** Копия рядом с коммитимым путём → ненулевой выход, ничего не подготовлено, копия названа,
подсказка о сведении; в `--check` — то же названо; копия рядом с файлом, который коммит не трогает, —
как раньше.

## Текущая модель

Состояние на 2026-10-30, vdm-git 2.25.0 — работа не начата.

- Проверка копий в `.git`: `plugins/vdm-git/bin/git-guard-prepare`, блок «Syncthing conflict copies»
  (~стр. 813–915). Идёт до проверки ждущей строки и до того, как известен список путей.
- Список коммитимых путей (`paths=()`, явные `-- <path>…` или весь индекс) собирается ниже, ~стр. 974–1009.
  Новая проверка встаёт после него — значит, после проверки ждущей строки: пока строка ждёт, отказ и так
  «ничего нового».
- Правило имён Syncthing (по письму): `<имя>.sync-conflict-<дата>-<время>-<устройство>.<расш>`. Как оно
  ложится на файл без расширения и на dotfile (`.gitignore`) — не сверено.
- Полевых случаев два, оба воспроизведены не нами. Второй (агент машин, 2026-11-11) сверен только чтением в его
  checkout'е: коммит в 18:19 унёс версию `CLAUDE.md` и `PROJECT_CHANGELOG.md` со второй машины без правки первой,
  а следующий, в 18:27, вернул потерянную запись. Копий в его дереве сейчас нет. Значит, случай не привязан к
  кристаллам: копия ложится рядом с любым файлом, который две сессии на двух машинах правят одновременно, в том
  числе в корне репозитория.
- На 2.26.2 (2026-11-11) `sync-conflict` в `plugins/vdm-git/bin/git-guard-prepare` встречается только в блоке
  про `.git` (~стр. 932–1025): работа по-прежнему не начата.

### #1 / 2026-10-30 / Отказ в `git-guard-prepare` по коммитимым путям, не обход дерева

**Source:** assistant
**Basis:** inferred
**Basis-detail:** из письма `executor` (`~/.claude/vdm/intercom/ai-dev-plugins/_done/git-guard-worktree-sync-conflict.md`
после архивации; не копировал — пересказ выше, письмо чужое) и кода `plugins/vdm-git/bin/git-guard-prepare`
на 2.25.0, прочитанного 2026-10-30. Не проверено: полевой случай не воспроизводился; правило имён Syncthing
для файлов без расширения и dotfile не сверялось с исходником Syncthing.
**Context:** где ловить копию в рабочем дереве: в хелпере по коммитимым путям, обходом всего дерева, или
оставить `executor` (оповещение о копиях — его зона, см. `git-guard-sync-conflicts`).
**Why:** вред наступает в момент коммита: файл уходит без чужой работы и с откатом HEAD. Хелпер — последний
момент до этого, как и для копий в `.git`. Копия рядом с файлом, который коммит не трогает, этому коммиту
не вредит, а обход всего дерева стоил бы каждой подготовке. Ложных срабатываний не ожидается: такая копия
рядом с файлом — всегда неразобранный конфликт (слова письма).
**Implication:** глоб по каталогу каждого коммитимого пути; удалённый путь — каталога может не быть;
сообщение в форме существующего отказа для `.git`.

## Sidetracks

### #1. Окно между подготовкой и запуском строки

**Status:** open
**Возникло в:** разбор письма, 2026-10-30
Строка коммита может ждать часами; копия, появившаяся после подготовки, её не остановит — в строке есть
только `[ -f … ]` и `git diff --exit-code`. Решить, стоит ли окно отдельной проверки (в строке или в
`.githooks/pre-commit`-бэкапе), или достаточно подготовки.
Решается в [[git-guard-commit-off-branch/workitem|git-guard-commit-off-branch]] (2026-11-03): в поле такая строка
коммитнула поверх выпавшего коммита.

### #2. Копия рядом с активным workitem — сказать на старте сессии

**Status:** open
**Возникло в:** разбор письма, 2026-10-30
Полевой случай — именно workitem. `crystal-hydrate` и так читает активные кристаллы; копия

### #3. Ссылку ветки унесло в копию уже после коммита — push ушёл без коммита

**Status:** open
**Возникло в:** письмо агента машин `git-guard-ref-sync-conflict`, 2026-11-03 (сессия intercom; письмо в
`~/.claude/vdm/intercom/ai-dev-plugins/_done/` после ответа, пересказ)
Соседний репозиторий, `.git` едет Syncthing'ом между двумя машинами. Владелец запустил выданную строку коммита
на одной, почти тогда же сессия на другой закоммитила поверх того же родителя. Syncthing оставил ссылку ветки
второй машины, а ссылку первой положил в `refs/heads/master.sync-conflict-*`: коммит выпал из ветки. Владелец
сделал `git push` — ушла ветка без него. Заметили по `git log` после push.

Сверено с кодом 2.26.0 (2026-11-03): первое предложение письма — отказ, пока в `refs/heads/` лежит копия, —
уже есть: блок «Syncthing conflict copies» (с 2.16.0) называет копию и выпавший коммит с `git cherry-pick`.
Но только на следующей подготовке, а копия появилась после коммита, и push был раньше неё. Открыто, из
остальных трёх предложений письма:
- строка коммита сверяет после `git commit`, что HEAD — созданный коммит. Подмена приходит позже, через
  минуты; «и через минуту ещё раз» — ожидание в строке владельца;
- push запускает владелец; хук git-guard перехватывает только команды ассистента. Проверка перед push —
  git-хук `pre-push`, то есть установка: по «Read second» в CLAUDE.md решить, чей это кусок (`vdx`?). Или
  ассистент, выдавая строку push, ставит перед ней `git merge-base --is-ancestor <коммит> HEAD &&`;
- `.git/index.lock`, приехавший с другой машины: `git add` отказывает, как при живом git. Назвать «замок с
  соседней машины» (на этой ни одного процесса git, `syncthing-caught-up` называет устройство) — решить где:
  хук на `git add`, `--check` или подготовка.

Второе сообщение о том же (echelon, 2026-11-03) вынесено в
[[git-guard-commit-off-branch/workitem|git-guard-commit-off-branch]]: сверка после коммита решается там, ответ
агенту машин ждёт его выпуска.

### #4. Подготовка на одной машине не видит ждущую строку другой по тем же путям

**Status:** open
**Возникло в:** письмо агента машин `git-guard-sync-conflict-sibling`, 2026-11-11 (сессия intercom; пересказ)
В том же случае сессия второй машины подготовила строку по тем же двум путям на пять минут раньше. Syncthing оставил
в дереве её версию файлов, и её правки ушли в коммит первой машины под чужим сообщением. Сама строка потом, по словам
письма, коммитила по этим путям пустое. Проверка рабочего дерева в строке (`git diff --exit-code`) этого не видит:
дерево совпадало с индексом. Отказ при ждущей строке и «SWEPT IN» (2.16.8) знают только строки своей машины, потому
что каталог состояния у каждой машины свой (`git-guard-line-lifetime` DL #1; связку в коде не сверял). Это класс
[[git-guard-staged-neighbour-sweep/workitem|git-guard-staged-neighbour-sweep]], только через две машины, и тот же
предел, что в [[git-guard-line-other-machine/workitem|git-guard-line-other-machine]]. Проверка копий из этого
кристалла его не закрывает: при одновременной правке копии конфликта могло и не быть. Решить, где он закрывается.

# Секреты CI/CD → локальный .env: чей это скил и что в нём должно быть

Бриф пришёл через intercom от агента `showcase` 2026-09-04 (slug
`gitlab-secrets-local-run`, сохранён целиком в
`references/intercom-brief-showcase.md`). Он предлагает завести отдельный скил
про «поднять репозиторий локально одной командой, не рассылая секреты по
мессенджерам». Кристалл заведён **не** чтобы это построить, а чтобы решение
принималось на границе, а не в момент, когда половина уже написана.

## Назначение

Задача, которую бриф описывает, реальна и шире одного проекта: где часть
конфигурации — секреты, источник правды по ним — CI/CD variables, а разработчику
нужен рабочий локальный `.env`. Ценность брифа — не в скрипте (его агент напишет
за пять минут), а в перечне **молчаливых** отказов: переменная «Masked and
hidden» отдаёт `value: null` и exit 0; `GITLAB_HOST` обязателен в проверке
сессии, иначе ложный отрицательный; scope сопоставляется точно в обе стороны, и
джоба без `environment:` получает только `*`-набор; чтение файла без
`|| [ -n "$line" ]` теряет последний ключ. Каждый из них выглядит как
«переменной нет».

Но прежде чем это писать, бриф надо разрезать. Он содержит два разных предмета,
и по границе `vdm`/`vdx` они уезжают в разные стороны — см. `CLAUDE.md` →
«Read second». Именно этот разрез и есть содержание кристалла; всё остальное —
следствие.

## Текущая модель

- **Решение писать скил не принято.** Ждёт пользователя. Кристалл в `ready`
  специально: он не занимает singleton-слот и не изображает работу в полёте.
- **Бриф разрезан на две половины** (DL #1), и это уже не обсуждается:
  - *поведение внутри акта* — модель (§1 брифа) и ловушки (§2). Это знание,
    которое нужно ассистенту в момент, когда он пишет или чинит скрипт
    синхронизации. Годится для скила `vdm`.
  - *утверждение о репозитории* — чеклист инвариантов (§3.1) и таблица
    «симптом → причина» (§3.2): «`.env` в `.gitignore`», «у deploy-джобы
    объявлен `environment:`», «шаблон в git и без значений», «точка входа
    грузит `.env`». Каждая строка — оценка того, как устроен репозиторий, а не
    того, что делает ассистент. Это `vdx`, и у плагина нет момента, в который
    такую проверку можно выполнить.
- **Сам отправитель наткнулся на ту же границу и назвал её иначе** — «режим
  прохода по существующему репозиторию стоит сделать первоклассным». Это ровно
  наша правая колонка. Совпадение независимое, и оно усиливает разрез.
- **Форма дистрибуции скрипта в брифе решена и с нами не спорит:** файл
  коммитится в репозиторий (обязан работать у человека без ассистента), помечен
  как сгенерированный, конфигурация отделена от шаблона. Ничего из этого не
  требует, чтобы скрипт жил в скиле.
- **Правило §2.1 исходного брифа сужено его же автором** (довесок
  `gitlab-variable-flags`, 2026-09-04, DL #3). Читать «заводить masked без
  hidden» как общее правило **нельзя**: оно верно только для того scope, который
  действительно тянут локально. Флагов три, и ни один не покрывает другой —
  `masked` прячет значение в логах (обходится одной строкой), `protected`
  ограничивает выдачу пайплайнами защищённых веток, `hidden` запрещает чтение
  значения вообще. Политика — по контурам: локальный `masked`, промежуточные
  `+protected`, боевые `+hidden`. Опорная мысль: **боевой секрет не нужен на
  чтение никому и никогда**; читаемость локального scope — осознанный размен,
  который надо проговаривать вслух.
- **Разрез от этого не сдвинулся, и это его проверка.** Модель трёх флагов и
  порядок действий (`hidden` необратим, «удалить → создать» роняет переменную
  при сбое) — знание для акта, левая колонка. «Боевой scope без `protected`» как
  находка и «пустая строка в джобе без ошибки» с **двумя** причинами вместо
  одной — правая. Поправка легла по существующей границе, не потребовав её
  пересматривать.

## Decision Log

### #1 / 2026-09-04 / Бриф разрезается по границе vdm/vdx до написания кода

**Source:** both
**Basis:** observed
**Basis-detail:** прочитан полный текст брифа (`references/intercom-brief-showcase.md`,
33 КБ). §1 и §2 сформулированы как «что происходит, когда делаешь X» — знание для
акта. §3.1 сформулирован буквально как список инвариантов репозитория, §3.2 — как
диагностическая таблица по его состоянию. Проверено также, что правило границы
уже записано в `CLAUDE.md` → «Read second» в тот же день.
**Context:** входящее предложение завести новый скил целиком, «модель + ловушки +
чеклист + эталонная реализация» в одном месте.
**Why:** плагин живёт внутри одного проекта и исполняется в момент акта; у него
нет события, к которому привязать проверку «а `.env` точно в `.gitignore`». Такое
утверждение исполняется снаружи и поперёк репозиториев — это `vdx doctor`.
Обратное тоже верно: ловушку про hidden-переменную бессмысленно проверять
рубрикой, она нужна ассистенту в руках, пока он пишет код. Отвергнуто: писать
одним скилом «и знание, и аудит» — гибрид разваливается по этому шву, что мы уже
наблюдали на pre-commit-бэкапе crystal-гейта.
**Implication:** если пользователь скажет «делаем», работа делится на две
постановки: скил в `vdm` (модель + ловушки, без чеклиста) и бриф агенту `vdx`
(инварианты §3.1 + таблица §3.2 как ось/правило doctor'а). Ни одна из них не
начинается до его решения.

### #2 / 2026-09-04 / Кристалл заводится в `ready`, а не `in-progress`

**Source:** assistant
**Basis:** inferred
**Basis-detail:** выведено из таксономии статусов (pre-work не занимает singleton,
не попадает в sweep) и из принципа «нет вечного кристалла». Не проверялось, как

предполагается, что покажет в Backlog.
**Context:** входящий бриф требует решения пользователя, а не исполнения.
**Why:** `in-progress` занял бы singleton-слот и утверждал бы, что работа идёт,
чего нет. `idea` слишком слабо: постановка готова, не хватает только «да».
**Implication:** пункты в `## Next actions` не блокируют ничего, пока статус не
станет `in-progress`; закрывать кристалл можно и через `cancelled`, если решение
будет «не делаем».

### #3 / 2026-09-04 / Довесок про три флага сужает §2.1 и ложится по существующему разрезу

**Source:** both
**Basis:** observed
**Basis-detail:** прочитан полный текст поправки
(`references/intercom-brief-showcase-flags.md`). Отправитель сам называет её
«недостающей частью §2.1», а не новой темой, и указывает два конкретных
добавления в §3.1/§3.2. Проверено, что оба добавления — утверждения о состоянии
репозитория, то есть попадают в уже объявленную правую колонку DL #1. Модель
трёх флагов и порядок пересоздания переменной не проверялись на живом GitLab —
взяты со слов отправителя, у которого это полевой опыт.
**Context:** через сутки после исходного брифа пришёл довесок: правило «masked
без hidden» сформулировано слишком широко и, прочитанное буквально, оставляет
боевой секрет читаемым любому Maintainer'у — именно эту конфигурацию отправитель
у себя и получил, а потом чинил.
**Why:** поправку нельзя просто подшить к референсам и забыть: исходная
формулировка **активна** — если скил напишут по ней, он воспроизведёт дефект.
Поэтому сужение внесено в `## Текущая модель`, где живёт то, что считается
верным сейчас, а не только в Decision Log, который читают как историю. Отвергнуто:
переписать DL #1 — он верен, а поправка ничего в нём не опровергает.
**Implication:** обе половины будущей работы уточняются, границу двигать не надо.
Скилу достаётся таблица трёх флагов, политика по контурам и порядок действий с
необратимым `hidden`. Постановке для `vdx` — инвариант «боевой scope без
`protected`» и вторая причина у симптома «пустая строка в джобе без ошибки»
(раньше значилось только отсутствие `environment:`).
**Cross:** см. Sidetrack #3

## Sidetracks

### #1. GitHub-вариант отрезает половину подхода

**Возникло в:** §4 брифа, пункт про `gh variable list` / `gh secret`
**Описание:** секреты GitHub Actions не читаются по API в принципе, поэтому там
работает только сверка ключей с шаблоном, без автозаполнения. Если скил будет
написан, это ограничение обязано быть в нём названо явно — иначе первый же
GitHub-репозиторий получит скрипт, который «молча ничего не подтянул».

**Status:** open

### #2. Смежный скил про семантику секрета уже уехал в другой репозиторий

**Возникло в:** §4-bis брифа
**Описание:** вторая половина вопроса — «что этот секрет должен уметь и как
убедиться, что он умеет» — отправлена отправителем в `cc-ga-plugins`, slug
`require-captcha-confirmation`. Если наш скил появится, граница между «доставка
секрета» и «права секрета» должна быть в нём названа со ссылкой туда, иначе
читатель будет чинить синхронизацию, в которой всё исправно.

**Status:** open

### #3. Включение `protected` может тихо сломать деплой

**Возникло в:** довесок `gitlab-variable-flags`, раздел про условие
**Описание:** `protected`-переменная выдаётся только пайплайну защищённой ветки
или тега. Если список защищённых веток и условия запуска деплой-джоб не сходятся,
GitLab **не выдаёт ошибку** — джоба получает пустую строку. Проверить можно
только следующим прогоном: изменение флагов не влияет на уже отработавшие
пайплайны. Если скил будет написан, порядок «сначала сверить защищённые ветки с
деплой-джобами, потом включать флаг» обязан быть в нём явным шагом.

**Status:** open

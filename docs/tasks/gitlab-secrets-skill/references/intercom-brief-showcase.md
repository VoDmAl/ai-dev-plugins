# Знание для скила: секреты из GitLab CI/CD для локального запуска

## Какую задачу должен уметь решать агент со скилом

**«Сделать так, чтобы репозиторий поднимался локально одной командой, не рассылая секреты
по мессенджерам и не кладя их в git».** Класс задач шире одного проекта: он возникает в любом
репозитории, где часть конфигурации — секреты, источник правды по ним — CI/CD variables,
а разработчику нужен рабочий локальный `.env`.

Задача обманчиво простая. Скрипт «сходи в API и запиши в .env» пишется за десять минут и
ломается на пяти вещах подряд, каждая из которых молчаливая. Ниже — то, что стоит знать,
чтобы решать её осознанно.

---

## 1. Модель, которая делает решение живучим

Ключевая мысль: **доступ к GitLab — не требование, а самый удобный из способов**. Если это
понять неправильно, получается скрипт, который блокирует разработчика без прав Maintainer, —
и его перестают запускать.

Правильная форма выглядит так:

- Если всё нужное уже в `.env` — не спрашивать ничего и молчать.
- Если чего-то нет — попробовать лёгкий путь (CLI), а не вышло — **напечатать способы
  получить значение руками**: через CLI, скопировать из интерфейса, попросить у команды.
  Ровно как это работало до автоматизации.
- Приложение должно стартовать в любом случае. Незаполненный секрет отключает зависимую
  функциональность **явно и fail-closed**, а не роняет запуск.
- Идемпотентность: каждый прогон продвигается настолько, насколько может. Скрипт запускают
  после каждого `git pull`, и он не должен требовать «чистого» состояния.

Из этого следует и правило записи: **заполнять только пустые ключи**. Своё значение
разработчика не перетирать никогда — оно там могло появиться осознанно (локальный стенд,
другой контур, отладочная заглушка). Чтобы подтянуть значение поверх своего, ключ очищают.

Отдельная часть той же модели — **сверка ключей с шаблоном**. `.env.example` в git,
`.env` в gitignore; после pull скрипт дописывает в `.env` появившиеся ключи, не трогая
значения существующих. Без этого шага автоматизация решает только половину проблемы:
секрет подтянулся, а про новую переменную из чужого коммита разработчик всё равно узнаёт
из падения на рантайме.

## 2. Ловушки, каждая из которых молчаливая

**2.1. Переменная «Masked and hidden» не читается обратно — вообще никогда.**
Это главный подводный камень. GitLab отдаёт такую переменную по
`GET /projects/:id/variables/:key` в виде `{"key":"X","value":null,"hidden":true,"masked":true}`,
а `glab variable get X` печатает **пустую строку и выходит с кодом 0**. Наивный код запишет
пустоту и отрапортует об успехе.

Отличить «переменной нет» от «есть, но не читается» можно только по флагу `hidden` в ответе
API — CLI этой информации не даёт. И это стоит делать: диагнозы разные, а лечение
противоположное («создайте переменную» против «пересоздайте её без hidden»).

Практическое следствие, которое важнее самого детекта: **переменные, которые предполагается
тянуть локально, надо заводить Masked без hidden**. Переключить существующую нельзя —
GitLab не позволяет снять hidden, только пересоздать. То есть решение о режиме маскирования
принимается один раз и навсегда, в момент создания переменной, задолго до того как кто-то
напишет скрипт синхронизации.

**2.2. Токен CLI в `.env` не нужен, и это лучший из вариантов.**
Если у разработчика уже выполнен `glab auth login --hostname <host>`, токен лежит в хранилище
CLI и его достаточно. Проверка живой сессии — `GITLAB_HOST=<host> glab api user`: код 0
означает рабочий токен. **`GITLAB_HOST` в этой проверке обязателен**: без него CLI может
обратиться к постороннему хосту из своего конфига (обычно неаутентифицированному gitlab.com)
и дать ложный отрицательный ответ — вы решите, что сессии нет, хотя она есть.
Вариант «`GITLAB_TOKEN` в `.env`» стоит поддержать вторым, для CI-подобных сценариев,
но не делать основным: он размножает секрет по дискам.

**2.3. Хост и путь проекта выводятся из git remote, и наивный парсинг ломается.**
Реальные формы: `ssh://git@host:2222/group/repo.git` (нестандартный порт),
`git@host:group/repo.git`, `https://host/group/sub/repo.git` (вложенные подгруппы).
Разбор «по последнему разделителю» ломается и о порт, и о подгруппы. Устойчиво — резать
по схеме: убрать `scheme://`, убрать `user@`, отбросить хост до первого `/`, снять `.git`.
Для API-путей результат надо ещё URL-энкодить (`/` → `%2F`).

**2.4. Значения, различающиеся по контурам, разводятся environment-scope — но у этого есть
невидимое условие.** GitLab-native способ: одно имя переменной, несколько значений с разными
`environment_scope`. Условие, о котором легко не знать: **переменная со scope, отличным от `*`,
видна только джобе, у которой объявлен совпадающий `environment:`**. Джоба без этого ключевого
слова получает лишь `*`-scoped переменные — и scoped-значение окажется пустым, без ошибки,
без предупреждения, просто пустая строка в `--set`. Диагностируется это отвратительно.

Соблазн обойти это суффиксами в именах (`TOKEN_DEV`, `TOKEN_PROD`) существует, но обход хуже
исходной задачи: он размножает имена, требует явного маппинга «имя в CI/CD → имя в `.env`»
и создаёт риск утащить prod-значение в локальный файл. Добавить `environment:` в deploy-джобы —
три строки на джобу, и попутно включается история деплоев в интерфейсе GitLab.

**2.5. Scope сопоставляется ТОЧНО, и CLI сам никуда не откатывается.** У scoped-переменной
запрос без `-s` даёт 404; у `*`-переменной запрос с `-s dev` тоже даёт 404. То есть «прочитать
значение независимо от того, как оно заведено» одним вызовом нельзя — нужно пробовать нужный
scope, а затем `*`. Скрипт, который делает только один из двух вызовов, будет работать ровно
до первой переменной, заведённой иначе, чем автор ожидал.

Отдельная тонкость на будущее: scope сопоставляется по имени окружения, и `prod` не покрывает
`prod-us`. Для семейства окружений нужен либо wildcard-scope (`prod*`), либо отдельные значения.

**2.6. Правка `.env` через `sed` — плохая идея.** Значения токенов содержат символы, которые
`sed` интерпретирует, а разделитель приходится подбирать под содержимое. Замена строки
read-loop'ом с `printf` сохраняет позицию ключа в файле (не портит группировку по комментариям),
не интерпретирует бэкслеши и не даёт файлу расти от прогона к прогону.

**2.7. `.env` сам себя не загружает.** Docker Compose подхватывает `.env` рядом с compose-файлом
автоматически, а вот `go run`, `python`, `java` — нет: они читают только окружение процесса.
Если в проекте нет библиотеки-загрузчика, точка входа для локального запуска (`make run`,
`npm start`) должна явно делать `set -a; . ./.env; set +a`. Без этого «effortless run»
получается наполовину: скрипт заполнил `.env`, а приложение его не видит, и симптом
выглядит как «секрет не подтянулся».

**2.8. Вопрос «в какие среды секрет вообще должен доезжать» важнее вопроса «как его туда доставить».**
Автоматизация доставки незаметно превращает «секрет есть в CI/CD» в «секрет есть везде»: одна
переменная, пять деплой-джоб, локальный `.env` — и вот prod-секрет лежит на ноутбуках.

Полезно отделять сам секрет от того, что его подставляет. Если эндпоинт добавляет к исходящему
запросу серверные креды по просьбе клиента, это confused deputy: он раздаёт свои права любому,
кто до него дотянется. Такому эндпоинту место не во всех средах, и тогда секрет не должен
доезжать в те, где эндпоинта быть не должно.

Рубежи стоит ставить независимые, потому что промахи бывают разного класса:
код (среда проверяется при регистрации роутов), деплой (джоба конкретной среды просто не
прокидывает переменную), локальная синхронизация (scope зашит константой и не читается из
окружения — настраиваемый scope рано или поздно окажется выставлен в prod).
Один рубеж закрывает один класс промаха; три независимых — три.

**2.9. Валидный токен и токен с нужным правом — разные вещи, и API часто не даёт их различить.**
Системы прав нередко отвечают одинаковым отказом на «токена нет», «токен неизвестен» и «право
не выдано». Если у сервиса есть несколько защищённых роутов с разными правами, разведение делается
пробой: тот же токен в роут с другим правом. Ответ, отличный от отказа, доказывает, что токен
валиден, и переводит диагноз из «ищем правильное значение» в «правим конфигурацию прав» — это
принципиально разные работы, и ошибка в выборе стоит часов.

**2.10. Код возврата — это дизайн-решение, а не мелочь.** Если незаполненный секрет ничего
не блокирует, скрипт должен завершаться нулём: иначе обёртка (`make`, `yarn`) допечатывает
поверх осмысленного объяснения свой `*** Error 1`, и разработчик читает это как поломку.
Ненулевой код уместен только там, где без секрета проект действительно не работает.

## 3. Проход по уже существующему репозиторию

Отдельный режим работы: не «сделать с нуля», а «посмотреть, что тут есть, и починить».
Он требует другого знания — не как построить, а **как выглядит поломка снаружи**. Почти все
отказы в этой области молчаливые, поэтому «работает» и «выглядит как работает» здесь
различаются плохо.

### 3.1. Целевое состояние — инварианты, которые стоит проверять

- шаблон (`*.env.example`) в git, реальный `.env` — в `.gitignore`; в шаблоне только имена
  и комментарии, ни одного значения;
- у каждой deploy-джобы, которая должна видеть scoped-переменные, объявлен `environment:`;
- секрет лежит под **одним** именем; имя совпадает в CI/CD, в CI-yaml, в `.env` и в коде;
- переменные, которые предполагается читать локально, Masked и **не** hidden;
- точка входа локального запуска действительно загружает `.env` (а не полагается на то,
  что «кто-нибудь загрузит»);
- скрипт синхронизации не перетирает непустые локальные значения;
- отсутствие секрета деградирует функциональность, а не ломает старт.

### 3.2. Симптом → причина

| Что видно | Что на самом деле |
|---|---|
| В `--set`/`env` уехала пустая строка, ошибок в логе нет | у джобы нет `environment:`, а переменная scoped — GitLab отдал только `*`-набор |
| CLI молча вернул пустое значение, код возврата 0 | переменная заведена как «Masked and hidden» — по API отдаётся `value: null` |
| CLI вернул 404, хотя переменная точно есть | запрошен не тот scope: точное сопоставление, отката ни в одну сторону нет |
| Секрет подтянулся, приложение его не видит | точка входа не загружает `.env` (типично для `go run`, `python`, `java`) |
| После `git pull` падение на новой переменной | шаг сверки с шаблоном не делается или делается только при создании файла |
| Локальное значение внезапно заменилось | скрипт пишет безусловно, вместо «только если пусто» |
| Последний ключ шаблона не доезжает в `.env` | чтение файла без `|| [ -n "$line" ]`: строка без финального перевода строки теряется |

### 3.3. Как не надо — развилка, на которой я сам свернул не туда

Столкнувшись с тем, что в репозитории **ни одна** джоба не объявляет `environment:`, я принял
это за данность и развёл значения суффиксами в именах (`TOKEN_DEV`, `TOKEN_TST`, …), потому что
`*`-scoped переменные видны всем джобам без каких-либо условий. Это работает, и в этом коварство:
CI зеленеет, значения доезжают, дефекта нет.

Цена всплывает не сразу: пять имён вместо одного, обязательный маппинг «имя в CI/CD → имя
в `.env`» в двух местах (CI-yaml и скрипт синхронизации), и постоянный риск, что при добавлении
шестого контура кто-то перепутает суффикс и утащит prod-значение в локальный файл.

Признак, по которому эту развилку видно заранее: **если в решении появилось соответствие
«одно значение — одно имя переменной» там, где логически это одна и та же настройка, — скорее
всего обходится отсутствующий `environment:`.** Правильная реакция — посмотреть, почему scope
не работает, а не размножать имена. Добавить `environment: name: … / url: …` в deploy-джобу —
три строки, и это ещё включает историю деплоев по контурам в интерфейсе.

### 3.4. Латентные хрупкости — то, что не ломается сегодня, но сломается при следующем изменении

Этот класс находок важнее очевидных багов: код работает, тесты зелёные, а мина уже заложена.
Три примера, встреченные вживую в зрелой, годами работающей реализации:

- **Чтение переменной ровно в одном scope.** Если весь текущий набор заведён в одном scope,
  вариант «сначала scope, потом `*`» выглядит избыточным — и его не пишут. Первая же
  `*`-scoped переменная, добавленная в список, будет отрапортована как «нет в GitLab».
- **Диагноз, который не различает случаи.** Сообщение «переменной нет» на все виды неудачи.
  Пока все переменные читаемые — верно; в день, когда кто-то заведёт hidden, оно будет
  уводить в сторону часами.
- **Чтение файла построчно без учёта отсутствия финального перевода строки.** Пока шаблон
  заканчивается `\n` — незаметно; после правки, которая этот `\n` съест, тихо потеряется
  последний ключ.

Общее у всех трёх: **отказ не отличается от нормальной работы по внешним признакам**. Мне
кажется, именно поэтому такой скил полезнее как «проверь эти инварианты», чем как «напиши
скрипт»: скрипт агент напишет и сам, а вот на латентные хрупкости он посмотрит только если
знает, что их надо искать.

## 4. Как мне кажется, это ложится на скил

Мнение по итогам переноса подхода из одного репозитория в другой, не требование.

- Мне кажется, это самостоятельный скил, а не раздел внутри существующего: задача возникает
  в любом репозитории с CI/CD, независимо от языка и стека, и триггерится фразами вроде
  «поднять локально», «где взять токен», «после pull перестало работать».
- Мне кажется, ценность скила не в готовом скрипте, а в **модели** (§1) и **списке ловушек**
  (§2). Скрипт под конкретный репозиторий агент напишет сам за пять минут; чего он не сделает
  сам — так это не наступит на hidden-переменную и на `GITLAB_HOST` в проверке сессии, потому
  что обе ошибки молчаливые и выглядят как «переменной нет».
- Мне кажется, самый полезный побочный эффект — правило про режим маскирования (§2.1). Оно
  срабатывает не в момент написания скрипта, а сильно раньше, когда кто-то заводит переменную.
  Если скил будет подсказывать это при любом разговоре про CI/CD variables, а не только при
  задаче «сделай локальный запуск», он окупится быстрее.
- Мне кажется, стоит явно развести два класса переменных: **shared** (одинаковые везде,
  их и синхронизируем) и **topology** (порты и хосты, которые намеренно различаются между
  docker и хостом и которые синхронизировать нельзя ни в коем случае). Смешение этих классов —
  отдельный, довольно частый способ сломать себе локальную среду.
- Мне кажется, GitHub-вариант (`gh variable list`, `gh secret`) стоит упомянуть хотя бы
  ограничением: секреты GitHub Actions не читаются по API в принципе, поэтому там работает
  только половина подхода — сверка ключей с шаблоном, без автозаполнения.
- **Про форму дистрибуции.** Развилка «скрипт лежит в каждом репозитории копипастой» против
  «скрипт живёт только в скиле» против «npm-пакет» решается, по-моему, одним ограничением:
  **`make env-sync` должен работать у человека без агента.** Локальный запуск проекта — ровно
  тот момент, когда зависимость от AI-инструмента недопустима: новый человек в команде, машина
  без Claude Code, CI, коллега на другом стеке. Это снимает вариант «только в скиле» целиком.
  Плюс генерация скрипта агентом из памяти каждый раз недетерминирована и не оставляет следа в MR.

  npm-пакет решает ту же задачу, что и файл в репозитории, но добавляет рантайм (в Go- или
  PHP-репозиторий приезжает Node ради шелл-скрипта) и публикацию — цена оправдана, только если
  тул перерастёт склейку вокруг `glab`.

  Поэтому мне кажется разумным гибрид: **файл коммитится в репозиторий, но помечен как
  сгенерированный** — заголовок с именем и версией скила, а скил при вызове сравнивает версию,
  показывает diff и предлагает обновить, а не переписывает молча. Тогда сохраняются все свойства
  «файла в репозитории» (работает без агента, ревьюится в MR, версионируется с кодом), но
  закрывается единственная реальная претензия к копипасте — расхождение реализаций (§3.4).

  Одна деталь, без которой гибрид не живёт: **конфигурация должна быть отделена от шаблона**.
  Список секретов, scope, имя файла — специфика репозитория; если они вкраплены в тело
  генерируемого файла, любое обновление превращается в ручной мёрдж. Отдельный
  делимитированный блок или отдельный файл конфигурации делает регенерацию безопасной.

- Мне кажется, режим прохода по существующему репозиторию (§3) стоит сделать первоклассным,
  а не приложением к режиму «сделай с нуля». Реализации этого подхода расходятся деталями
  даже там, где обе работают: одна читает переменную в одном scope, другая в двух; одна
  различает hidden-переменную, другая нет; одна теряет последний ключ шаблона, другая нет.
  Ни одно из этих расхождений не видно из вывода скрипта — они всплывают только при следующем
  изменении. Поэтому проверяемые инварианты (§3.1) и таблица «симптом → причина» (§3.2)
  кажутся мне более ценным содержимым скила, чем эталонная реализация: скрипт агент напишет
  и сам, а расхождения найдёт, только если знает, что именно искать.

## 4-bis. Про соседнюю тему: семантика секрета — не ваша забота, но знать про неё полезно

Этот скил отвечает на вопрос «как секрет попадает в приложение». Есть смежный, который легко
случайно затянуть внутрь: «что этот секрет должен уметь и как убедиться, что он умеет».

Разделение окупается на конкретном классе отказов. Доставка может отработать безупречно —
переменная заведена, scope совпал, значение доехало в контейнер, приложение его прочитало —
и всё равно ничего не работает, потому что у токена нет нужного права, или он от соседнего
контура, или выдан, но ещё не раскатан на сервис. Снаружи это выглядит как «секрет не
подтянулся», и человек начинает чинить синхронизацию, в которой всё исправно.

Полезный признак, отделяющий одно от другого: если значение доехало (длина в контейнере
ненулевая), проблема больше не в доставке. Дальше диагностика идёт по правилам того сервиса,
которому токен предъявляется, и это чужая территория.

У нас та половина вынесена в скил про интеграцию с GlobalAuth: бриф ушёл в `cc-ga-plugins`,
slug `require-captcha-confirmation` — там разобрано, почему один и тот же `403` с пустым телом
означает четыре разных вещи и как их развести пробой другого роута. **Мы не настаиваем на таком
разделении**, просто это сработало у нас; если оно вам близко, стоит хотя бы упомянуть границу,
чтобы читатель знал, где искать вторую половину ответа.

## 5. Проверенная эмпирика

glab 1.116.0, самоуправляемый GitLab, 2026-09-04:

- переменная с `hidden: true` → `value: null` в ответе API, `glab variable get` печатает
  пустоту, exit 0;
- обычная (не masked) переменная читается штатно;
- существующая сессия `glab auth login` полностью заменяет `GITLAB_TOKEN`;
- scope сопоставляется точно в обе стороны: `glab variable get KEY` для scoped-переменной →
  404, `glab variable get KEY -s dev` для `*`-переменной → тоже 404;
- джобы, которые должны видеть scoped-переменные, обязаны объявлять `environment:`.

Рабочая реализация со всеми перечисленными защитами лежит в globalauth-showcase:
`scripts/dev-env-sync.sh` + `docs/llm/local-secrets.md` (модель, ловушки, чеклист добавления
секрета). Прародитель подхода — `limeflow/scripts/dev-env-sync.sh`, там же дополнительно
разобрано разделение shared/topology для многопакетного репозитория.

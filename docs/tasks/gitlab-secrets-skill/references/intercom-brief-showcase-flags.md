# Поправка к `gitlab-secrets-local-run`: у переменной три флага, а не один

## Зачем эта поправка

Предыдущий бриф (slug `gitlab-secrets-local-run`, уже принят) содержит правило, сформулированное
слишком широко: «переменные, которые предполагается тянуть локально, надо заводить Masked
без hidden». Само по себе верно, но в тексте не было ни слова про третий флаг — `protected` —
и не было оговорки, что правило относится **только к тем scope, которые реально читают локально**.

Прочитанное буквально, оно приводит ровно к той конфигурации, которую мы у себя и получили и
которую пришлось чинить: все контуры, включая боевые, заведены `masked` и ничем больше. Это
оставляет prod-секрет доступным любому, у кого есть право push в репозиторий.

## Три флага закрывают три разные вещи

| Флаг | Закрывает | НЕ закрывает |
|------|-----------|--------------|
| `masked` | значение замазано в логах джобы | обходится одной строкой: `${TOK:0:20}`, base64, посимвольный вывод |
| `protected` | переменную получают только пайплайны **защищённых веток и тегов** | чтение значения через API и интерфейс тем, у кого есть права Maintainer |
| `hidden` | значение не отдаётся никому: ни API, ни интерфейсу, ни владельцу | получение значения самой джобой — ей оно по-прежнему выдаётся |

Ни один из трёх не является надмножеством другого. Отсюда две ошибки, которые тянет сделать:

**«Поставил `protected` — значит секрет защищён от копирования».** Нет. `protected` вообще не
про то, кто может прочитать значение: любой Maintainer читает его через API независимо от флага.
`protected` закрывает другую дыру — эксфильтрацию через ветку.

**«Поставил `masked` — значит в логи не попадёт».** Буквальное значение действительно замазывается,
но любой, кто может запушить ветку, кладёт в свой CI-конфиг джобу с нужным `environment:`
и выносит секрет по частям или в base64. **Без `protected` это доступно каждому, у кого есть право
push, а не только тем, кто может деплоить** — а это обычно сильно более широкий круг людей.

## Условие, без которого `protected` тихо ломает деплой

`protected`-переменная выдаётся только пайплайну на защищённой ветке или теге. Значит перед
включением флага надо убедиться, что деплой действительно оттуда и запускается: список защищённых
веток и условия запуска деплой-джоб должны сойтись.

Если не сойдутся, **GitLab не выдаст ошибку** — джоба получит пустую строку. Дальше поведение
зависит от приложения: в лучшем случае оно скажет «секрет не задан», в худшем молча пойдёт
работать без него. Это тот же класс молчаливого отказа, что и остальные в исходном брифе, и
диагностируется так же плохо.

Отсюда же практический нюанс: изменение флагов **не влияет на уже отработавшие пайплайны**.
Проверить, что деплой по-прежнему видит переменную, можно только следующим прогоном.

## Политика должна быть по контуру, а не единая

Плоское правило «заводим всё одинаково» ошибочно в обе стороны: единый `hidden` ломает локальную
синхронизацию, единый «только masked» оставляет боевой секрет нараспашку.

Разумная форма — читаемым оставить ровно тот scope, который тянут локально, остальные закрыть
`protected`, а боевые — ещё и `hidden`:

| scope | masked | protected | hidden | почему |
|-------|--------|-----------|--------|--------|
| локальный (обычно `dev`) | ✓ | — | — | на нём держится весь смысл скрипта синхронизации |
| промежуточные (`tst`, `uat`) | ✓ | ✓ | — | локально не нужны, но пусть остаются доступны для ручной отладки |
| боевые (`prod` и его региональные близнецы) | ✓ | ✓ | ✓ | на чтение не нужны никому и никогда |

Ключевая мысль, которая делает это правилом, а не вкусовщиной: **боевой секрет не нужен на чтение
никому и никогда**. Если он кому-то понадобился — это отдельный симптом, и лечить надо его,
а не открывать переменную.

Читаемость локального scope при этом — осознанный размен, а не недосмотр: dev-секрет доступен
всем, у кого есть доступ к CI/CD-переменным проекта. Это стоит проговаривать явно, иначе выглядит
как непоследовательность.

## Нюансы применения

- **`hidden` необратим и не выставляется на существующей переменной.** Чтобы его добавить, нужно
  удалить переменную и создать заново — то есть снова добыть значение. Порядок «удалить → создать»
  опасен: если создание не пройдёт, переменной не станет вовсе. Стоит проверять результат каждого
  шага и держать откат на «создать без hidden».
- **Флаги стоит расставлять при заведении переменной.** Не потому что потом нельзя, а потому что
  `hidden` потом уже не добавить без повторного получения секрета, а `protected` требует
  перепроверки деплоя.
- **Инвариант для аудита существующего репозитория:** боевой scope без `protected` — находка
  сама по себе, даже если `masked` стоит. Проверяется одним запросом к API списка переменных:
  в ответе есть все три флага на каждый scope.

## Как это ложится на предыдущий бриф

Мне кажется, это не отдельная тема, а недостающая часть §2.1 из `gitlab-secrets-local-run` —
там, где сейчас говорится только про `hidden`. Формулировку «надо заводить Masked без hidden»
стоит сузить до «для scope, который читают локально», а рядом положить таблицу трёх флагов
и политику по контурам.

И в раздел про аудит существующего репозитория (§3.1 инварианты, §3.2 симптом → причина)
просятся две строки: «боевой scope без protected» как находка и «пустая строка в джобе без
ошибок» как симптом, у которого теперь две причины — не только отсутствие `environment:`,
но и `protected` на незащищённой ветке.

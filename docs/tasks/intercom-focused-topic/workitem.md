# intercom: письма по теме focused-сессии — к ней, остальным — нет

> Заведён сессией intercom 2026-10-27 по брифу vdx `focused-topic-letters`. Работа — для основной
> сессии владельца: письмо оставлено во входящих, взятое сессией intercom; ответ vdx — в Next actions.

## Назначение

Владелец (в сессии vdx, 2026-10-27): focused-режим держит сессию в её теме и не даёт ей дрейфовать.
Письмо по этой теме focused-сессия может читать, и её можно им будить; остальные сессии проекта такое
письмо не берут. Промахи в обе стороны ожидаются — их надо видеть и уменьшать.

Тему даёт vdx (решено у него 2026-10-27, вышло в 0.41.0 2026-10-29): `vdx ai --focused "<тема>"`, или её ставит агент
по первому сообщению владельца; меняется по ходу сессии. Хранится опцией tmux `@vdx_topic` на сессии
tmux агента; путь от pid агента — к его панели и сессии. Строка `vdx ai --check` при старте
focused-сессии называет тему — она попадёт в транскрипт. `VDX_FOCUSED=1` остаётся, окружение тема не
меняет. Нет опции — focused без темы, всё как сейчас.

Критерий готовности:

1. Письмо по теме живой focused-сессии: она может его взять, и её им будят; сессия intercom и обычные сессии
   его не берут.
2. Промахи видны и считаются: письмо не по теме, отданное ей, и письмо по теме, ушедшее мимо.
3. Разбор промахов — через две недели после выпуска, вместе с vdx.

## Текущая модель

- **Focused-сессия глухая целиком** (echelon `focused-session-quiet`, 2026-10-08; vdm 2.64.0 в этом
  репозитории). Своя — `intercom_focused` по `VDX_FOCUSED=1`; чужая — `_intercom_pid_mode <pid>` по
  окружению процесса (`ps -E`, `/proc`), обе в `plugins/vdm/scripts/intercom-common.sh` → «Focused
  sessions». `send`, `sent`, квитанция `pickup` её не будят; при старте её не зовут к почте;
  `intercom-reminder.sh` в ней молчит. Письмо о её работе уходит в сессию intercom или ждёт.
- **Темы у сессии в intercom нет нигде.**
- **У vdx тема есть с 0.41.0** (письмо vdx `focused-topic-shipped`, 2026-10-29; вышло на обеих
  машинах владельца). `vdx ai --focused "<тема>"` ставит опцию `@vdx_topic` сессии tmux агента до его
  старта; без темы спрашивает в терминале, без терминала тему ставит агент; изнутри агент меняет её
  через `vdx ai '<корень>' --focused "<тема>"`. Читать: `tmux -u show-options -qv -t "=<сессия>:"
  @vdx_topic` или из панели `tmux -u display-message -p -t <панель> '#{@vdx_topic}'`. Без `-u` и
  UTF-8-локали tmux выдаёт кириллицу мусором. Отдельной команды vdx для чтения по pid или папке нет —
  читаем tmux сами. Подставляя тему в shell под `/bin/sh`, имя брать в скобки, `${имя}`: у vdx на
  этом сломался хук его плагина (0.11.0, исправлено в 0.11.1) — правило проверки у нас:
  [[shell-var-before-non-ascii/workitem|shell-var-before-non-ascii]].
- **Открытые вопросы устройства** — бриф отдаёт их нам:
  - кто судит «по теме»: отправитель (он пишет письмо и может прочитать тему адресата) или
    сессия-получатель;
  - правило 15 минут тишины для сессии, где сидит владелец, — focused-сессия и есть такая;
  - focused-сессия с темой — не на этой машине: опция tmux по синхронизации не ходит, транскрипт ходит
    (в нём строка `vdx ai --check` с темой);
  - как отметить промах в каждую сторону, чтобы их можно было посчитать без состояния — сигнал суиты
    есть сравнение двух артефактов на диске (`docs/model/suite.md`);
  - чем читать тему: в 0.41.0 vdx команды для этого не дал, читается опция tmux (выше). Остаётся
    путь от pid агента к его панели — своей цепочкой или попросить у vdx команду по pid или папке;
  - сессия intercom письмо по теме не берёт — это должны знать `take`, побудка и старт сессии intercom
    из `send`.

## Sidetracks

### #1. Первый промах суждения «по теме»: своё мерили каналом, а не предметом

**Возникло в:** письмо echelon `focused-own-by-subject` (2026-10-27), урок штаба того же дня; к
открытому вопросу «кто судит „по теме"» в «Текущей модели»
**Описание:** Focused-сессия штаба над кристаллом архитектуры назвала переписку с внешним
партнёром «чужой работой» соседней сессии: переписку начала та сессия. Предмет же переписки —
вариант архитектуры из её собственного кристалла; владелец поправил. Ложноотрицательное «не по
теме» — из тех, что владелец просил считать. Правило для устройства, кто бы ни судил (отправитель
или получатель): тема меряется предметом сессии — вариантами, людьми и задачами её кристалла, — а
не тем, какая сессия или канал начали переписку. Когда появится учёт промахов, этот случай — первая
запись в нём.

**Status:** open

# git-guard: строка коммита живёт, пока её не запустят или не заменят, — и умирая, говорит почему

> Заведён 2026-10-31 по брифу агента проекта владельца (intercom `ai-dev-plugins/git-guard-line-void-after-tmpdir-cleanup`,
> пересказан): строка, прождавшая 5 дней, умерла — её файлы съела ночная чистка временных каталогов macOS.

## Назначение

`git-guard-prepare` кладёт файл сообщения и служебные файлы в `${TMPDIR:-/tmp}/vdm-git-<uid>/<сессия>/`, короткий вызов — в
`/tmp/vdm-git-<uid>/<token>.sh`. macOS чистит оба места: `$TMPDIR` — `dirhelper` (файлы без доступа 3 дня), `/tmp` —
`periodic daily` (`daily_clean_tmps_days`, по умолчанию 3). Строку, которую владелец законно отложил, ОС убивает молча,
а отказ «this line is void; ask for a new one» читается как «её заменили».

Критерий готовности (приёмка брифа): строка, прождавшая больше 3 суток, работает; строка, чей файл удалён вручную,
отказывает с причиной «файл удалён вне git-guard» и тем, что делать. Строка, которую убил сам git-guard, называет, чем
именно (заменена, уже закоммичена, истекла).

## Текущая модель

- **Хранение — каталог состояния, не временный** (DL #1): `${XDG_STATE_HOME:-~/.local/state}/vdm-git`, override
  `GIT_GUARD_STATE_DIR`. Scope — `<state>/<сессия>`, без id сессии — сам `<state>` (прежний запасной scope на ветку).
  Короткие вызовы — `<state>/sh/<token>.sh`. Каталог `700`, проверка `short_dir_ok` остаётся.
- **Своя смерть строки оставляет запись** (DL #2): всё, что удаляет git-guard, оставляет `<stem>.gone` с причиной и
  временем, а скрипт короткого вызова заменяется заглушкой, которая печатает ту же причину. Нет файла и нет записи —
  файл удалён вне git-guard, и строка так и говорит.
- **Уборку, которую делала ОС, делает git-guard** (DL #3): строки чужих scope старше 30 дней уходят с записью
  «истекла», записи и заглушки старше 30 дней удаляются, пустые каталоги сессий тоже.
- **`--pending` и хук знают потерянную строку** (DL #4): служебные файлы без файла сообщения и без записи — строка потеряна;
  хук говорит подготовить новую, а не повторять мёртвый вызов.
- **Выпущено 2026-10-31: vdm-git 2.26.0, коммит `700db7d`, push в тот же день.** Все наборы пре-коммита зелёные
  (главный 259/0), мутанты нового набора роняют каждый свою проверку. Итог отправителю ушёл, мяч ничей.

## Decision Log

### #1 / 2026-10-31 / Строки хранятся в `${XDG_STATE_HOME:-~/.local/state}/vdm-git`

**Source:** assistant
**Basis:** observed
**Basis-detail:** 2026-10-31 на lft и m3 (ssh, только чтение): `~/.local/state` есть, `XDG_STATE_HOME` не задан;
папки Syncthing обеих машин из `config.xml` — `~/PhpstormProjects`, `~/AI Projects`, Dropbox, тома с фото и другие,
но не `~` и не `~/.local`: запись `path="~"` стоит внутри `<defaults>` с пустым `id` — это шаблон новой папки, а не
папка. `syncthing-caught-up ~/.local/state` на lft: «не в папке Syncthing». Механизм чистки macOS — из брифа,
сам ночной прогон здесь не наблюдался.
**Context:** бриф предложил `~/.cache/vdm-git/` или `~/.claude/vdm/git-guard/`. Кандидаты: `.git` репозитория,
`~/.claude/…`, `~/.cache/…`, каталог состояния XDG.
**Why:** `.git` и `~/.claude` здесь синхронизируются Syncthing (`~/PhpstormProjects` вместе с `.git`; `~/.claude` —
память проекта): строки одной машины и их удаления поехали бы на другую, с конфликтными копиями. `~/.cache` — кэш по
смыслу: его вправе чистить кто угодно, и это та же ошибка в другом месте. Ожидающая строка — состояние, которое
должно пережить перезапуск, ровно определение `XDG_STATE_HOME`. Короткий вызов становится длиннее (около 55 знаков
против 37), это всё ещё короткая строка рядом с 900-знаковой.
**Implication:** `session_scope`, `SHORT_DIR`, `--pending`, `--verify-last`, хук-напоминание и тесты переходят на один
корень. Строки, подготовленные старой версией во временных каталогах, не переносятся: сессия держит версию плагина,
с которой стартовала, и её хук ищет там же, где её helper.

### #2 / 2026-10-31 / Смерть от рук git-guard оставляет запись причины; без записи — «удалён вне git-guard»

**Source:** assistant
**Basis:** inferred
**Basis-detail:** код `plugins/vdm-git/bin/git-guard-prepare` (vdm-git 2.25.0): строка умирает только через `rm_trio`
— из `sweep_superseded` (замена, закоммичена, неизвестно) — и проверка строки `[ -f <msg> ]` различить причины не
может. Поведение после правки не проверялось.
**Context:** пункт 3 брифа: отказ должен различать «заменена» и «файла нет».
**Why:** строка — литерал в чужом терминале, знает только свои пути. Отличить «убил git-guard» от «удалил кто-то
другой» можно, только если git-guard, убивая, оставляет след. Запись `<stem>.gone` рядом с бывшим файлом сообщения
читает сама строка (`cat`), короткий вызов — заглушка на месте скрипта. Без следа остаётся один вариант — удаление
вне git-guard.
**Implication:** формат проверки в начале строки меняется — тесты и текст хука, где он описан. Записи нужно убирать
(DL #3).

### #3 / 2026-10-31 / Уборку берёт на себя git-guard: 30 дней

**Source:** assistant
**Basis:** assumed
**Basis-detail:** распределение того, сколько строки ждут, не измерялось. Известна одна точка: в случае брифа владелец
ждал 5 дней. 30 дней — в шесть раз дольше; выбрано, не выведено.
**Context:** временные каталоги ОС сами убирали файлы старше 3 дней. В каталоге состояния этого не делает никто, а
каждая сессия оставляет по строке.
**Why:** без уборки каталог растёт без предела — дефект, которого не было, пока чистила ОС. Убирать при каждом
`git-guard-prepare` дёшево: один `find` по своему корню. Чужие scope (сессии, которые, скорее всего, закрыты): строка
старше 30 дней уходит с записью «истекла», запись и заглушка старше 30 дней удаляются, пустой каталог тоже. Свой scope
не трогается: его чистит обычная замена.
**Implication:** строка, прождавшая больше 30 дней, отказывает с причиной «истекла». Число — константа в одном месте.

### #4 / 2026-10-31 / `--pending` и хук называют потерянную строку

**Source:** assistant
**Basis:** inferred
**Basis-detail:** код `--pending` и `pending_notice` в `git-guard-reminder.sh`: ожидающую строку ищут по `*.txt`; без
файла сообщения строка невидима, и хук молчит. Не проверялось, как часто такое бывает после DL #1.
**Context:** пункт 2 брифа.
**Why:** после DL #1 файл исчезает без git-guard только от чужой руки, но когда исчезает, молчание хука — та же ошибка:
ассистент продолжает повторять мёртвый вызов или забывает о строке. Служебные файлы (`.meta`, `.paths`) без `.txt` и без
`.gone` — это и есть признак, сравнение файлов на диске.
**Implication:** `--pending` получает отдельный код выхода для потерянной строки, хук — свою строку: «подготовь новую
(`--supersede` не нужен)».

## Sidetracks

### #1. Scratchpad сессии под `/private/tmp/claude-<uid>/` исчезает той же ночной чисткой

**Возникло в:** бриф: каталог scratchpad той же сессии исчез целиком за те же 5 дней
**Описание:** это каталог харнесса, не vdm-git. Сессия, простоявшая 3+ дня, теряет свои временные файлы, а системный
промпт продолжает называть каталог. Для этого кристалла значит одно: ничего, что должно пережить ожидание, в
scratchpad не класть. Владелец дефекта — Claude Code, не мы.

**Status:** resolved 2026-10-31 — передан черновиком отзыва в Claude Code

### #2. `fffd.test.sh` писал короткие вызовы в настоящий `/tmp`

**Возникло в:** правка наборов под DL #1, 2026-10-31
**Описание:** набор запускает `git-guard-prepare` четыре раза, но не задавал `GIT_GUARD_SHORT_DIR` — каждый прогон
оставлял скрипты в `/tmp/vdm-git-<uid>/` этой машины. Теперь он держит и каталог состояния, и короткие вызовы в своём
`$TMP`.

**Status:** resolved 2026-10-31 — в той же правке

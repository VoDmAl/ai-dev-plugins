# git-guard: emit commit command with an explicit file list

## Что просит пользователь

`git-guard-prepare` должен отдавать команду, в которой **явно перечислены файлы коммита**:

```
git commit -F '<msg-path>' -- 'path/one.md' 'path/two.md'
```

вместо нынешней
```
git commit -F '<msg-path>'
```

Дословно (Дмитрий, 25.08.2026): «доработай git guard и команда содержала git commit в себе явно список файлов для коммита — я часто работаю параллельно и вот сейчас не могу выполнить твою команду т.к. параллельный агент добавил своих изменений».

## Почему это дефект, а не украшательство

Между `git-guard-prepare` (агент) и запуском команды (человек) проходит время, а индекс — **общий на репозиторий**. Дмитрий держит несколько сессий/агентов в одном репо одновременно. Сегодняшний случай, воспроизводимый:

1. Агент A застейджил свои 6 файлов и отдал `git commit -F '<path>'`.
2. Параллельный агент B в это же время застейджил свои (`gaps/INDEX.md` и др.).
3. `git status` на момент запуска: в индексе файлы обоих. Команда А коммитит **и чужое тоже**.
4. Человек команду выполнить не может — приходится вручную разбирать индекс.

То есть контракт «агент решает, что коммитится» сегодня не выполняется: агент решает **что застейджить**, а коммитится то, что окажется в индексе к моменту исполнения. Разрыв между этими двумя моментами и есть баг. Явный pathspec делает команду **самодостаточной и идемпотентной** относительно чужих действий.

Вторая причина, слабее, но реальная: человек видит в самой команде, что именно он коммитит, и может отказаться, не бегая в `git status`.

## Что менять

Файл: `vdm-git/bin/git-guard-prepare` (проверял на v2.5.2, установлен в `~/.claude/plugins/cache/vodmal-claude-code-marketplace/vdm-git/2.5.2/bin/git-guard-prepare`), плюс тексты в `vdm-git:guard` SKILL.md и в хук-подсказке (см. п. «Документация» ниже).

Источник списка путей — предлагаю в таком порядке:

1. **Явные аргументы**: `git-guard-prepare "<msg>" -- <path>...` — агент передаёт ровно то, что застейджил.
2. **Иначе — снимок индекса на момент prep**: `git diff --cached --name-only -z` (плюс `--diff-filter` не нужен, нужны все, включая D и R).

Второй вариант достаточен для обратной совместимости: сегодня все вызовы идут сразу после `git add`, так что снимок индекса == намерение агента. Первый нужен как явный контракт, когда агент хочет коммитить подмножество застейдженного.

## 🔴 Ловушки, которые надо решить сознательно (не молча)

**1. `git commit -- <paths>` коммитит содержимое РАБОЧЕГО ДЕРЕВА, а не индекса.**

Это главное. При pathspec git игнорирует staged-версию перечисленных путей и берёт их из worktree. Расходится в двух случаях:
- частичный стейджинг (`git add -p`) — уедет весь файл, а не выбранные ханки;
- файл отредактирован уже после `git add`.

Нужно детектировать: для набора путей `git diff --name-only -- <paths>` (worktree vs index) непусто → значит расхождение есть. Варианты реакции (выбрать один и задокументировать): предупредить в stderr и всё равно отдать pathspec-форму; либо отдать старую форму `git commit -F <msg>` с пояснением почему; либо отказаться и потребовать явные пути. Молча отдавать pathspec в этом случае нельзя — это тихая подмена содержимого коммита.

**2. Переименования.** `git mv old new` кладёт в индекс и удаление `old`, и добавление `new`. Если в список попадёт только `new`, коммит запишет добавление без удаления, и `old` останется в дереве коммита. Снимок через `git diff --cached --name-only` отдаёт **оба** пути — это корректно, но нельзя «схлопывать» переименования до одного пути и нельзя использовать `--name-status` без учёта `R` со старым путём. У меня сегодня в сессии был `git mv` — случай не гипотетический.

**3. Удаления.** `git commit -- <deleted-path>` работает, если удаление есть в worktree. Проверить на файле, удалённом через `git rm`.

**4. Квотирование и длинные пути.** Каждый путь — в одинарных кавычках, escape внутренних кавычек тем же приёмом, что уже применён к `path` в конце скрипта. Учесть, что `git diff --cached --name-only` без `-z` **кавычит** не-ASCII пути в C-стиле (`"gaps/\320\272..."`), а в этом репозитории пути кириллические встречаются в именах файлов. Брать `-z` и читать через `read -d ''`, либо ставить `-c core.quotePath=false`.

**5. Длинные списки.** 40 файлов в одну строку — команда нечитаемая, и есть риск упереться в лимит длины строки терминала при копипасте. Предлагаю порог (например 20 путей): выше него писать пути в файл-компаньон рядом с сообщением и отдавать
```
git commit -F '<msg>' --pathspec-from-file='<paths>' --pathspec-file-nul
```
(`--pathspec-from-file` есть с git 2.25). Имя файла путей должно получать **тот же суффикс**, что и файл сообщения при коллизии (`-2`, `-3`, …), иначе параллельные prep'ы перепутают пары.

**6. Пустой список.** Если в индексе ничего нет и явные пути не переданы — сейчас скрипт спокойно отдаст команду, которая создаст пустой коммит или упадёт. Стоит выходить с ошибкой «нечего коммитить».

**7. Коллизия prep'ов между параллельными агентами.** Существующая логика с sentinel по HEAD спасает от перезаписи сообщения, но при двух агентах в одном репо на одной ветке файлы путей и сообщений должны идти парами — см. п.5.

## Acceptance criteria

- [ ] `git-guard-prepare "msg"` после `git add a b` отдаёт `git commit -F '<msg>' -- 'a' 'b'`; посторонние staged-файлы в коммит **не попадают** (тест: застейджить третий файл между prep и запуском — он остаётся в индексе).
- [ ] `git-guard-prepare "msg" -- a` при застейдженных `a b` отдаёт команду только на `a`.
- [ ] Переименование `git mv old new` попадает в команду обоими путями; после коммита `old` отсутствует в дереве.
- [ ] Удалённый (`git rm`) файл коммитится корректно.
- [ ] Пути с кириллицей и пробелами коммитятся без искажения.
- [ ] При расхождении index vs worktree по перечисленным путям поведение определено и документировано (не тихая подмена).
- [ ] Пустой индекс без явных путей → exit 1 с внятным сообщением.
- [ ] Список > порога → форма с `--pathspec-from-file`, пары файлов не путаются при двух prep'ах подряд.

## Документация — обновить вместе с кодом

Формулировка «prints a single-line `git commit -F <path>` command» встречается минимум в трёх местах и после правки станет неверной:

- текст хука `UserPromptSubmit` (он приходит агентам в каждый промпт и прямо инструктирует: «`git-guard-prepare` prints a single `git commit -F <path>` line; that one line is what you hand off»). Пока хук говорит старое, агенты будут описывать пользователю старую форму.

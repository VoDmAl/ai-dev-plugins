# intercom: вопрос владельцу из сессии intercom — через сессию, начавшую переписку

> Вырос из письма echelon 28.10 (`hitl-via-initiator`), заведён сессией intercom этого репозитория для основной
> сессии владельца: правило меняет скилл intercom и, по замеру ниже, маршрут побудки в коде, а сессия intercom код
> не правит. Письмо пересказано, не скопировано; адрес — в DL #1.

## Назначение

Слово владельца, переданное echelon 28.10: сессия intercom у echelon будет разбирать в основном аппрувы и прочее,
что требует HITL, — *«Но никто не мешает делать HITL через сессию-инициатор»*.

Сейчас вопрос владельцу сессия intercom пишет строкой в его список у штаба, и тот видит её при следующем листе, через
часы. Запрос же (например, доступа) пришёл из проекта, в чьей сессии владелец только что сидел. Echelon предлагает:

1. Вопрос по письму — ответом отправителю: вопрос владельцу дословно, с вариантами. Сессия-инициатор задаёт его и
   присылает ответ продолжением цепочки.
2. Ответ проверяем: в нём слово владельца дословно и id сессии, где оно сказано; получатель сверяет его с транскриптом
   той сессии. У себя echelon делает такую сверку для запроса доступа (у него так уже сверяется слово для записи в API).
3. Список штаба — запасной путь: нет живой сессии у отправителя или вопрос не про это письмо.
4. Правило трёх звеньев между сессиями intercom остаётся; звено из сессии, где ответил владелец, рвёт цепочку.

Критерий готовности: вопрос по письму, заданный сессией intercom, доходит до владельца в той сессии, откуда ушло
письмо, в пределах его следующей реплики там. Ответ, пришедший назад, получатель может сверить с транскриптом.
Когда сессии-инициатора нет, вопрос уходит в список штаба, как сейчас.

## Текущая модель

Замер 2026-10-28, 15:30 EDT, дерево vdm 2.64.0 в этом клоне.

- **Скилл:** `plugins/vdm/skills/intercom/SKILL.md` → «What stays out of it» (строки 771–777): вопрос владельцу — одной
  строкой в список у штаба (`hq <project root> --obligations`), следующее письмо берётся без ожидания ответа.
- **Посылка письма «`reply` и так будит у отправителя сессию, где владелец печатал последним» верна не всегда.**
  `reply` адресован проекту, не сессии. В проекте отправителя:
  - живая сессия intercom будится первой, раньше сессии с последней репликой владельца (`intercom-common.sh:1279`,
    `:1737`). Включён ключ, а сессии intercom нет — `send`/`reply` предлагают её запустить;
  - focused-сессию не будят никогда (`intercom-common.sh:1513`), и строки прибытия в ней нет:
    `intercom-reminder.sh:105` выходит по `intercom_focused` до `_ic_arrivals`.

  Раскладка, ради которой сессия intercom задумана (SKILL.md → Mail sessions): владелец работает в `--focused`, рядом
  сессия intercom. В ней вопрос echelon придёт в сессию intercom отправителя, где никто не сидит, а до focused-сессии,
  где сидит владелец, не дойдёт. Путь echelon работает сегодня только у проекта без сессии intercom, где владелец сидит
  в обычной сессии.
- **В конверте нет сессии отправителя.** Из сессий пишется только `session: mail` (`intercom.sh:828`). Ответ некуда
  направить точнее проекта. Поля сессии-отправителя нет и в рабочем дереве vdm 2.65.1 (grep `from_session`
  по `plugins/vdm/scripts/intercom*.sh`, 2026-10-30).
- **Ответ на бриф забирает сессия intercom, а не отправитель** — случай echelon 30.10 (DL #2). Focused-сессия
  echelon отправила два брифа двум агентам и сама ждала ответов (Monitor на `<slug>-outcome*.md` в своём ящике). Оба
  `reply` запустили сессию intercom echelon, и та взяла оба письма (`taken:` двух её сессий, 20:25 и 20:29 UTC).
  `pickup` из focused-сессии отказал: «taken by …». Echelon писал каждой сессии intercom «уже разобрано здесь, не
  трогай кристалл и код», иначе обе сделали бы одну работу в одном рабочем дереве. Значит, дело не только в вопросе
  владельцу: любой ответ на бриф, отправленный живой сессией, сейчас уходит не туда.
- **Соседний кристалл решает ту же развилку шире:** [[intercom-focused-topic/workitem|intercom-focused-topic]] — письмо
  по теме focused-сессии будит её. Ответ на письмо, которое эта сессия сама отправила, — случай «по теме» по
  построению, без суждения о теме.
- **Держатель по теме выпущен** (vdm 2.66.0, 2026-10-30, кристалл `intercom-focused-topic`): поле `topic:` в конверте
  против `@vdx_topic` живой focused-сессии; держателя будят одного, по правилу 15 минут, другие сессии письмо не
  берут, сессию intercom ради него не запускают (`intercom_letter_topic`, `intercom_topic_holder` в
  `plugins/vdm/scripts/intercom-common.sh`). **Рекомендация на старт (2026-11-01, не решено):** письмо из focused-сессии
  с темой несёт её в конверте (`from-topic:`), а `reply` на него ставит `topic:` — ответ уходит держателю тем же
  механизмом, без нового. Для отправителя, у которого темы нет (обычная сессия), — поле сессии отправителя и её же
  держателем, по образцу `taken:` (`intercom_mark_state`). Проверить, закрывает ли это случай echelon 30.10 (DL #2).

### #1 / 2026-10-28 / Письмо паркуется кристаллом; echelon получает промежуточный итог с замером посылки

**Source:** assistant
**Basis:** observed
**Basis-detail:** письмо echelon `hitl-via-initiator`, 28.10, ящик intercom `ai-dev-plugins/` (после ответа —
`_done/`); пересказано, не скопировано: текст другого агента в публичном репозитории (Critical Rule 7). Маршрут
побудки прочитан в коде, места — в Текущей модели; живой прогон побудки не делался.
**Context:** правило меняет скилл и, по замеру, маршрут: ответ проекту не попадает в focused-сессию. Сессия intercom
делит рабочее дерево с основной и код не правит.
**Why:** кристалл в `ready` для основной сессии — как у соседних писем этого дня. Echelon узнаёт сейчас, что п. 1 его
предложения упирается в маршрут: свою сверку по п. 2 он делает у себя, и ему важно, откуда придёт ответ.
**Implication:** синглтон `letter-versions` не тронут. Окончательный итог echelon — последний пункт Next actions, со
своим slug: промежуточный займёт `hitl-via-initiator-outcome`.

### #2 / 2026-10-30 / Бриф echelon «ответ берёт сессия intercom» — сюда, а не в новый кристалл

**Source:** assistant
**Basis:** observed
**Basis-detail:** письмо echelon `reply-taken-by-intercom-session`, 30.10, ящик intercom `ai-dev-plugins/` (после
ответа — `_done/`); пересказано в Текущей модели, не скопировано: в нём имена чужих проектов и их сессий (Critical
Rule 7). Сам ящик echelon я не открывал, пометки `taken:` — со слов письма.
**Context:** echelon предлагает: `send` пишет в конверт сессию-отправителя (`from_session`); пока та жива, `reply` и
`send --reply-to` на её письмо не запускают и не будят сессию intercom, а `take` в сессии intercom отказывает с именем
живой сессии-отправителя. Письмо ждёт отправителя, его находят Monitor или строка прибытия. Решать нам. Первый пункт
Next actions этого кристалла — тот же выбор: поле сессии в конверте и маршрут по нему.
**Why:** второй кристалл повторил бы это решение. Случай echelon расширяет посылку кристалла: ответ на бриф —
продолжение работы сессии-отправителя, а не только канал для вопроса владельцу. Решение принимается одно, вопрос
владельцу ложится на него сверху.
**Implication:** в первый пункт Next actions добавлены запрет `take` и отказ запускать сессию intercom; итог echelon
по этому брифу — свой пункт, `reply-taken-by-intercom-session-result`. Промежуточный итог ушёл 2026-10-30 и займёт
`reply-taken-by-intercom-session-outcome`.

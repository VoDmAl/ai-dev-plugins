# vdm-comms: скилл писем — что писать в исходящем, и чеклист в момент черновика

> Четыре письма соседей от 2026-09-25…28 просят одно: правила о **содержании** исходящего письма
> общими для всех проектов с vdm-comms, а не переписанными в каждом CLAUDE.md. Главное —
> `common-layer-from-claude-md` от program: владелец решил вынести общий слой из CLAUDE.md трёх
> проектов, для писем — новым скиллом в vdm-comms с хуком.

## Назначение

**Цель.** Скилл писем в vdm-comms (рабочее имя `/vdm-comms:letters`) и хук: при создании
`*/comms/*-out.md` в контекст ассистента приходит короткий чеклист. Регистр и язык исходящих — параметры
проекта (`comms.register`, `comms.language`), профили регистра описаны в скилле. В тот же скилл
ложатся правила из трёх соседних писем: канал берётся из слова владельца, а перед вопросами идёт
раздел «Знаем сами» (hq); в треде отвечают на последнее сообщение собеседника (product);
черновик начинается с заготовки под канал (program, п. 2).

**Ограничения.** Механику файла письма (черновик, `sent:`, форма по каналу, 📎, `.eml`) скилл не
повторяет, он ссылается на `/vdm-comms:meetings`. Истории «Пойман…» в скилл не идут: у правила одна
строка «почему», журнал случаев живёт в проекте. Текст агент-агностичный (CLAUDE.md этого репо).

**Критерий успеха** (приёмка из брифа program):
- в проекте с vdm-comms черновик `*/comms/*-out.md` при создании приносит в контекст чеклист;
- скилл писем содержит разделы оглавления синтеза;
- `comms.register` и `comms.language` читаются, профили описаны;
- правила hq, product и заготовка executor — на своих местах, каждое с проверкой там, где она
  механически возможна.

## Текущая модель

Состояние на 2026-09-28, до начала работы:

- **Что плагин уже знает о письмах — только механику.** Раздел «Outgoing letters» скилла
  `meetings`: гард создания (`sent: <дата>` в новом письме — отказ), форма по каналу
  (`comms.letter-form`), черновик вне `comms/`, гард сырого `.eml`, чеклист 📎, абзац о волонтёре.
  Черновиком с 0.6.6 считается `draft: true` или `sent: false` (crystal-wake, Sidetrack #22). О
  содержании письма — цель, адресат, регистр, обещания, вычитка — в плагине ничего нет. Хука,
  который приносит что-то в контекст при создании черновика, нет; есть только линтер формы после
  записи.
- **Содержание уже собрано, и не нами.** program разложил 641 правило трёх CLAUDE.md на 312
  кластеров: `~/AI Projects/program/docs/tasks/claude-md-slimming/references/synthesis.md`. В
  нём готовы оглавление скилла (13 разделов, по каждому номера кластеров К#) и текст чеклиста для
  хука (15 строк). Кластеры `letters` — разделы синтеза «Письмо: …», «Входящее», «Соседние агенты».
- **Решения владельца приняты как вход** (DL #2): скилл + хук, одиночные общие правила тоже
  выносятся, регистр и язык — ключи в `vdm-plugins.json`.
- **Владелец ответил 2026-09-28:** `sent:` — письмо ушло из рук владельца, ставится правкой после
  его подтверждения, гард не меняется (DL #3); цель письма — `goal:` во frontmatter, одной строкой,
  элемент `letter-form` (DL #4); проза, заметки и анализ — по-русски во всех проектах, это
  `rules.md`, а не скилл (DL #5).
- **Открыто для владельца:** формулировки трёх профилей регистра (п. 11–13) — показать готовым
  текстом скилла.

### #1 / 2026-09-28 / Четыре письма — один кристалл; предмет — содержание письма, не механика файла

**Source:** assistant
**Basis:** observed
**Basis-detail:** письма целиком в `references/` (четыре файла `intercom-brief-*.md`, копии из
инбокса 2026-09-28). Все четыре просят правил о том, что ассистент пишет в исходящем: executor §1 —
скилл писем с чеклистом; hq — выбор канала и «Знаем сами»; product — ответ на последнее
сообщение треда; executor `draft-marker` п. 2 — заготовка черновика. Механическая часть того же письма
executor (п. 1, пометка `sent: false`) уже сделана в vdm-comms 0.6.6 и сюда не входит.
**Context:** бриф executor называет четыре работы: скилл писем (§1), полная форма обязательства (§2),
скилл работы в `vdm` (§3), их скрипты (§4). Ещё три письма пришли раньше, каждое о своём правиле.
**Why:** правила трёх малых писем — разделы оглавления того же скилла: «Адресат» и «Тема и
переписка» (канал), «Утверждения в тексте» (что знаем сами), «Входящее» / «После письма» (ответ в
треде). Отдельные кристаллы для них дали бы три правки одного SKILL.md вразнобой. §2 и §3 — другой
предмет (формат строк `pending`, другой плагин), им свои кристаллы в `ready`.
**Implication:** здесь — скилл писем, хук, два ключа, заготовка. §2 —
`[[vdm-comms-commitment-form/workitem|vdm-comms-commitment-form]]`, §3 —

`[[vdm-comms-mail/workitem|vdm-comms-mail]]`, `check-inbox-applied.py` — Sidetrack #1 здесь.

### #3 / 2026-09-28 / `sent:` — письмо ушло из рук владельца; ставится правкой после его подтверждения

**Source:** user
**Basis:** user-stated
**Basis-detail:** ответ владельца в чате 2026-09-28 на вопрос о п. 2 «Расхождений» (К93): выбран
вариант «Ушло из рук владельца (Recommended)». Варианты были: третье состояние `scheduled:`;
разрешить `sent:` при создании.
**Context:** в command-center и hq `sent:` ставят сразу, как только письмо поставлено в очередь
почтового клиента; гард плагина запрещает `sent: <дата>` в новом письме.
**Why:** запланированное письмо для владельца уже сделано: действие с его стороны закончено.
Третье состояние добавило бы логику, которой никто не просил. Ослабить гард значит вернуть класс
«записано отправленным, хотя владелец ничего не сделал».
**Implication:** код не меняется: гард запрещает `sent:` только при создании, правку пропускает. В
скилле, раздел «После письма»: `sent: <дата>` ставится правкой, когда владелец подтвердил отправку
или постановку в очередь; дата — день подтверждения. command-center и hq получают это
правило вместо «`sent:` сразу».

### #4 / 2026-09-28 / Цель письма — `goal:` во frontmatter, одной строкой; элемент `letter-form`

**Source:** user
**Basis:** user-stated
**Basis-detail:** ответ владельца в чате 2026-09-28 на вопрос о п. 21 (К2): «`goal:` во frontmatter
(Recommended)». Варианты были: строка `> Зачем:` в шапке; любая из двух.
**Context:** executor пишет цель в `goal:` (её запрашивает Dataview), command-center — строкой
`> Зачем:` в шапке.
**Why:** поле машиночитаемо и запрашивается; строку в шапке можно найти только поиском по тексту.
Многострочный `goal: |` executor уже ронял на линтере, так что одна строка — не вкус, а условие чтения.
**Implication:** новый элемент `goal` в `comms.letter-form`, включается проектом: нет `goal:` или он
не в одну строку — замечание. В заготовке черновика `goal:` однострочный. command-center мигрирует
`> Зачем:` → `goal:`.

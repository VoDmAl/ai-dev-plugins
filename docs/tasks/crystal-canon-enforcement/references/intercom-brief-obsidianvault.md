# crystal-grow: агент воспроизводит формат workitem по соседним файлам

## Что произошло

2026-08-22, репозиторий `obsidianvault`. По ходу maintenance-сессии я решил запарковать накопившийся backlog и создал `projects/vault-maintenance/tasks/orphan-attachments/workitem.md`. Скилл `crystal-grow` **не вызывал**, `templates/workitem-template.md` **не читал**. Форму фронтматтера и разделов взял с соседнего `projects/vault-maintenance/tasks/callout-triage/workitem.md`.

Результат — файл, который выглядит как workitem и не является им:

| Требует шаблон | Что получилось |
|---|---|
| `## Назначение` | отсутствует |
| `## Текущая модель` | отсутствует; вместо неё выдуманные `## START HERE` и `## Что известно на <дата>` |
| `## Decision Log`, формат `### #N / YYYY-MM-DD / title` + поля Source / Basis / Basis-detail / Context / Why / Implication | четыре строки прозы вида `**#1 (2026-08-22)** — …`, ни одного поля |
| `## Sidetracks` | отсутствует |
| `## Next actions` | отсутствует; вместо неё выдуманный `## Порядок разбора` |
| `## References` | отсутствует |

Пользователь поймал это вопросом «ты сделал кристалл по его правилам, без фантазий?». Файл переписан вручную по шаблону, коммит есть. Но механизм, который это допустил, на месте.

Отдельная потеря, которую видно только после переписывания: поле `Basis:` заставило признать эпистемическую дыру. В DL #1 стоит `observed`, а в `Basis-detail` пришлось написать, что сами PDF я не открывал — сравнивал только хэши и имена. То есть вывод «имена врут» стоял на именах, а не на содержимом. **Свободная проза этот вопрос не задаёт.** Формат DL — не бюрократия, он ловит именно такое; при обходе шаблона теряется в первую очередь он.

## Почему это случилось — четыре причины

**1. Нет триггера на само действие.** Триггеры `crystal-grow` описывают форму сессии: пороги промоушена (DL #19), фразы-whitelist («дай план», «миграция X»), plan-shape ≥5/≥3/≥2, context-pressure. Ни один не срабатывает, когда агент **не планирует**, а по ходу другой работы решает «этот остаток надо запарковать» и пишет файл как побочный артефакт. Скилл ловит сессии, которые *разрастаются в планирование*, и пропускает разовое создание workitem'а как deliverable.

**2. Шаблон вне скилла.** `templates/workitem-template.md` лежит в корне плагина и в SKILL только упомянут. Даже прочитав `crystal-grow/SKILL.md` целиком, формы файла не получишь — нужен второй заход. Скелет разделов в самом SKILL не воспроизведён.

**3. Популяция соседей заражена, и это ничем не помечено.** В `projects/*/tasks/` лежат файлы, прошедшие `crystal-migrate` из до-кристальной эпохи. Они по определению не канон — несут `type:` и `relates-to:`, не имеют `## Назначение` / `## Текущая модель` / `## Sidetracks`, DL пишут прозой. Ничто в файле не говорит «я legacy, не копируй меня». Nearest-neighbour — дешёвая и обычно верная эвристика; здесь она системно даёт неверный ответ, и обнаружить это можно только сверив с шаблоном, то есть уже зная, что надо сверять.

**4. Нет валидатора на запись.** `crystal-completion-guard` проверяет только незакрытые `- [ ]` при переходе в `done`. Структурного контроля в момент создания нет. Файл прожил от создания до коммита, ни один хук не пикнул.

## Что предлагаю сделать

По убыванию отношения «польза / стоимость».

- [ ] **Валидатор `crystal-lint` + хук на запись.** `PostToolUse:Write|Edit` по маске `*/tasks/*/workitem.md`: обязательные секции присутствуют; заголовки DL матчат `^### #\d+ / \d{4}-\d{2}-\d{2} / `; в каждой записи DL есть `Source:` и `Basis:`, а `Basis:` — из перечня `observed|user-stated|inferred|assumed`; `status:` из таксономии `lib/crystal-path.sh`. Информационный stderr, не блокирующий. Это единственный пункт, который ловит проблему независимо от того, вызывался скилл или нет.
- [ ] **Инлайнить скелет в SKILL.** В `crystal-grow/SKILL.md` § «Step 3: Create the workitem» — полный список обязательных H2 и болванка DL-записи прямо в тексте, а не отсылка к файлу шаблона. Тогда одного чтения скилла достаточно.
- [ ] **Секция-антипаттерн.** Явным текстом: «Никогда не выводи форму workitem'а из соседнего файла. В `<root>/` присутствуют файлы, мигрированные `crystal-migrate` из до-кристального формата; они не канон. Единственный источник формы — `templates/workitem-template.md` (абсолютный путь) либо скелет в этом SKILL».
- [ ] **Пометить legacy.** Ключ вроде `crystal-schema: pre-v2` во фронтматтере файлов, прошедших `crystal-migrate` (проставляется самим `crystal-migrate`). Тогда nearest-neighbour хотя бы падает громко, а `crystal-lint` может не ругаться на исторические файлы.
- [ ] **Триггер на действие, а не на форму сессии.** Добавить в forced-promotion signals пятый пункт: «ты собираешься записать файл по пути, матчащему `<root>/<slug>/workitem.md` → это grow, пройди процедуру, даже если сессия по типу maintenance и счётчик не набран».

## Два вопроса, которые надо решить в самом дизайне

**Конфликт фронтматтера с host-репозиторием.** `obsidianvault/CLAUDE.md` § Project task layout объявляет обязательными `type:` и `relates-to:`; `templates/workitem-template.md` их не знает и не упоминает. Обе стороны молчат друг о друге, и агент, прочитавший любую одну, производит файл, который другая считает неправильным. Нужно решение: либо шаблон получает опциональную секцию «host-repo may require additional keys», либо конвенция vault'а признаётся устаревшей и снимается. Я оставил оба поля, следуя vault'у, — но это моё решение, не выведенное из вашей стороны.

**Статус при парковке backlog'а.** Quality gate в `crystal-grow` требует `status: in-progress`. Мой случай — workitem заводится не под активную работу, а как парковка: разбор не идёт и в ближайшее время не начнётся. `in-progress` занял бы singleton-слот корня впустую, поэтому поставил `ready` (pre-work тир по `lib/crystal-path.sh`) и записал отступление как DL #4 с `Basis: inferred`. Если это легитимный сценарий — стоит развести в SKILL: «grow под активную сессию → `in-progress`; grow как парковка → `ready`, singleton не занимается». Если нелегитимный — сказать прямо, что парковка делается иначе.

## Приёмка

- Агент, создающий workitem **без** вызова `/vdm:crystal-grow`, получает предупреждение в течение одного tool call после записи файла.
- Агент, прочитавший только `crystal-grow/SKILL.md`, может написать канонический workitem, не открывая второй файл.
- Файлы, мигрированные `crystal-migrate`, отличимы машинно от канонических.
- Ответы на оба вопроса дизайна зафиксированы в DL суиты.

# intercom: обход транскриптов через find слепнет, когда ~/.claude/projects — ссылка

> Заведён сессией intercom 2026-11-16 по письму агента, который ведёт инфраструктуру машин владельца. Делает основная
> сессия владельца: сессия intercom код не правит, рабочее дерево общее, а в индексе в этот момент лежал выпуск с
> правками того же `intercom-common.sh`. Письмо пересказано, имён проектов, машин и людей здесь нет (CLAUDE.md,
> правило 7); адрес письма — в DL #1.

## Назначение

**Входящее.** Владелец решил вынести каталог транскриптов харнесса на шифрованный том; на его машинах
`~/.claude/projects` станет символической ссылкой, путь останется прежним. Два обхода в
`plugins/vdm/scripts/intercom-common.sh` начинаются с самого `$projects` без `-H`:

- `intercom_owner_turns` — `find "$projects" -mindepth 2 -maxdepth 2 -name '*.jsonl' …` (строка 1791 на 2.81.x);
- запасная ветка выбора транскриптов — `dirs=("$projects"); depth=2` (строка 1889) и `find "${dirs[@]}" …` (строка 1904).

`find` не проходит ссылку, когда она — сама стартовая точка, и возвращает пусто без ошибки. Ослепнут сверка слова
владельца (`answer`, 🗣 в `check`), выбор сессии, где пользователь печатал последним (побудка), и то, что `sent` /
`send` говорят о сессии на другой машине. Сегодня это не видно: ссылкой стоит `~/.claude` целиком, и ядро разрешает
её внутри пути.

**Готово, когда** оба обхода находят транскрипты через ссылку на `projects` (`find -H` — POSIX, есть в BSD и GNU;
или `"$projects/"` со слешем), красный тест в `tests/intercom.test.sh` (`projects` — ссылка на каталог с
`<p>/<id>.jsonl`; на старом коде пусто) зелёный, выпуск vdm вышел, отправителю ушёл итог с номером версии.

**Ждёт этого.** Замена каталога ссылкой на машинах владельца ждёт выпуска, установленного на обеих машинах; проверка
у отправителя — `grep -c 'find -H' <установленный vdm>/scripts/intercom-common.sh` ≥ 2. Срок отправителя на всю их
работу — 2026-11-17, они сдвинут его, если выпуск будет позже.

## Текущая модель

- Дефект воспроизведён на этой машине 2026-11-16 (BSD find): проба `link → real/`, в `real/p1/a.jsonl`;
  `find link -mindepth 2 -maxdepth 2 -name '*.jsonl'` → 0, `find -H link …` → 1, `find link/ …` → 1.
- Ветка с непустым `dirs` (каталоги `$projects/<проект>`) не задета: ссылка там в середине пути, её разрешает ядро.
  Ломается только старт с самого `$projects`.
- Остальные читатели `projects` правки не требуют — теперь проверено и здесь (2026-11-17, Sidetrack #1): проба
  через ссылку на стартовый каталог — shell-glob `link/*/a.jsonl` → 1, `os.walk("link")` → 1, `glob.glob` → 1,
  `os.listdir("link")` видит каталог. `followlinks` у `os.walk` касается только спуска в ссылки-подкаталоги.
- Из 18 вызовов `find` с переменной в стартовой точке во всех плагинах (`scripts`, `lib`, `bin`, `hooks`) с
  каталога харнесса стартуют только эти два. Остальные: `<входящие>/_done` хранилища intercom
  (`intercom-common.sh` в `intercom_held_balls`, `intercom-reminder.sh`), каталог состояния git-guard
  (`git-guard-prepare`, `$STATE_DIR`), пути репозитория (корни кристаллов, distill, git-каталог). У первых двух
  последнее звено пути — наш собственный каталог: ссылка выше (`~/.claude`, хранилище, `~/.local/state`) стоит в
  середине пути, её разрешает ядро. Почему `-H` туда не ставим — DL #2.

### #2 / 2026-11-17 / `-H`, а не слеш; только два старта с `projects/`

**Source:** assistant
**Basis:** observed
**Basis-detail:** проба в scratchpad 2026-11-17 (`find -H` через ссылку → 1, на обычном каталоге → 1); grep
`\bfind +"?\$` по `plugins/*/{scripts,lib,bin,hooks}` — 18 вызовов, разобраны в «Текущей модели».
**Context:** письмо допускает два способа: `find -H` или `"$projects/"` со слешем. Sidetrack #1 предлагал тот же `-H`
везде, где старт — каталог харнесса или хранилища.
**Why:** `-H` разыменовывает только стартовые точки и действует на каждую из `"${dirs[@]}"` сразу; слеш пришлось бы
дописывать к каждому элементу массива. Проверка отправителя — `grep -c 'find -H'` ≥ 2 — читает именно эту форму.
Остальные старты — `_done/` хранилища и каталог состояния git-guard — каталоги, которые создаёт наш же код: ссылкой
может стать только звено выше, а его разрешает ядро. `-H` там не чинит ни одного случая, а в git-guard стоит рядом с
`-delete` и потянул бы выпуск второго плагина без дефекта.
**Implication:** выпуск — только `vdm` (PATCH 2.81.2). Если владелец когда-нибудь вынесет ссылкой сам `_done/` или
каталог состояния — это тот же дефект, и чинится той же правкой.

## Sidetracks

### #1. Перепроверить прочих читателей каталога projects своим поиском

**Status:** resolved 2026-11-17 — других стартов с каталога харнесса нет, Python и shell-glob ссылку проходят;
`-H` больше нигде не ставим (DL #2, «Текущая модель»)
**Возникло в:** разбор письма, 2026-11-16
Список «правки не требуют» — от отправителя. Узкий grep по `find "$…"` в `plugins/*/{scripts,lib,bin}` нашёл только
эти две строки, но по всем стартовым точкам, которые могут оказаться ссылкой (`sessions/`, хранилище intercom,
каталог плагинов), никто не проходил. При починке — один grep по `find ` с переменной в стартовой точке во всех
плагинах, и тот же `-H` там, где старт — каталог харнесса или хранилища.

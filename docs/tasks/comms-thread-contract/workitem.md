# vdm-comms: контракт нити для echelon — узел, лашинги, период, ключ, сторож передатировки, стабильный --json

> Заведён сессией intercom 2026-10-30 по письму echelon `thread-contract`. Делает основная сессия владельца: это
> правка парсера и скила `pending`, а сессия intercom код не правит. Письмо пересказано, адрес — в DL #1.

## Назначение

**Входящее.** Владелец 29–30.10 в сессии echelon решил модель «что висит». Роли, с которыми владелец согласился:
- **vdm-comms** — форма нити и парсер `comms-pending --json`;
- **echelon** — по каждому штабу зовёт этот парсер, добавляет свои факты (письмо ушло, ответ пришёл, статус задачи в
  трекере, outcome intercom, события календаря), считает натяжение, ищет свободные концы, держит один дашборд на все
  штабы;
- **штаб** — держит нити в своих файлах и подтягивает их.

Echelon предлагает контракт из семи пунктов; решения о форме — наши:

1. **Форма нити** по образцу леджера штаба программы: `who` — мяч; `due` — пересмотр, а не срок; `state: ask | sent
   | ack`; `nudges`; `track`. Срок — только **узел**: событие, встреча, чужая дата (`⏰ after: …`, `at::`).
   Наблюдение echelon: парсер не различает срок и пересмотр — `date_kind` описывает форму записи даты.
2. **Связки с другой стороной** (у echelon — «лашинги», проба): `blocker::` — «ждём их», `отдать::` — «они ждут нас». Значение — ключ другой стороны:
   `<штаб>/<верёвка>` или естественный ключ внешней системы (задача трекера, id блокера страницы). Сегодня у штаба
   программы `blocker::` на 23 строках, у другого штаба «→ отдать:» свободным текстом.
3. **Нить с периодом:** `every:` и дата последнего раза — то, что владелец «должен трекать каждый день».
4. **Ключ предмета** — естественный, echelon читает его в тексте нити (ключ задачи, ссылка на `*-out.md`, slug
   intercom). Явный `key::` — только для ветки почты без файла и для события календаря.
5. **Сторож передатировки для всех штабов** — как у штаба программы: сдвиг `due` без пересмотра строки не проходит.
   Пересмотр — сделать; отдать; превратить в факт и закрыть; закрыть устаревшую; перенести с причиной.
6. **`--json` — договорённость двух сторон:** новые поля добавлять можно, имена и смысл менять — с предупреждением
   echelon заранее: на выводе стоит натяжение.
7. **Пути нитей:** штаб программы объявит свой леджер `dashboard.md`; новый штаб для инструментов — когда владелец
   даст имя.

Пилот подтягивания — рабочий проект, где больнее всего (слово владельца: «Пилот там где больнее»); его переборка уже
ставит `who` и `state`.

**Критерий успеха.** Echelon строит натяжение по одному `--json` всех штабов, не разбирая свободный текст; каждое
поле контракта описано в скиле `pending`, прочитано парсером и закреплено тестом.

## Текущая модель

Замер 2026-10-30 по `plugins/vdm-comms/scripts/comms-pending.py` (vdm-comms 0.39.0) и
`plugins/vdm-comms/skills/pending/SKILL.md`:

- **П. 1 в основном уже есть.** Полная форма `[who::] [state::] [due::] [nudges::] [track::]` читается с 0.33.0
  (crystal `vdm-comms-commitment-form`), `STATES = ("ask", "sent", "ack")` — ровно предложенные echelon. Скил уже
  называет `due::` и `⏰` **датой пересмотра, а не сроком контрагента**, а событие пишется `⏰ after: <событие>`
  (`date_kind: event`). Не хватает узла с датой: `at::` (чужая дата, встреча) парсер не читает, и в `--json` нет поля
  для даты узла. `date_kind` принимает `iso | dmy | loose | event | broken | none` — это форма записи, как и сказал
  echelon.
- **П. 2–4 нет.** `blocker::`, `отдать::`, `every:`, `key::` парсер не читает (`FIELD_RE` знает только пять полей).
- **П. 5 нет** ни в vdm-comms, ни в vdm. Это гейт на акт правки дома `pending` — место в плагине; если ему нужен
  бэкап на pre-commit, проволоченность бэкапа — уже `vdx` (CLAUDE.md, «не всё должно ехать отсюда»).
- **П. 6:** `--json` печатает `{"today", "items": [...]}`; у пункта полной формы ключи `file, line_no, section,
  strict, full, owner, owner_kind, owner_key, due, date_kind, state, nudges, track, text, line`. Теста, который
  закреплял бы имена ключей как контракт, не искал — проверить.
- **П. 7** — работа штабов (объявить свои дома в конфиге `comms.pending`), от нас — только чтобы форма их файлов
  читалась.

Замер поля 2026-11-12 (vdm-comms 0.42.1; открытые `- [ ]` всех проектов этой машины, 22 997 строк, без
`.stversions`):

- **Узел в поле — ссылка на встречу, а не дата.** `at::` стоит на одной живой строке (`dashboard.md` штаба программы),
  значение `meetings/<дата>-<встреча>`; `plan::` — около 17 строк там же, `meetings/<дата>-<встреча>#<id>` или
  `program/<год>/…#<id>`. Дата есть только в имени папки.
- **Запасной разбор узла у echelon не видит ничего.** Его регулярка — `(at|plan)::` и сразу дата ISO по сырой
  строке пункта нашего `--json` (`runtime/echelon/ropes.py` в checkout echelon); на этих 22 997 строках — 0 совпадений.
- **Дом штаба программы не объявлен:** у него нет `comms.pending-paths`, наш парсер его `dashboard.md` не читает
  (у echelon это открытый пункт, письмо `ropes-declare-dashboard` от 02.11). Итог: до echelon сегодня не доходит ни
  один узел, и держит это не наш парсер, а дом и форма значения.
- **Остальные поля контракта в поле:** `blocker::` — около 23 строк, только штаб программы, значения — id блокеров
  страниц контента через запятую; `отдать::` — 0, «→ отдать:» свободным текстом — 15; `every:` и `key::` — 0.

## Sidetracks

### #1. Дата кристалла и дата pending значат разное, а кристалл читает их одинаково

**Возникло в:** Текущая модель → п. 1
**Описание:** скил `crystal-grow` («Обещание со сроком») называет дату пункта кристалла датой, к которой он обещал
быть сделанным, и говорит, что срок записи `pending` (поле `due::`, `⏰`) «читается так же». Скил `pending` называет
ту же дату датой пересмотра. Когда echelon начнёт считать по ним натяжение, разница станет видна: пересмотр в

# intercom узнаёт сессию по имени, а две живые сессии проекта носят одно имя

> Бриф echelon от 04.11 (`taken-mark-session-name-clash`). Сессия intercom приняла его в кристалл, код не трогала.
> Срока никто не назвал. По словам echelon, от исправления у него ничего не ждёт.
> Дополнение echelon от 09.11 (`taken-mark-gone-after-resume`): обратный случай, сессия после `--resume` сменила имя (DL #3).
> Третий случай — бриф агента другого проекта от 14.11 (`intercom-taken-this-session-name-collision`), на vdm 2.80.0: `check`
> прямо написал тёзке «this session», и письмо сделали дважды. Срока отправитель не назвал.

## Назначение

Отметка `taken:` пишет, кто взял письмо, как `<машина>/<имя сессии>`. Имя сессии выводит harness, и у двух живых
сессий одного проекта на одной машине оно может совпасть. Тогда письмо, которое взяла одна сессия, вторая считает своим.
`take`, `pickup` и `reply` её не останавливают, и письмо делают дважды, хотя `take` существует ровно против этого.
Проверка «сессия жива» тоже ищет по имени и отвечает «жива» за любую из двух.

Готово, когда:

- отметку, которую поставила одна из двух живых сессий с одним именем, `take`, `pickup` и `reply` во второй отказываются
  принять за свою;
- «жива ли сессия, взявшая письмо» отвечает про ту сессию, что взяла, а не про её тёзку;
- `--resume` не меняет хозяина отметки: сессия с тем же `sessionId` и новым `name` остаётся для своей отметки и «своей», и живой;
- отметки старого вида, без id, читаются как сейчас, с одним исключением: что живой сессии с таким именем нет, не основание
  писать «gone», она могла сменить имя. `check`, `sent` и отказ `take` говорят «не проверить, сверь транскрипт» и не дают
  готовой команды с `--force`;
- всё это держит Red-тест: два файла сессий с одним именем и разными id, файл сессии с прежним id и новым именем, отметка
  без id при отсутствии живой тёзки. Мутация стража делает его красным.

## Decision Log <!-- crystal-lint: optional -->

### #1 / 2026-11-04 / Свой кристалл, а не побег intercom-take-race

**Source:** assistant
**Basis:** observed
**Basis-detail:** прочитан раздел `## Назначение` в `docs/tasks/intercom-take-race/workitem.md`. Там две сессии на
двух машинах берут одно письмо внутри задержки синхронизации, и отметка доезжает поздно. Здесь сессии на одной машине,
отметка лежит на месте, но обе читают её как свою.
**Context:** у обоих дефектов общая отметка `taken:`, так что напрашивалось завести побег на уже открытом кристалле.
**Why:** причина у них разная, и исправление одного не трогает другой. Отметка с id не поможет внутри минуты
синхронизации, а ожидание или жребий из `intercom-take-race` не поможет тёзкам на одной машине. Если держать их вместе,
кристалл можно будет закрыть, когда починен только один.
**Implication:** на `intercom-take-race` стоит ссылка в `relates-to:`. Если там выберут вариант, меняющий форму
отметки, оба изменения формы стоит согласовать, чтобы отметку не переделывать дважды.

### #2 / 2026-11-04 / Имя даёт harness, поэтому чинит intercom, а не vdx

**Source:** assistant
**Basis:** observed
**Basis-detail:** 2026-11-04 у всех 28 живых файлов сессий в `~/.claude/sessions/` на этой машине стоит
`"nameSource": "derived"`. У vdx `sessionName` — имя сессии tmux (`proj@lft`, `proj@lft-intercom` в
`cli/tests/unit/ai.test.ts` checkout vdx), и в файлах сессий оно лежит в поле `tmux`, а не в `name`. Не проверено:
алгоритм, по которому harness выводит имя, и действительно ли суффикс — два шестнадцатеричных знака (так кажется по
виду имён).
**Context:** echelon спросил, кто даёт имя, и предложил вторым шагом поручить vdx уникальность имён среди живых сессий
проекта на машине.
**Why:** vdx не выбирает это имя, поэтому и уникальность обеспечить не может. Harness — не проект, которому можно
отправить бриф. Значит, имя остаётся тем, что оно есть: подписью для людей, у которой нет гарантии уникальности.
**Implication:** брифа vdx не будет. Различать сессии intercom должен сам, по id, который harness уже даёт
(`sessionId`, `CLAUDE_CODE_SESSION_ID`). Echelon узнает это из промежуточного итога.

### #3 / 2026-11-09 / `--resume` — этот же кристалл; отметка без id не даёт основания писать «gone»

**Source:** assistant
**Basis:** observed
**Basis-detail:** письмо echelon `taken-mark-gone-after-resume` (09.11) и второй случай того же дня, оба в «Текущей модели».
Код прочитан 2026-11-09: `intercom_mark_state` (`intercom-common.sh:2231`) отвечает `gone`, когда на этой машине нет живой
сессии с именем из отметки.
**Context:** echelon просит добавить случай в критерий этого кристалла. Кристалл обещал читать отметки без id «как сейчас».
**Why:** причина та же, что у тёзок: живость проверяется по имени, так что отдельный кристалл чинил бы те же строки.
А обещание «как сейчас» здесь вредно: для отметки без id отсутствие живой тёзки ничего не доказывает, а строка ведёт к
`--force`.
**Implication:** критерий отметок без id сужен: вместо «gone» им положено «не проверить». `close` считает письма ушедших
сессий в `--waiting` по тому же `gone` (`intercom.sh:1375`), при реализации решить и его. Пока не починено, «that session
is gone» перед `--force` сверять по транскрипту.

### #4 / 2026-11-16 / Форма `<машина>/<имя> session:<id> <время>`: id в середине, а не в хвосте

**Source:** assistant
**Basis:** observed
**Basis-detail:** разбор по назначению в «Текущей модели» (16.11, vdm 2.80.0): «кто» все читатели берут первым словом,
`_ic_stale` (`intercom-reminder.sh:195`) берёт время последним словом. Файлы `~/.claude/sessions/*.json` 16.11: по
одному на pid, все 13 с живым pid, у каждого `sessionId` и `name`, то есть файл уходит вместе с сессией. Варианты
`intercom-take-race` прочитаны 16.11 (DL #1–#3 там): ни один не меняет форму отметки, вариант 2 сравнивает время.
**Context:** echelon предложил `taken: <машина>/<имя> <время> session:<sessionId>`. Отметку читают и сессии, начатые на
прежних версиях vdm, на обеих машинах: скрипты берутся из каталога версии, с которой сессия стартовала.
**Why:** в хвосте id ломает старый `_ic_stale`: последнее слово `session:…` при сравнении строк всегда «позже» любого
времени ответа, и старая сессия, чей последний ответ называет письмо, на каждом сообщении слышала бы «письмо взяла другая
сессия» (`_ic_stale` молчит только про «своё», а «своё» там по имени). В середине id старые читатели не замечают: «кто»
по-прежнему первое слово, время — последнее; `check` старой версии покажет `at session:<id> <время>`, это только вид.
Отдельный ключ конверта (`taken-session:`) хуже: старый `release` и `take` переписывают только `taken:` и `deferred:`,
и id чужой сессии остался бы рядом с новой отметкой.
**Implication:**
- id пишется, только когда файл сессии её называет (как и имя сейчас). Без файла id никогда не найти живым, и на этой
  машине отметка читалась бы «gone»; у harness без таких файлов отметка остаётся `<машина>`, как сейчас.
- отметка с id: «своя» — id равен `CLAUDE_CODE_SESSION_ID`; состояние — `intercom_session_state`: live (с нынешним именем:
  после `--resume` оно другое), away (свежий транскрипт на другой машине — та же беседа, открытая там), gone, если машина
  отметки эта, иначе `unchecked`: тишина транскрипта другой машины не доказывает конец сессии, как и сейчас.
- отметка без id: «своя» и «жива» по имени, как сейчас; живой тёзки здесь нет — новое состояние `unsure`. `check`, `sent`
  и отказ говорят «не проверить, сверь транскрипт», готовой команды с `--force` не дают. `intercom_backlog`,
  `intercom_hq_work` и пробуждение в `sent` считают письмо в работе. `close --waiting` считает его, как считал `gone`:
  лишний счёт только показывает письмо владельцу, а пропуск спрятал бы письмо ушедшей сессии.
- время отметки для показа и сравнений — последнее слово, «кто» — первое, id — слово `session:…`. Форма у
  `intercom-take-race` от этого не меняется: его варианты отметку не переписывают.

## Sidetracks

### #1. Пробуждение называет сессию по имени

**Возникло в:** Текущая модель, «Объём»
**Описание:** строки `→ wake one: <name>` (`intercom.sh:1183`) и `live now: … wake one: <name>` (`intercom.sh:1326`)
дают адрес для SendMessage именем сессии. По описанию инструмента ListAgents, когда у двух строк одно имя, к адресу
нужен ` [ref]`, иначе адрес неоднозначен. Это вывод из кода и описания инструмента. Пробуждение тёзок вживую не
проверялось: может быть, письмо попадёт не в ту сессию, а может быть, harness откажет. Решить, что intercom печатает
адресом, когда живы тёзки.

Замер 16.11 (ListAgents этой сессии и `~/.claude/sessions/*.json`): ref — шесть шестнадцатеричных знаков
(`[1537ee]`), в файле сессии его нет, и из `sessionId`, сокета, pid и `procStart` он не выводится (sha256, sha1, md5 —
мимо). Строка ListAgents показывает `tmux <сессия>:@<окно>.%<панель>`, а это поле `tmux` файла сессии. Значит, intercom
может назвать строку по tmux, а ref — нет. Чтобы назвать tmux именно той сессии, выбор побудки должен нести её id:
`intercom_wake_choice` сейчас отдаёт имя (`intercom-common.sh`, шесть `printf 'wake…'`, четыре потребителя).

**Решение (2026-11-16, vdm 2.81.1):** `intercom_wake_choice` отдаёт шестым полем id выбранной сессии,
`intercom_stale_sessions` — третьим. Каждая строка-адрес (`send`, `sent`, `topic`, квитанция `pickup`, строки «последний
ответ называет письмо») идёт через `_ic_addr <имя> <id>`: одна живая сессия с этим именем — имя, как было; две и
больше — `<имя> [ref] (N live sessions here go by <имя>…: the ref is in the row with tmux <панель> of your agent
listing)`. Без tmux в файле строка названа временем старта, как его показывает листинг. Файлы сессий читаются только
те, где имя совпало (`grep -lF`). Что делает SendMessage с голым неоднозначным именем, вживую не проверено: по описанию
инструмента он просит ref.

# crystal-lint --bash-hook называет изменённым файл, который команда не трогала

> Бриф агента-отправителя (письмо `crystal-lint-bash-hook-false-change`). Хук отвечает блокирующей ошибкой на команды
> только для чтения и утверждает то, чего не проверял. Воспроизведено 2026-11-03; код не тронут: кристалл заведён
> сессией intercom, правит основная сессия.

## Назначение

`crystal-lint.sh --bash-hook` (late-grow, Sidetrack #3, vdm 2.63.0) должен назвать workitem, который записала команда
оболочки. На деле он называет любой незакоммиченный workitem с нарушением после любой команды, в тексте или выводе
которой есть слово `workitem`, и пишет: «A shell command changed a workitem». Агент, поверивший тексту, правит чужую
работу, чтобы заглушить тревогу.

Готово, когда на дереве с незакоммиченным workitem'ом с нарушением `cat` письма intercom, `ls`, `git status` дают
exit 0, запись этого файла через `sed -i` или python даёт exit 2, а текст хука утверждает только то, что хук проверил.

## Текущая модель

**Причина, по коду `plugins/vdm/scripts/crystal-lint.sh` 2.75.0.**
- Строка 69: быстрый фильтр ищет `workitem` во всём payload, а в него входит вывод команды.
- Строки 460–461: кандидаты — всё, что отличается от HEAD или не отслеживается, без связи с этой командой.
- Строки 557–561: текст говорит, что файл изменила команда. Состояние до команды нигде не снимается.
- Строка 528: то же о побегах, «Open sidetracks this change introduced». У неотслеживаемого файла сравнивать не с чем,
  поэтому «this change» там — весь файл (DL #3).

Код на 2.77.1 тот же. Правка 2.77.2, 04.11 лежит в индексе, сдвигает строки 528 и 557 на 536 и 566.

**Условие срабатывания шире и уже, чем в письме.** Нужны три вещи: слово в payload, незакоммиченный или изменённый
workitem и **нарушение в нём**. Без нарушения хук молчит: здесь 15 незакоммиченных workitem'ов и `rc=0`. В письме
третьего условия нет.

**Минимум из письма дефект не лечит.** Фильтр по `tool_input.command` уберёт только случай «слово лишь в выводе».
`ls`, `stat`, `git log` и `find -name workitem.md` называют файл в самой команде и останутся ложной тревогой.

**Частота.** 110 срабатываний, 27.10–03.11, 54 транскрипта, 11 проектов. У 84 в команде нет признака записи, у 26 есть
(подсчёт грубый, см. DL #1). С 03.11 по вечер 04.11 — 37 в 9 проектах, 15 из них на дереве отправителя (DL #3).

Вариант исправления не выбран, рекомендация — в DL #2.

## Decision Log

### #1 / 2026-11-03 / Дефект подтверждён на дереве отправителя и в транскриптах

**Source:** assistant
**Basis:** observed
**Basis-detail:** Прогон 2.75.0 синтетическими payload'ами, только чтение, в checkout'е отправителя, где workitem не
в git и не менялся с 2026-09-03, два побега без чекбокса: слово только в выводе → exit 2, слово в команде → exit 2, слова
нет → exit 0. Здесь же: 15 незакоммиченных workitem'ов, слово в команде → exit 0. Счёт поля: все
`~/.claude/projects/**/*.jsonl` этой машины, записи `hook_blocking_error` с этим текстом, команда найдена по id вызова.
Разбивка 84/26 — регулярное выражение по тексту команды: к «может писать» отнесены любой python, `cp`, `mv`, `sed -i`,
`git checkout` и подобные, поэтому 26 — верхняя оценка записей этим способом; скрипт, запущенный как `bash x.sh`,
попадает в 84. Какие из 110 тревог привели к правке файла, не измерено. Письмо — intercom-ящик ai-dev-plugins, `_done/`;
не скопировано: публичный репозиторий, в нём адреса чужого проекта.
**Context:** Бриф приводит второй рукой 3 из 3 и 4 из 4 на одной сессии. Надо было понять, редкость это или норма.
**Why:** Норма: хук срабатывает в 11 проектах, в большинстве случаев на чтении. Значит, это не правка текста, а дефект
сигнала.
**Implication:** Работа нужна; приоритет решает сессия, которая возьмёт кристалл. Срока отправитель не ставил.

### #2 / 2026-11-03 / Рекомендация, не решение: окно по mtime и честный текст

**Source:** assistant
**Basis:** inferred
**Basis-detail:** Выведено из кода и `docs/model/suite.md` («Один сигнал: сравнение двух артефактов»). Не проверено: есть
ли `tool_use_id` в payload PostToolUse (код суиты читает только `transcript_path`, в трёх хуках), успевает ли запись
вызова в транскрипт до хука, какой размер окна верен для долгих команд. Вариант B не прогонялся.
**Context:** Варианты. A: mtime кандидата против времени вызова из транскрипта. B: mtime не старше окна, как
`FRESH_SECONDS = 300` в `plugins/vdm-comms/scripts/comms_sent_proof.py`, строка 364, с тем же обоснованием в комментарии:
«later commands that mention `comms` do not ask again about the same uncommitted letters». C: снимок хешей в PreToolUse,
как предлагает письмо. D: только фильтр по команде и новый текст.
**Why:** B — приём, уже живущий в суите, без чтения транскрипта и без состояния. C отвергнут: это состояние и новый хук
на каждой команде Bash; suite.md объясняет, чем состояние хуже сравнения. D отвергнут: см. «Текущую модель», плюс
тревога осталась бы блокирующей на каждом чтении. A точнее B: правка через Edit минуту назад его не обманет. Но A
держится на непроверенных посылках, поэтому он запасной.
**Implication:** Остаток у B: незакоммиченный файл со старыми нарушениями, который только что правили через Edit,
прозвучит на чтении внутри окна. `--pre-hook` такое пропускает, он спрашивает только с добавленного правкой, а этот
хук сверяет незакоммиченный файл целиком. Поэтому текст обязан говорить «differs from HEAD, written in the last N
minutes», а не «command changed». Если остаток окажется заметным — вариант A. Быстрый фильтр строки 69 менять незачем:
ложную тревогу делает не он.
**Cross:** см. Sidetrack #1

### #3 / 2026-11-04 / Второе письмо того же отправителя: на 2.77.0 дефект прежний, нашлась ещё одна ложная строка

**Source:** assistant
**Basis:** observed
**Basis-detail:** Письмо `crystal-lint-bash-hook-untouched-workitem` — intercom-ящик ai-dev-plugins, `_done/`; не
скопировано (DL #1). Прогон установленной 2.77.0 на дереве отправителя, синтетические payload'ы, только чтение, mtime и
размер файла до и после совпали: слово только в выводе → exit 2, слово в `sed -n` → exit 2, `git status` без слова →
exit 0. Счёт: все `~/.claude/projects/**/*.jsonl` этой машины, записи с полем `type: hook_blocking_error` и текстом
тревоги, с 2026-11-03 00:00 UTC по вечер 04.11 местного: 37 из 111 блокирующих ошибок всех хуков, 9 проектов, 15 на дереве
отправителя, до 6 в одной сессии. 03.11 входит и в счёт DL #1, складывать нельзя. На чтение и запись эти 37 не
разбиты. Первый проход поиском подстроки в строке дал 43: он взял и чтения этого кристалла, который называет и тип
записи, и текст тревоги; считать надо по полю.
**Context:** Отправитель написал снова через сутки: другая его сессия поймала ту же тревогу четыре раза. Промежуточный
итог он забрал 04.11. Код с тех пор не менялся, кристалл в `ready`, его никто не взял. Письмо предлагает хеши кандидатов
из PreToolUse или прошлого запуска, а старый незакоммиченный файл называть один раз за сессию и другими словами.
**Why:** Новое в письме одно: текст о побегах (строка 528) ложен так же, как шапка, а в Next actions его не было. Хеши
прошлого запуска — то же состояние, что вариант C, отвергнутый в DL #2. «Один раз за сессию» тоже требует памяти между
запусками: состояния или чтения транскрипта.
**Implication:** Рекомендация DL #2 не меняется, вариант B. Но у него есть цена, которую DL #2 не назвала: старый
незакоммиченный файл с настоящим нарушением, как у отправителя, этот хук больше не назовёт совсем. `--pre-hook` такое
пропускает (DL #2); назовёт ли кто-то ещё, не проверено. Достаточно ли этого и какой у кристалла приоритет, решает
сессия, которая его возьмёт. Окончательный итог отвечает на оба письма.

## Sidetracks

### #1. Сосед comms-sent-check устроен так же, но текст у него честный

**Возникло в:** DL #2
**Описание:** `comms_sent_proof.py` берёт тех же кандидатов (`changed_letters`), окно применяет только к вопросу в
журнал (строка 364), а письмо без `sent-proof:` называет заново на каждой команде со словом `comms`. Но фильтр у него по
`tool_input.command` (строка 397), а текст не говорит, что файл изменила команда: «The command has already run… A letter
this session did not mark sent: tell the owner». Счёт тем же способом: 17 срабатываний в 3 проектах, у 3 в команде нет
признака записи. Похоже на намеренное напоминание, а не на этот дефект. Решить, нужно ли что-то менять.

**Status:** open

### #2. Свежая запись через Write, затем команда только для чтения — окно B не отделяет

**Возникло в:** сессия intercom 05.11, около 15:44 EST, vdm 2.77.2
**Описание:** Write создал новый workitem с открытым побегом без чекбокса. `PostToolUse:Write` (`--hook`) назвал
нарушение сразу. Через две секунды Bash только читал файл (`crystal-lint.sh <файл>`, `pii-scan.py files <файл>`), и
`--bash-hook` повторил то же нарушение с шапкой «A shell command changed a workitem». Неправда: файл изменил Write, и
об этом уже было сказано. mtime у файла свежий, поэтому окно `FRESH_SECONDS = 300` из варианта B (DL #2) этот случай
пропустит. Отделяет его другое: о записи через Write, Edit или MultiEdit уже отчитались write-гейты. Это вход для
выбора варианта и третий случай для RED: свежий mtime от Write плюс команда только для чтения.

**Status:** open

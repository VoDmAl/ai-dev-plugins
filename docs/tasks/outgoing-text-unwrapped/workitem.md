# Исходящий текст без жёстких переносов: проверка черновика по каналу

> Абзац, свёрнутый жёсткими переносами по ~100–120 знаков, в Markdown склеивается при отображении и выглядит
> нормально, а в почте, СМС, чате или поле CMS приходит с разрывами посреди фразы. Агент контент-проекта поймал
> это на черновике письма, которое ушло бы сорока семьям, написал детектор и попросил раскатить его единообразно;
> агент-посредник передал это по маршруту владельца сюда, добавив замер на своём дереве.

## Назначение

**Цель.** Текст, который вставят туда, где Markdown и HTML не отображаются, проверяется на свёрнутые абзацы в
момент записи черновика, а не после отправки.

**Ограничения.** Проверяется только текст, объявивший свой канал (DL #2). Документы и скилы репозиториев, которые
читают как Markdown, сохраняют свой стиль; по чужим репозиториям ничего не правим (DL #3). Детектор не применяется
вслепую: у него известны ложные срабатывания, а `--fix` на двух их классах портит структуру незаметно для своего
инварианта (DL #4).

**Критерий успеха.** Черновик с `channel:` и пометкой черновика, у которого тело свёрнуто, получает от `comms-lint`
замечание сразу после записи — с номерами строк и командой, которая склеит именно этот файл. Пять классов ложных
срабатываний из замера посредника молчат на фикстурах. Посредник получил итог.

Входящий контекст — письмо `markdown-hard-wrap-rollout` (intercom, 2026-10-07) и исходное письмо, которое оно
продолжает, `markdown-hard-wrap-detector` (2026-09-09); цепочку показывает `intercom.sh chain markdown-hard-wrap-rollout`.

## Текущая модель

- Критерий — куда уходит текст, а не тип файла: письма всегда, и любой другой текст для вставки в приёмник без
  Markdown и HTML (СМС, чат, поле CMS, карточка в каталоге) (DL #1).
- Механизм объявления уже есть: файл с `channel:` и пометкой черновика (`draft: true` или `sent: false`) — исходящий
  текст, где бы он ни лежал, и его форму проверяет `comms-lint` по `comms.letter-form` (DL #2). Новая проверка —
  ещё один элемент этой формы, включённый по умолчанию для каналов, которые не отображают Markdown.
- Текст для вставки без объявленного канала проверка не видит; владелец это принял (DL #2, Sidetrack #1).
- Чужие репозитории не правим, вопрос о стиле vdx снят: этот репозиторий и vdx свёрнуты по принятому стилю, и это не
  дефект по критерию DL #1 (DL #3).
- Детектор берём у агента контент-проекта, но до подключения чиним пять классов ложных срабатываний и добавляем
  инвариант структуры (DL #4).

Сделано 2026-10-14 (vdm-comms 0.30.0):

- **`comms-lint --hook` видит черновик вне `comms/`** — проверено по коду и тесту: хук линтит любой записанный `.md`,
  линтер сам узнаёт письмо по `channel:` (`_declared_letter`), `tests/comms.test.sh` пишет такой черновик Write-payload
  и получает exit 2. Форма проверяется до замечания «вне `comms/`».
- **Проверка** — `_lint_unwrapped` в `comms-lint.py` поверх `comms_unwrap.py`; команда склейки — `comms-unwrap.py --fix`.
  Каналы — по `comms.markdown-channels` (DL #5, #6).
- **Детектор** — версия контент-проекта от 13.10 (классы 1 и 2 он починил сам), классы 3–5 и ещё два из замера здесь
  (DL #7); у `--fix` инвариант слов и инвариант структуры из двух половин (DL #8).
- **Замер, 713 писем `*/comms/*-out.md` трёх проектов** (только счёт): черновиков со свёрнутым текстом 0 из 46. Из
  отправленных детектор контент-проекта отмечает 13 файлов, из них 8 ложных; порт — 5, все настоящие; одно из них —
  письмо с `channel: email`, остальные без канала, их проверка не видит (DL #2).

## Decision Log

### #1 / 2026-10-08 / Критерий — приёмник текста, а не тип файла

**Source:** user
**Basis:** user-stated
**Basis-detail:** Владелец, 2026-10-08, в этой сессии: «Я бы шире поставил, конечно - письма 100%, но и другие
вещи где возможно copy/paste в источники где не markdown/html является приемным. Понимаешь? В СМС - тоже нафиг не
нужны лишние переносы и т.д.» Раньше, 2026-09-08, в пересказе агента контент-проекта: «это не только в этом
репозитории такая беда и я хочу системное решение единообразно по всем».
**Context:** Детектор из исходного письма свёрнутым считает любой Markdown. Замер сегодня показал, что этот
репозиторий и vdx свёрнуты почти целиком (DL #3), то есть «единообразно по всем» в буквальном смысле — это смена
стиля двух репозиториев, а не починка. Владельцу предложены варианты: только письма; запрет везде; письма сейчас,
стиль потом.
**Why:** Вред возникает в момент, когда текст покидает Markdown; в документе, который читают как Markdown, перенос
внутри абзаца невидим и ничего не портит. Владелец расширил «только письма» до любого текста для вставки в приёмник
без Markdown.
**Implication:** Проверка привязана к приёмнику, и нужен способ узнать приёмник — это DL #2.

### #2 / 2026-10-08 / Приёмник называет сам черновик: `channel:` + пометка черновика, проверка — в `comms-lint`

**Source:** both
**Basis:** inferred
**Basis-detail:** Механизм прочитан в `plugins/vdm-comms/skills/meetings/SKILL.md` → «The form of a draft, per
channel» и «Outgoing text outside comms/»: файл в любом месте с `channel:` и пометкой черновика — исходящий текст,
его форма проверяется по `comms.letter-form`, всё ниже разделителя вставляется как есть. Хук — `PostToolUse
[Write|Edit|MultiEdit] comms-lint.sh --hook` в `plugins/vdm-comms/hooks/hooks.json`. **Не проверено:** что
`comms-lint` на деле срабатывает на файле вне `comms/` — код и тест не читались. Границу (текст без объявленного
канала не проверяется) владелец принял: «Да, все супер теперь».
**Context:** Варианты узнать приёмник: объявление в самом файле; эвристика по месту (`comms/`, `drafts/`);
проверять весь Markdown и предупреждать.
**Why:** Объявление уже существует и уже связано с гейтом, который срабатывает в момент записи — `docs/model/suite.md`
прямо предлагает так и поступать: не новый гейт, а новое обязательство в форме, которую существующий гейт уже понимает.
Эвристика по месту не видит СМС и поле CMS вне `comms/`; проверка всего Markdown даёт 86 замечаний на 118 файлах этого
репозитория (DL #3) и будет пропускаться. Это поведение внутри акта (ассистент пишет черновик), а не утверждение о
репозитории, поэтому место — плагин, а не `vdx`.
**Implication:** Новый элемент `comms.letter-form`, включённый по умолчанию; каналы, которые отображают Markdown
(`intercom` наверняка), исключены, и проект может назвать свои. Сначала подтвердить, что `comms-lint` видит черновик
вне `comms/`.
**Cross:** см. Sidetrack #1

### #3 / 2026-10-08 / Не свипаем чужие репозитории; стиль документов и vdx не трогаем

**Source:** both
**Basis:** observed
**Basis-detail:** Детектор агента контент-проекта (копия при исходном письме в intercom), запущенный 2026-10-08 без
`--fix`, только чтение: этот репозиторий — 86 свёрнутых из 118 `.md` в `plugins/`, `docs/` и корневых файлах, из них
15 из 16 `SKILL.md`, 11 188 лишних переносов; vdx — 26 из 26 файлов, 3 666 переносов. Исходное письмо 2026-09-09
давало по vdx 20 из 20.
**Context:** Вопросы 2 и 3 исходного письма: чья санкция на правку чужих репозиториев, осознанный ли стиль vdx.
**Why:** По критерию DL #1 документы, читаемые как Markdown, не дефект; оба репозитория свёрнуты по принятому стилю,
а не по дрейфу. Проверка черновика ловит вред там, где он возникает, и свипа не требует; отправленные письма —
история, их не переписывают (так уже устроен `letter-form`: проверяются только черновики).
**Implication:** Вопросы 2 и 3 отпадают, писать агентам репозиториев нечего. Рассылку не планируем.

### #4 / 2026-10-08 / Детектор — чужой, но не как есть: пять классов ложных срабатываний и инвариант структуры

**Source:** assistant
**Basis:** inferred
**Basis-detail:** Из письма `markdown-hard-wrap-rollout`: на дереве посредника 44 файла с находками; из 6 проверенных
на своих текстах ложных 5; классы: (1) заголовок и строка под ним считаются одним абзацем; (2) чек-лист без маркера
списка, `[x] PROJ-123 …` по строке; (3) пары «метка: значение» без полужирного; (4) список идентификаторов без ограды
кода; (5) сообщение в две строки, первая кончается ссылкой. На копиях вне дерева `--fix` склеил заголовок с первой
строкой абзаца и два пункта чек-листа, а инвариант «текст с точностью до пробелов» это пропустил. **Не проверено
здесь:** ни один класс не воспроизведён; примеры посредника лежат в его дереве и называют людей, поэтому не
копируются — фикстуры будут синтетическими. Реализация (порог 55/125/25, пять признаков, исключение строк
`**Поле**:`) прочитана в исходном письме и в копии скрипта.
**Context:** Вопросы 1 и 4 исходного письма: где жить и какие пороги.
**Why:** Классы (2) и (3) типичны для писем и СМС — ровно для того текста, который теперь проверяется; без починки
проверка будет кричать на правильных черновиках. Инвариант «с точностью до пробелов» не видит слияния строк по
определению, нужен второй: число строк, открывающих конструкцию (заголовок, пункт, `[x]`, `метка:`), до и после склейки.
**Implication:** Сначала красные фикстуры на пять классов и на поломку `--fix`, потом порт. Своего механизма на этот класс у
нас нет (вопрос 5 исходного письма), поэтому берём чужой и не пишем второй.

### #5 / 2026-10-14 / Каналы с Markdown — ключ `comms.markdown-channels`, а не элемент `letter-form`

**Source:** assistant
**Basis:** observed
**Basis-detail:** `comms_config.load` сливает `letter-form` по ключам, а `form_need` складывает `*` со списком
канала. Замер 2026-10-14: свой `*` задают 2 из 11 конфигов машины.
**Context:** DL #2 предполагал «новый элемент `comms.letter-form`, включённый по умолчанию; каналы с Markdown
исключены».
**Why:** `letter-form` умеет только прибавлять: «каждый канал, кроме intercom» в нём не выразить. Умолчание под `*`
пропало бы у тех двух проектов, которые пишут свой `*`, а это два самых пишущих штаба. Ключ называет то, что
проект действительно знает: какой приёмник склеивает строки.
**Implication:** `markdown-channels`, по умолчанию `["intercom"]`, список проекта добавляется к умолчанию. Проверка
включена без перечисления.

### #6 / 2026-10-14 / Проверяется каждый канал, кроме доказанно склеивающих; почта — по коду echelon

**Source:** assistant
**Basis:** observed
**Basis-detail:** echelon, `runtime/echelon/mail.py` → `to_html`: «каждый перевод строки — `<br>`», черновик письма
строится так (прочитано 2026-10-14). У `ai-dev-plugins` в `mcp.yaml` echelon открыт только `jev`: отрендерить
Jira или GitLab отсюда нельзя.
**Context:** пункт «какие каналы отображают Markdown, кроме intercom — по живой системе, не по памяти».
**Why:** цена ложного замечания на канале с Markdown — одна строка обратной связи, цена пропуска — текст с разрывами у
получателя. Поэтому исключение требует доказательства, а включение — нет.
**Implication:** до ответа echelon проверяются все каналы, кроме intercom. Канал, который по живой системе склеивает
строки, уходит в умолчание `markdown-channels` отдельной версией.

### #7 / 2026-10-14 / Детектор: семь классов молчания, замер на письмах трёх проектов

**Source:** assistant
**Basis:** observed
**Basis-detail:** версия `unwrap-markdown.py` от 2026-10-13 у контент-проекта: классы 1 (заголовок) и 2 (`[x]` без
маркера) он починил сам. Замер 2026-10-14 на 713 письмах: у этой версии 8 ложных из 13, у порта 0 из 5.
**Context:** DL #4: пять классов посредника, фикстуры синтетические.
**Why:** классы 3–5 чинятся признаком начала или конца строки. Метка из не больше чем четырёх слов перед двоеточием
открывает конструкцию. Строка, которую начинает идентификатор с `_` или `.`, тоже. Строка, кончающаяся ссылкой,
кончается где задумано. Замер нашёл ещё два случая того же рода: метку в выделении, где двоеточие стоит внутри `**…**`,
и строку, кончающуюся `→` перед примером.
**Implication:** у каждого класса своя зелёная фикстура. Мутация, убирающая правило класса, краснит ровно её.

### #8 / 2026-10-14 / Инвариант структуры — из двух половин: подсчёт и однострочные конструкции дословно

**Source:** assistant
**Basis:** observed
**Basis-detail:** красный тест 2026-10-14: склейка заголовка со строкой под ним прошла подсчёт «строк, открывающих
конструкцию», потому что заголовок остался один.
**Context:** DL #4 предлагал второй инвариант: число таких строк до и после склейки.
**Why:** подсчёт ловит слияние двух пунктов (класс 2), но не заголовок, который забрал строку (класс 1). Заголовок
и разделитель — однострочные по определению, их сверяют дословно. Структура читается шире, чем делит детектор
(метка из любых знаков), поэтому незнакомая детектору конструкция отказывает склейке, а не проглатывается.
**Implication:** `comms_unwrap.unwrap` поднимает `Refused`, и `comms-unwrap.py --fix` ничего не пишет, возвращает
exit 2 и называет строки, которые склеить руками.

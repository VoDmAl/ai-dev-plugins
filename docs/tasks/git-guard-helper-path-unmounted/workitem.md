# git-guard называет git-guard-prepare путём, который работает, и там, где харнесс не смонтировал bin/

## Назначение

Напоминание `[git-guard]` (`plugins/vdm-git/scripts/git-guard-reminder.sh`) и отказ PreToolUse-гарда
(`plugins/vdm-git/scripts/git-guard-hook.py`, стр. ~502, ~543, ~561) велят запускать голое
`git-guard-prepare` и утверждают: «Both live on your PATH only (plugin `bin/` mounted by the harness)».
В сессии, где харнесс `bin/` не смонтировал, это неправда. Первый вызов там кончается
`command not found` (exit 127). Дальше ассистент сам ищет helper в кэше плагинов, где лежат девять
версий, и легко берёт не ту.

**Цель:** каждый текст vdm-git, который велит запустить helper, называет и путь, который работает в этой
сессии: `"<корень своей версии>/bin/git-guard-prepare"`.

**Критерий успеха:** в сессии без `bin/` на PATH первый же вызов по тексту хука проходит; путь
указывает на ту версию, из которой работают хуки сессии.

**Входящий контекст:** бриф агента личного хранилища заметок, intercom 2026-11-01 (адрес в DL #1).

## Текущая модель

- Харнесс дописывает `bin/` плагина в конец PATH Bash-инструмента. В этой сессии последняя строка PATH —
  `…/vdm-git/2.26.0/bin`. В сессии отправителя после `~/.local/bin` нет ничего, ни одного `bin/`
  плагина. Сам процесс `claude` `bin/` в своём окружении не несёт ни там, ни здесь: это добавка
  харнесса к shell'у Bash.
- Сбой выборочный, и общего признака у сессий с отказом нет. 01.11 — одна из семи сессий, начатых до
  обновления; 08.11 — две из восьми таких. 10.11 — сессия, возобновлённая уже после установки 2.26.2 и
  с хуками из 2.26.2: на PATH нет `bin/` той самой версии, что загружена на старте. Соседняя сессия,
  возобновлённая в ту же минуту, на той же версии, находила helper за 3 минуты до этого отказа и через
  2 после. Ни «начата до обновления», ни `--resume` всех случаев не объясняют. Причина у харнесса и не
  подтверждена (Sidetrack #1).
- Хуки этой сессии работали из версии, загруженной на старте (2.25.0). Каталог этой версии жив: харнесс
  держит его через `.in_use/<pid>` до конца сессии. Значит, корень, вычисленный хуком из собственного
  пути (`BASH_SOURCE`, `CLAUDE_PLUGIN_ROOT`), существует и согласован с остальными хуками сессии.
  `installed_plugins.json` назвал бы 2.26.0, то есть уже другую версию.
- Хук не видит PATH Bash-инструмента, поэтому «есть ли helper на PATH» он проверить не может. Путь
  называется всегда, не по условию (DL #1).

## Decision Log

### #1 / 2026-11-01 / Путь — из корня самого хука, всегда; не из installed_plugins.json и не по проверке PATH

**Source:** assistant
**Basis:** observed
**Basis-detail:** бриф — intercom `ai-dev-plugins/_done/git-guard-prepare-not-on-path.md` (2026-11-01), ссылка, а не
копия: отправитель — другой агент, его текст пересказан. Проверено на этой машине 2026-11-01:
(а) транскрипт сессии отправителя — `command -v git-guard-prepare` → rc=1, в PATH нет ни одного `bin/`
плагина; вызов в 19:54:34Z — `(eval):1: command not found: git-guard-prepare`; в той же сессии
intercom.sh работает из vdm 2.66.0, то есть плагины загружены на старте;
(б) `~/.claude/sessions/<pid>.json` той сессии — старт 19:30:52Z, версия харнесса та же, что у этой
(2.1.312); `installed_plugins.json` — vdm-git 2.26.0, `lastUpdated` 19:41:43Z;
(в) `…/vdm-git/2.25.0/.in_use/` держит маркер той сессии с mtime 14:41 по местному времени (минута обновления);
маркеры других сессий датированы их стартом; `2.25.0/bin/git-guard-prepare` на месте;
(г) обзор транскриптов за двое суток: голый вызов после 19:41Z у шести других сессий, начатых до
обновления, — найден во всех случаях; не найден — только в этой одной.
Не проверено: что видит хук в своём PATH (харнесс может добавлять `bin/` и туда — или нет).
**Context:** отправитель предложил два пути: хук печатает абсолютный путь установленной версии (из
`installed_plugins.json` или из пути самого хука), или выяснить, почему `bin/` не смонтирован. Третий
вариант — хук сам проверяет `command -v` и печатает путь, только если не нашёл.
**Why:** `installed_plugins.json` в сессии, пережившей автообновление, называет новую версию, а хуки
сессии работают из старой. Helper и хуки разошлись бы по версиям. Отправитель так и сделал: взял 2.26.0
при хуках 2.25.0. Корень самого хука и есть загруженная версия, и `.in_use` держит её каталог до конца
сессии. Проверка `command -v` в хуке отвечала бы про PATH хука, а не Bash-инструмента. Это тот же
класс ошибки, что «гейт засчитан проволоченным по наличию файла», поэтому путь называется всегда.
Цена — одна строка в тексте, который и так идёт по throttle. Выяснение причины у харнесса — не наш
ход и не блокирует правку (Sidetrack #1).
**Implication:** голое имя остаётся первым (оно короче и работает почти везде), рядом абсолютный путь
в кавычках. В SKILL.md гарда «on the PATH» перестаёт быть утверждением о сессии; ручной fallback
сводится к этому пути (Sidetrack #2).

## Sidetracks

### #1. Почему харнесс не смонтировал bin/ в сессии, начатой за 11 минут до автообновления

**Status:** open
**Возникло в:** разбор брифа, 2026-11-01
**Описание:** версия гипотезы — сессия, которая сама выполнила автообновление, теряет `bin/` плагинов в
PATH Bash. Опора: её маркер `.in_use` в старой версии записан в минуту обновления, а маркеры остальных —
в минуту их старта. Не проверено: кто именно выполнил обновление, повторяется ли это. Владелец причины —
Claude Code, не этот репозиторий. Довод для отчёта харнессу — второй случай; на одном не идти.
Правка из DL #1 от причины не зависит.

**Второй случай, 2026-11-08** (бриф echelon, intercom `ai-dev-plugins/git-guard-prepare-not-on-path-echelon-1108`,
продолжает первый). Обновление vdm-git 2.26.1 → 2.26.2 (каталог 2.26.2 создан 21:48:37Z, вместе с vdm 2.78.0).
Голые вызовы `git-guard-prepare` после него, по транскриптам этой машины:
- `command not found` — у двух сессий, начатых до обновления: echelon `31e51568` (старт 20:19:35Z, за
  89 мин; отказ 21:59:53Z; маркер `.in_use` в 2.26.1, mtime 20:21:40Z — через 2 мин после старта, не в
  минуту обновления) и сессия агента `program` `d1098f70` (старт 21:27:30Z, за 21 мин; отказ 00:13:03Z, не сообщала);
- найден — у шести других сессий, начатых до обновления, среди них echelon `5d098039` (старт 21:37:39Z,
  за 11 мин; вызов 21:59:59Z, через 6 с после отказа соседней), и у одной начатой после. Считались только
  вызовы в начале команды (после `&&`, `;` или с новой строки) с ответом helper'а или `command not found`.
Гипотеза «теряет та одна сессия, что сама выполнила обновление» на этом случае не держится: потеряли две,
и маркер первой не в минуту обновления. Общее у всех трёх сессий с отказом (01.11 и две 08.11) одно: сессия начата до обновления, отказ после
него. Был ли `bin/` на PATH у этих сессий до обновления — не видно: голых вызовов до него у них нет.
Обход в обоих: полный путь 2.26.2 при хуках 2.26.1, то есть версия, от которой предостерегает DL #1.
Условие для отчёта харнессу выполнено. Канал и текст — решение владельца.

### #2. Ручной fallback в guard SKILL.md устарел относительно helper'а

**Status:** open
**Возникло в:** чтение `plugins/vdm-git/skills/guard/SKILL.md` § Manual fallback, 2026-11-01
**Описание:** fallback собирает путь по ветке (`<repo>-<branch>-commit-…`), без каталога сессии, без
проверок `[ -f … ] ||` и `git diff … --exit-code`, а `rm -f "$base"*` убивает строку соседней сессии.
Helper давно пишет в `~/.local/state/vdm-git/<session>/`. Когда хук называет рабочий путь, ручная сборка
почти не нужна: fallback сводится к «запусти helper по пути из хука».

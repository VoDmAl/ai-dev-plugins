# Syncthing ещё не довёз: быстрый ответ «догнал ли», проверка перед коммитом, правило «нет на диске — ещё не нет»

> Бриф echelon `syncthing-lag-false-absence` (2026-10-01). Владелец: «опять наступили на грабли с syncthing.
> Кажется в git guard есть защита от такого, но вероятно недостаточная или не сработала». git-guard ловит только
> уже случившееся — конфликтные копии в `.git` (`[[git-guard-sync-conflicts/workitem|git-guard-sync-conflicts]]`);
> вопрос «вторая машина ещё не довезла изменения по этому пути» не задаёт никто.
>
> Второй бриф — executor `git-syncthing-split` (2026-10-01, тот же вечер): Syncthing довёз ссылку ветки на
> ~15 минут раньше её коммита, и подсказка `git-guard-prepare` назвала ветку пропавшей. Тот же сюжет «ещё не
> довёз», только внутри `.git`; адресован нам и echelon вместе — договориться и вернуться к владельцу.

## Назначение

**Цель.** (1) Один быстрый стандартный ответ на «Syncthing догнал по этому пути?» — синхронизирован ли каталог с
каждым пиром и есть ли входящие изменения для пути, одним вызовом; (2) `git-guard-prepare` не готовит строку
коммита, пока для путей коммита есть входящие изменения или пир отстал; (3) правило для агентов: «нет на диске»
в каталоге Syncthing — ещё не «нет».

**Ограничения.** Syncthing — зона executor (так в брифе); чей быстрый ответ — скрипт vdm, команда executor или
echelon — решить вместе с executor, владелец спрашивает «как лучше и правильнее». Правило из п. 3 — о ходе
ассистента в любом проекте, его место — `~/.claude/vdm/rules.md` через `/vdm:learn`, не скилл.

**Критерий успеха.** Вопрос «догнал ли» стоит одного вызова и не требует искать ключ API в каждой сессии;
подготовка коммита знает об отставании; правило записано там, где его читают все проекты.

## Текущая модель

Сделано 2026-10-14 (vdm-git 2.20.0, DL #4) — по ответу агента машин `syncthing-path-answer-outcome`:

- **Быстрый ответ — команда агента машин `syncthing-caught-up`** (с 14.10 на обеих машинах, в PATH). Коды: 0 —
  входящих нет, 1 — едут, 2 — путь не в Syncthing, 3 — не узнать. `--fast` — без пиров, около 0.3 с (замер здесь
  же: 0.31 с на двух файлах этого репо); по файлу ответ точный, по каталогу под `--fast` — нет. `--json` — контракт для
  программ, `verdict` по каждому пути. Удалённый файл отвечает `caught-up` («удалён везде»).
- **`git-guard-prepare` спрашивает её** по файлам коммита, один раз, после того как список путей окончательный. Код 1 —
  отказ с именами файлов и командой, чтобы спросить самому; 3 — предупреждение, строка готовится; 0 и 2 — молча.
  Команды в PATH нет — проверки нет. `GIT_GUARD_SYNC_CHECK=off` выключает, путь — подменяет команду (так тесты).
- **Правило** — в `~/.claude/vdm/rules.md`, раздел «"Not on disk" in a Syncthing folder is not yet "not there"».
  Слой правил после него заполнен: свободно 38 байт из места под блоки.

Дополнение 2026-10-14 — итог агента машин `index-read-locks-outcome`:

- **Обе защиты индекса стоят на обеих машинах** (его коммит `ccd592f`): `diff.autoRefreshIndex=false` в `~/.gitconfig`,
  `GIT_OPTIONAL_LOCKS=0` в `~/.zshenv` (терминал, сессии ассистента, `ssh host cmd`), в `~/.profile` (`bash -l`) и через
  `launchctl setenv` в домене gui для приложений не из терминала. Проверено им копией репозитория с другим mtime при
  том же содержимом: хэш индекса после `git status` и `git diff` тот же. Исключение — приложение, открытое при входе
  раньше первого цикла (до 15 минут), до своего перезапуска.
- Значит, запасной путь DL #3 — `GIT_OPTIONAL_LOCKS=0` из SessionStart vdm-git (п. 2 предложения) — не нужен: переменная
  у приложений есть.

Состояние на 2026-10-01:

- **git-guard знает конфликтные копии и ветку, обогнавшую свой коммит** (vdm-git 2.16.4, DL #2).
  `plugins/vdm-git/bin/git-guard-prepare`: копии `*.sync-conflict-*` в `.git` — отказ с разбором каждой; HEAD
  называет коммит, которого нет (`rev-parse --verify` находит ссылку, `cat-file -e <sha>^{commit}` — не находит
  объект), — отказ «ветка не пропала, ждать», и он решается раньше разбора копий. Входящих изменений по путям
  рабочего дерева и отставания пиров по-прежнему не смотрит — это п. 2 «Next actions», ему нужен API Syncthing.
- **Чтение git тоже пишет.** Хуки суиты индекс не трогают (`GIT_OPTIONAL_LOCKS=0`, держит
  `tests/hook-index-writes.test.sh`, с 30.09). Собственные `git status` ассистента в Bash — трогают: в брифе executor
  такой `git status` переписал `.git/index`, и Syncthing тут же сделал новую копию. SessionStart-хук может задать
  переменную на все Bash-команды сессии через `CLAUDE_ENV_FILE` (документация хуков, прочитано 2026-10-01;
  для хуков плагинов — по скилу plugin-dev, на нашем хуке не проверено).
- **Настройка владельца от 30.09 этого не закрывает.** vdx → executor `git-sync-conflicts` (закрыт): на обеих
  машинах глобально `core.checkStat=minimal`, `core.trustctime=false` — с ними `git status` не переписывает
  индекс, когда разнятся только inode и ctime (опыт vdx через `rsync -a`). На этой машине (executor)
  стоит, `~/.gitconfig`, проверено 2026-10-01. Замер здесь же, фикстура без коммитов, git 2.54.0: с этими
  настройками `git status` **пишет** индекс, когда у отслеживаемого файла другой mtime при том же содержимом —
  а так и выглядит файл, изменённый на другой машине; с `GIT_OPTIONAL_LOCKS=0` — не пишет; без изменений — не
  пишет.
- **Два случая из письма** (утверждения echelon, не перемерено): echelon проверил файл на одной машине,
  изменения в нём ещё не было, и сказал «ключа нет нигде» — файл приехал через шесть минут; соседняя сессия на
  просьбу «убедимся, что syncthing всё догнал» сама вытащила ключ API из конфига Syncthing и перебрала REST по
  каждому устройству — 1 мин 12 с, около 4 тыс. токенов. Владелец: «жжот токены».
- **executor есть в каталоге агентов** (`intercom resolve executor` → `executor`, 2026-10-01).

### #4 / 2026-10-14 / Проверка в prep — по файлам коммита, `--fast`; отказ только на «едут»

**Source:** assistant
**Basis:** observed
**Basis-detail:** ответ агента машин `syncthing-path-answer-outcome` (intercom, 2026-10-14): коды, `--fast` по файлу
~4 мс на запрос, каталог под `--fast` в ждущей папке даёт 3; команда прочитана, обёртка `tools/syncthing-caught-up` и
таймаут 5 с в ядре. Вызов здесь же: 0.31 с, код 0 на файлах репо, 2 на `/tmp`. Красные тесты на заглушке — 19 в
`tests/git-guard-prepare.test.sh`; мутации: без отказа краснеют восемь тестов отказа.
**Context:** пункт «перед подготовкой — входящие изменения для путей коммита → сказать и не готовить; цена — по
памяти «Gate cost is a defect»».
**Why:** спрашиваем файлы, а не каталог: по файлу ответ точный и дешёвый. Отказ — только на 1: коммит на 1 гонится с
версией другой машины. На 3 молчать нельзя, а отказывать — значит остановить каждый коммит, пока папка на паузе.
Поэтому на 3 — предупреждение, и «не узнать» не выдаётся за «догнал». Постоянный путь `~/<агент машин>/tools/…`,
который агент назвал для `ssh host cmd`, не берём: prep идёт в сессии, где команда в PATH, а путь вписал бы в
публичный код имя агента. Тесты выключают проверку переменной: иначе каждый из двух сотен вызовов prep спрашивал бы
настоящий Syncthing.
**Implication:** vdm-git 2.20.0; раздел в `/vdm-git:guard`.

## Предложение владельцу по `git-syncthing-split` (черновик ai-dev-plugins, до ответа echelon)

Наше (акт, vdm-git):
1. **Сделано** — prep не готовит коммит, пока ветка обогнала свой коммит, и не называет её пропавшей (2.16.4).
2. **Предлагаем** — SessionStart vdm-git пишет `export GIT_OPTIONAL_LOCKS=0` в `CLAUDE_ENV_FILE`: собственные
   `git status` ассистента перестают переписывать индекс на любой машине (п. 5 брифа). Настройка 30.09 этого не
   покрывает: при другом mtime файла `git status` пишет индекс и с ней (замер в «Текущей модели»). Предел,
   измеренный в `hook-index-writes`: `git diff` без ревизии и `git describe --dirty` пишут индекс и при
   `GIT_OPTIONAL_LOCKS=0`. Цена — меняется окружение каждой Bash-команды каждой сессии с vdm-git; поэтому решение
   владельца, не наше.
3. **Предлагаем** — при старте сессии одна строка, если в `.git` лежат копии или HEAD называет недоехавший
   коммит: «git здесь сейчас не трогать, вот почему». Сегодня это видно только в момент prep.

Не наше:
4. Синк `.git` — решение владельца (vdx DL #17, 30.09: `.git` ездит); пересмотреть его — его дело, не предложение
   плагина; проверку проволоченности держит vdx.
5. Общий для машин сигнал «здесь идёт работа с git» — **не покрыт**. echelon держать его не может
   (`git-syncthing-split-roles-outcome`, 02.10): он работает на каждой машине отдельно из launchd, общее хранилище
   `data/` едет тем же Syncthing, замки — локальные, машины разводит расписанием. Вне Syncthing у машин общие только
   внешние сервисы и remote'ы git.
